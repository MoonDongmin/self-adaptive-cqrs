제공된 자료에 따르면, 이번 변경은 **Read Model 스키마 변경**이나 **새로운 테이블 생성**이 아닌, **투영 로직 (Projector) 의 예외 처리 정책 변경 (throw -> skip/log)** 및 **Dead-letter 로그 생성**을 포함하는 것입니다.

따라서 **v1 API 클라이언트의 구조적 변경은 전혀 필요 없습니다.** 클라이언트는 여전히 동일한 `read_grip_result` 테이블을 동일한 컬럼 구조로 조회할 수 있으며, 데이터가 누락되거나 `null`로 반환되는 경우를 처리하는 것은 클라이언트 측의 비즈니스 로직 (null check) 문제일 뿐, API 계약 (Contract) 이 깨지는 것은 아닙니다.

구체적인 단계별 절차는 다음과 같습니다.

### 1. 버전 경로 및 전략
*   **버전 전략**: **Backward Compatible (역호환)** 유지.
*   **이유**: 자료의 "Decision Outcome"에 명시된 바와 같이 "Read Model 구조 변경/신규 테이블 생성"은 Non-Goal(비목표)로 정의되어 있습니다. 스키마는 불변이며, API 엔드포인트도 변경되지 않습니다.
*   **버전 경로**: 기존 `v1` 경로를 그대로 유지합니다. 별도의 `v2` 버전을 생성할 필요가 없습니다.

### 2. 마이그레이션 및 컷오버 절차 (Human-in-the-loop)

DDL 실행이나 API 컷오버는 인간 승인이 필수이므로, 실제 데이터베이스 스키마 변경은 없으므로 **프로젝터 코드 수정 후 재시작**이 유일한 변경 사항입니다.

#### 단계 1: 코드 수정 (Developer Action)
*   `src/projection/projector/grip-result.projector.ts` 파일의 `map()` 함수 내 로직을 수정합니다.
*   `payload.objects` 가 빈 배열 (`length === 0`) 인 경우, 예외 (`throw new Error`) 를 던지는 대신 `LogAction.DEAD_LETTER` 로 로그를 남기고 `null` 을 반환하도록 변경합니다.
*   **주의**: `toyDataSchema` 의 Zod 검증 (`objects: z.array(objectsSchema)`) 에 `.min(1)` 을 추가하는 것은 이번 Non-Goal 항목이므로 수행하지 않습니다.

#### 단계 2: 인간 승인 (Human-in-the-loop)
*   변경된 코드가 적용된 상태 (배포된 상태) 를 확인합니다.
*   운영 담당자나 아키텍트가 "프로젝터 로직 수정 (Throw -> Skip/Log)"과 "Dead-letter 로그 생성"이 v1 API 클라이언트 호환성에 영향을 주지 않는다는 것을 승인합니다.
    *   *승인 근거*: 스키마 변경 없음, PK 유지, API 엔드포인트 변경 없음.

#### 단계 3: 재투영 (Re-projection / Catch-up)
*   수정된 프로젝터 (`grip-result-projector`) 를 재시작하거나, `CatchUpRunner` 를 재실행합니다.
*   이전 실패로 인해 `projection_cursor` 가 멈추거나, 정상 이벤트들이 롤백되어 미투영 상태인 경우, 커서를 현재 위치 (실패한 이벤트 이후) 로 재설정하여 미처리된 정상 이벤트들을 다시 투영합니다.
    *   *자료 참고*: "재실행 후 검증: poison 을 제외한 미투영 이벤트가 0 이어야 한다."

#### 단계 4: 검증 (Verification)
*   **DB 상태 확인**: `read_grip_result` 테이블에서 실패한 이벤트 (`5f22aa5e-c635-4cb1-ad2b-60856d1534dc`) 에 해당하는 레코드가 존재하지 않는지 확인합니다. (스킵 정책 적용 결과)
*   **정상 데이터 확인**: 실패한 이벤트의 `global_seq` 이전 및 이후의 정상 이벤트들이 `read_grip_result` 에 정상적으로 저장되었는지 확인합니다.
*   **API 응답 확인**: v1 API 클라이언트가 해당 시나리오 (빈 objects 가 있는 이벤트에 대한 쿼리) 를 실행했을 때, 해당 ID 에 대한 레코드가 없거나 `null` 을 반환하는지 확인합니다. 이는 클라이언트 로직이 `null` 처리를 해야 하므로, API 계약 자체는 깨지지 않았습니다.

#### 단계 5: Dead-letter 로그 확인
*   로그 시스템에서 `LogAction.DEAD_LETTER` 레벨의 로그가 생성되었는지 확인합니다.
    *   예: `objects 비어 있음 → skip` 메시지가 해당 이벤트 ID 로 기록되어야 합니다.

### 3. 요약: v1 API 클라이언트 보호를 위한 핵심
*   **추가 DDL 실행 금지**: `read_grip_result` 테이블 구조 변경 없이 유지합니다.
*   **추가 API 엔드포인트 생성 금지**: 기존 엔드포인트만 사용합니다.
*   **반응형 처리**: 클라이언트는 DB 에서 `null` 또는 `NOT FOUND` 를 반환받을 수 있으므로, 클라이언트 측에서 해당 ID 에 대한 조회 시 `null` 처리 로직을 갖춰야 합니다. 이는 API 계약 변경이 아닌, 클라이언트의 내구성 (Resilience) 강화입니다.

**결론**: 변경 사항이 **프로젝터 내부 로직**과 **로그 생성**에 국한되므로, v1 API 클라이언트는 별도의 버전 업그레이드 없이 기존 경로로 계속 작동하며, 데이터 누락 시 `null` 을 반환하는 것으로 충분합니다.
