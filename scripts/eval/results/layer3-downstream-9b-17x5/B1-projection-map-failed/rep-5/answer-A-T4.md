제공된 자료에 따르면, 이번 변경은 **Read Model DDL 변경**이 아닌 **결함 이벤트 (Poison Pill) 의 격리 및 스킵**을 위한 조치입니다. 따라서 기존 v1 API 클라이언트가 의존하는 테이블 스키마나 엔드포인트 구조는 변경되지 않습니다.

기존 v1 API 클라이언트가 깨지지 않게 하려면 **데이터 무결성 유지**와 **API 응답의 일관성**을 보장해야 합니다. 구체적인 단계는 다음과 같습니다.

### 1. 버전 경로 전략: 신구 병행 운영 (Backward Compatibility)
*   **이유**: 자료의 "API Versioning" 섹션에서 "API 버전 변경 없음"으로 명시되어 있으며, "신규 스키마·코드 변경의 확정"은 Non-Goal 로 정의되어 있습니다.
*   **조치**: 새로운 로직 (결함 이벤트 스킵) 은 기존 API 엔드포인트 (`/api/v1/read_grip_result`, `/api/v1/read_multimodal` 등) 에 적용되되, **버전 매개변수 (`?version=1`) 를 유지**합니다.
*   **결과**: 기존 v1 클라이언트는 URL 경로와 쿼리 파라미터가 동일하므로, 별도의 버전 경로 (`/api/v2/...`) 를 만들거나 기존 경로를 변경하지 않아도 됩니다.

### 2. 마이그레이션 절차: 인간 승인 후 DDL 적용 (Human-in-the-loop)
*   **이유**: "DDL 실행·API 컷오버는 인간 승인 후에만"이라는 제약 조건이 있습니다.
*   **조치**:
    1.  **격리 SQL 실행**: 먼저 `SELECT` 쿼리를 통해 `event_store` 에서 결함 이벤트 ID (`1582bc50-d513-4808-b5b8-523401a1c8f4`) 를 확인하고, 해당 이벤트가 `read_grip_result` 또는 `read_multimodal` 테이블에 영향을 미치는지 검증합니다.
    2.  **DDL 검토**: 만약 격리 SQL 에서 `read_grip_result` 테이블의 PK 제약 조건 (`scene_key`, `attempt_num`) 을 위반하는 데이터 (예: 빈 배열로 인해 생성될 수 없는 행, 혹은 PK 충돌) 가 예상되면, 해당 DDL 스크립트를 검토합니다. (현재 권고에서는 DDL 불필요하다고 명시되었으나, 안전을 위해 검토 단계는 필수입니다.)
    3.  **인간 승인**: DBA 또는 팀 리더가 "Poison 이벤트 스킵 및 격리"와 "DDL 변경 (필요시)"에 대해 승인합니다.

### 3. 컷오버 절차: 데이터 격리 후 재투영 (Data Containment & Replay)
*   **이유**: "projection_cursor 를 직접 전진시키지 마라"는 제약 조건과 "배치 트랜잭션 롤백" 위험 때문입니다.
*   **조치**:
    1.  **Poison 이벤트 격리**: 승인된 DDL (또는 스킵 로직) 을 적용하여 `event_store` 에서 결함 이벤트 (`1582bc50-d513-4808-b5b8-523401a1c8f4`) 를 `deleted` 또는 `dead_letter` 상태로 변경하거나, 투영 로직에서 해당 ID 를 필터링하도록 프로젝터 코드를 수정합니다.
    2.  **커서 유지**: `projection_cursor` 테이블의 `last_event_seq` 를 **변경하지 않습니다**. 이는 커서 이후의 정상 이벤트들이 다시 투영될 수 있도록 보장하며, 커서를 직접 조작하면 정상 이벤트가 영구히 유실될 수 있기 때문입니다.
    3.  **재투영 (Catch-up)**: 격리된 상태의 이벤트를 제외하고, `projection_cursor` 를 기준으로 프로젝터가 다시 시작되도록 합니다. 이 과정에서 결함 이벤트는 스킵되어 `read_grip_result` 테이블에 잘못된 행이 생성되지 않도록 합니다.
    4.  **검증**: 재투영이 완료된 후, `read_grip_result` 및 `read_multimodal` 테이블에서 해당 `stream_id` (`grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02011`) 에 대한 데이터가 정상적으로 존재하는지, 혹은 결함 이벤트로 인해 해당 시도가 누락되었는지 확인합니다.

### 요약
기존 v1 API 클라이언트를 보호하기 위해 **API 엔드포인트 URL 과 버전 파라미터는 변경하지 않고**, 백엔드에서는 **결함 이벤트를 데이터 스토어에서 격리 (스킵)**하여, **커서 위치는 그대로 유지**한 상태에서 **정상 이벤트만 재투영**하는 방식으로 진행합니다. DDL 변경은 인간 승인이 필수이며, 데이터 무결성 (PK 유지) 을 해치지 않는 범위 내에서만 실행됩니다.
