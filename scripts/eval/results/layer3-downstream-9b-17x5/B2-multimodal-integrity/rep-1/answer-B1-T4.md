제공된 자료 (로그 및 스키마) 에 따르면, 현재 `read_multimodal` 테이블은 `stream_id` 컬럼을 통해 이벤트 소싱 스트림을 식별하고 있으며, `global_seq` 컬럼을 통해 순서를 추적하고 있습니다. 또한, `stream_id` 는 `grip-attempt:장면_키` 형식을 사용하고 있어, 하나의 스트림이 하나의 장면 (`scene_key`) 과 하나의 시도 (`attempt_num`) 를 매핑하는 것으로 보입니다.

**주의:** 제공된 자료에는 **기존 v1 API 의 응답 형식, v2 API 의 변경 사항, 또는 버전 관리 전략**에 대한 정보가 전혀 포함되어 있지 않습니다. 따라서 "기존 v1 API 클라이언트가 깨지지 않게 하려면 무엇을 해야 하는가"라는 질문의 전제 조건 (v1 API 의 동작 방식, v2 의 변경 내용 등) 을 자료에서 유추할 수 없습니다.

이 경우, **자료에 없는 사실을 지어내지 않는 원칙**에 따라, 자료에 명시된 정보 (현재 상태) 만을 바탕으로 답변할 수 없습니다.

**결론:**
제공된 자료 (<logging_context>, <insight_read_db>) 에는 v1 API 의 구조나 v2 API 의 변경 사항에 대한 정보가 포함되어 있지 않으므로, **구체적인 마이그레이션 절차 (버전 경로, 신구 병행, 컷오버) 를 설계할 수 없습니다.**

*   **추천 조치:** v1 API 의 응답 스키마, v2 API 의 변경 사항 (예: 필드 추가/제거, 타입 변경, 구조 변경), 그리고 두 버전 간의 호환성 요구사항을 추가로 제공해 주시면, 해당 정보를 근거로 구체적인 마이그레이션 전략을 수립해 드리겠습니다.
