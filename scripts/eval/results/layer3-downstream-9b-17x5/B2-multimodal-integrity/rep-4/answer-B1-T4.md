제공된 자료 (로그 및 스키마) 에 따르면, 현재 `read_multimodal` 테이블의 `stream_id` 컬럼은 `grip-attempt:장면명_시도번호` 형식 (예: `grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02026`) 으로 정의되어 있습니다.

**[중요한 사실 확인]**
제공된 자료 (로그, 스키마, 상황 설명) 에서는 **기존 v1 API 클라이언트가 어떤 경로로 데이터를 호출하는지**, 또는 **v2 API 가 어떤 새로운 경로로 데이터를 호출해야 하는지**에 대한 정보가 전혀 포함되어 있지 않습니다.
*   `stream_id` 형식 변경에 따른 API 경로 (URL) 변경 필요성은 자료에 없습니다.
*   v1/v2 API 의 병행 운영 정책은 자료에 없습니다.
*   마이그레이션 절차의 구체적인 단계 (데이터 마이그레이션 스크립트 등) 는 자료에 없습니다.

따라서 "자료에 없는 사실은 지어내지 마라"는 지시에 따라, **자료에 근거할 수 없는 구체적인 API 변경 단계나 마이그레이션 절차를 제시할 수 없습니다.**

---

### 결론 및 대응 방안

현재 제공된 자료만으로는 "기존 v1 API 클라이언트가 깨지지 않게 하려면 무엇을 해야 하는가"에 대한 **구체적인 단계 (버전 경로, 신구 병행, 마이그레이션 절차)** 를 답변할 수 없습니다.

이 문제를 해결하기 위해서는 다음 정보를 추가로 제공해야 합니다:
1.  **v1 API 의 엔드포인트 정의**: 현재 v1 API 가 `stream_id` 를 어떻게 파싱하거나 URL 에 포함하는가? (예: `/api/v1/media/{scene_key}/{attempt}`)
2.  **v2 API 의 목표 엔드포인트 정의**: 변경 후 v2 API 가 `stream_id` 를 어떻게 처리할 것인가? (예: `/api/v2/media/{scene_key}/{attempt}` 또는 `stream_id` 를 직접 파라미터로 받는 경우)
3.  **데이터 마이그레이션의 범위**: `stream_id` 형식 변경이 `read_multimodal` 테이블의 `stream_id` 컬럼뿐만 아니라, 이를 참조하는 다른 테이블 (예: `read_grip_result`) 의 `stream_id` 도 함께 변경되는가?

**가정 (Hypothesis) 에 기반한 일반적인 CQRS/Event Sourcing 마이그레이션 패턴**이라면 다음과 같은 접근이 고려되지만, 이는 **자료에 없는 사실**이므로 답변으로 포함하지 않습니다.

*   **가정된 시나리오**: 만약 `stream_id` 형식이 `grip-attempt:장면명_시도번호` 에서 `scene_key:attempt` 로 변경된다면, v1 API 는 여전히 `stream_id` 를 `scene_key` 와 `attempt` 로 파싱하는 로직을 가지고 있다면, 데이터 스키마 변경 시 파싱 로직이 깨질 수 있습니다.

**요청하신 형식 (구체적 단계 포함) 으로 답변할 수 없는 이유:**
*   "버전 경로": v1/v2 의 경로 구조가 자료에 없습니다.
*   "신구 병행 운영": 병행 운영 기간과 전략이 자료에 없습니다.
*   "마이그레이션·컷오버 절차": 구체적인 SQL 스크립트나 절차가 자료에 없습니다.

**추천하는 다음 행동:**
v1 API 의 현재 구현 로직 (특히 `stream_id` 처리 부분) 과 v2 API 의 목표 스키마/로직을 명시해 주시면, 해당 자료의 `stream_id` 형식 (`grip-attempt:...`) 을 근거로 구체적인 마이그레이션 전략을 수립해 드리겠습니다.
