제공된 자료 (로그 컨텍스트, Read Model 스키마) 에 따르면, 요청하신 "객체별 파지 성공률 (시도 수, 성공 수, 성공률)"은 `read_grip_result` 테이블의 `object_name` 과 `grip_succeed` 필드를 집계하여 구할 수 있습니다.

하지만 질문하신 내용은 **기존 v1 API 클라이언트가 깨지지 않게 하는 변경 절차**에 대한 것입니다. 제공된 자료에는 기존 v1 API 의 응답 구조나 현재 서비스의 버전 관리 전략에 대한 정보가 포함되어 있지 않습니다. 따라서 "자료에 없는 사실은 지어내지 마라"는 원칙에 따라, **자료에 명시된 API 버전 정보나 기존 응답 스키마가 없으므로, 구체적인 버전 경로나 마이그레이션 절차를 정의할 수 없습니다.**

이러한 제약 하에서 답변할 수 있는 유일한 사실은 다음과 같습니다:

1.  **자료의 한계**: 제공된 `<logging_context>` 와 `<insight_read_db>` 에는 기존 v1 API 의 응답 형식, 필드명, 또는 버전 관리 규칙 (예: `/api/v1/...` vs `/api/v2/...`) 이 포함되어 있지 않습니다.
2.  **추론 불가**: 따라서 "버전 경로", "신구 병행 운영 방법", "마이그레이션 및 컷오버 절차" 중 구체적인 단계 (예: "version=1 인 요청은 기존 스키마로 응답한다", "version=2 인 요청은 새 스키마로 응답한다") 을 자료에 근거해 작성할 수 없습니다.

**결론**: 제공된 자료만으로는 구체적인 API 변경 및 마이그레이션 절차를 답변할 수 없으며, 기존 v1 API 의 스키마 정의나 버전 관리 정책이 추가로 필요합니다.

---

만약 **가상의 시나리오**로만 가정하여, 일반적인 이벤트 소싱/CQRS 아키텍처에서 새 Read Model 을 도입할 때의 **일반적인 원칙**을 묻는 것이라면, 다음과 같은 절차가 적용됩니다. (단, 이는 자료에 없는 내용임을 다시 한번 강조합니다.)

1.  **버전 경로 분리**: 새 API 엔드포인트를 별도의 버전 경로로 정의합니다. (예: `/api/v1/...` 은 기존 스키마, `/api/v2/...` 는 새 스키마 사용)
2.  **신구 병행 운영**: 새 Read Model (`read_grip_result` 집계 쿼리 등) 을 구축하되, 기존 v1 API 는 기존 Read Model 을 계속 사용하여 응답합니다.
3.  **Gradual Migration**: 클라이언트 측에서 새 버전 (v2) 을 지원하도록 업데이트된 후, 서버 측에서 새 Read Model 을 완전히 전환합니다.

**요청하신 대로 자료에 근거한 구체적인 SQL 코드나 절차는 작성할 수 없습니다.**
