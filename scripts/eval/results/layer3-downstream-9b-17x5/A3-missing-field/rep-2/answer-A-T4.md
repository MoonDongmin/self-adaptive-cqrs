제공된 자료에 따르면, 이번 변경은 **Read Model 테이블 구조 변경**이나 **API 엔드포인트 변경**이 없으며, 기존 v1 자산 (테이블/엔드포인트/프로젝터) 을 무손상 상태로 유지하는 것이 핵심 목표입니다.

따라서 기존 v1 API 클라이언트가 깨지지 않도록 하기 위한 구체적인 단계는 다음과 같습니다.

### 1. 버전 경로 전략: 새 버전 생성 (Parallel Versioning)
*   **행동**: 기존 API 엔드포인트 (`/projection/multimodal`, `/projection/grip-result`, `/projection/insert-all`) 의 경로를 변경하지 않고, **새로운 버전 경로**를 생성하여 변경된 로직을 노출합니다.
*   **구체적 경로**:
    *   기존: `/api/v1/projection/multimodal`
    *   새 버전: `/api/v2/projection/multimodal` (또는 `/api/v1/projection/multimodal/v2` 등 조직의 버전 관리 규칙에 따름)
*   **이유**: 자료의 "API Versioning" 섹션에서 "변경 없음. ... API 계약 불변"으로 명시되어 있으므로, 기존 클라이언트는 새 버전으로 이동하지 않고 현재 경로 (`/v1`) 를 계속 호출하며, 새 버전은 새 클라이언트나 호환성 테스트를 위해 별도로 노출합니다.

### 2. 신구 병행 운영 (Parallel Operation)
*   **행동**: 새 버전 API (`/v2`) 와 기존 버전 API (`/v1`) 를 **동시에** 운영합니다.
*   **로직**:
    *   **`/v1` (기존)**: 현재 구현된 로직 (Zod 거절 시 파일 스킵, Read Model 업데이트 없음) 을 그대로 유지합니다. 기존 클라이언트 연결은 이 경로로 이어지므로 깨지지 않습니다.
    *   **`/v2` (새 로직)**: "무유입 검증 절차"를 적용합니다.
        *   `insert.batch.done` 후, 실패 파일에서 도출된 `stream_id` 와 `attempt_num` 을 사용하여 `event_store` 에 해당 이벤트가 실제로 유입되었는지 `SELECT count(*)` 로 확인합니다.
        *   카운트가 0 이라면 (Zod 거절로 인해 유입 안 됨), 해당 `stream_id` 와 `attempt_num` 조합의 Read Model (`read_grip_result`, `read_multimodal`) 에서는 데이터가 조회되지 않거나 (NULL/Empty) 또는 명시적인 '미적재' 상태 플래그를 반환합니다.
        *   카운트가 1 이상이라면 (정상 유입), 기존과 동일하게 Read Model 을 업데이트하고 반환합니다.

### 3. 마이그레이션 및 컷오버 절차 (Human-in-the-loop)
*   **단계 1: DDL 승인 및 적용**
    *   자료의 "Read Model 생성 SQL" 섹션에 있는 **격리 (Containment) SQL**을 실행합니다.
    *   **주의**: 이 SQL 은 `read_grip_result` 또는 `read_multimodal` 테이블의 **DDL 변경 (ALTER TABLE)** 이 아니라, **데이터 조회용 SELECT 쿼리**입니다. 따라서 테이블 구조 변경 (PK 추가 등) 이 없으므로 v1 자산 무손상 원칙에 위배되지 않습니다.
    *   만약 "무유입 검증"을 위해 `event_store` 테이블에 인덱스를 추가하거나, 임시 검증 테이블을 생성해야 한다면, 해당 DDL 변경은 **인간 승인 후**에만 실행됩니다. (자료: "DDL 실행·API 컷오버는 인간 승인 후에만")
*   **단계 2: 새 API (`/v2`) 배포**
    *   새 버전의 API 서버를 배포하여 병행 운영을 시작합니다.
    *   기존 `/v1` 클라이언트는 `/v1` 엔드포인트를 계속 사용하여 정상 작동합니다.
*   **단계 3: 검증 및 모니터링**
    *   새 버전 API (`/v2`) 가 "Zod 거절된 파일은 Read Model 에 반영되지 않음 (무유입)" 로직을 올바르게 수행하는지 모니터링합니다.
    *   특히 `반려동물용품_CR01_강아지공룡알장난감_02004` 와 `02005` 파일에 대한 조회 결과가 기존 v1 로직 (데이터 없음) 과 일치하는지 확인합니다.
*   **단계 4: 컷오버 (Cutover)**
    *   새 버전 (`/v2`) 로직이 안정적으로 작동하고, 기존 v1 로직의 문제점 (Zod 거절로 인한 불일치) 을 해결했음을 확인합니다.
    *   **인간 승인**을 받습니다.
    *   기존 `/v1` 클라이언트들이 새 버전 (`/v2`) 로 이동하도록 안내합니다.
    *   `/v1` 서버를下线 (Decommission) 합니다.

### 요약
기존 v1 API 클라이언트를 보호하기 위해 **API 경로를 버전화 (`/v1` 유지, `/v2` 추가)** 하고, **병행 운영**을 통해 새 로직 (무유입 검증) 을 검증한 후, **인간 승인**을 거쳐 **컷오버**하는 것이 정답입니다. 자료에 명시된 "v1 자산 무손상" 및 "DDL 실행·API 컷오버는 인간 승인 후에만" 제약 조건을 모두 만족합니다.
