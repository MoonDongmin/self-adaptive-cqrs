제공된 자료에 따르면, 이번 변경은 **Zod 스키마 검증 로직을 강화하여 유효하지 않은 데이터를 원천에서 차단**하는 것이며, **Read Model 테이블 구조나 API 엔드포인트는 변경되지 않습니다**. 따라서 기존 v1 API 클라이언트는 구조적 변경 없이 그대로 작동할 수 있습니다.

하지만, **격리 SQL**을 통해 `insert.file.failed` 로그에 포함된 파일들이 이벤트 스토어에 실제로 유입되지 않았음을 **검증 (Audit)**하는 절차가 추가됩니다. 이 검증 로직이 API 응답에 직접 노출되거나, 클라이언트가 이를 직접 호출해야 하는 구조라면 API 호환성에 영향을 줄 수 있습니다.

따라서 "기존 v1 API 클라이언트가 깨지지 않게 하려면"이라는 질문의 전제 (API 응답 구조 변경) 를 고려할 때, **API 레벨에서는 변경이 없어야 하며**, 추가된 검증 로직은 **백엔드 내부 프로세스 (Human-in-the-loop 승인 단계)**로 격리되어야 합니다.

구체적 단계는 다음과 같습니다.

### 1. 버전 경로 전략: v1 유지 및 병행 운영
*   **이유**: 자료의 "Decision Outcome"에 "Modifying Zod schema... Altering projector logic... Creating new ReadModel tables"이 Non-Goals 로 명시되어 있으며, "API Versioning" 섹션에서도 "변 변경 없음"으로 결론이 났습니다.
*   **조치**: 기존 `/api/v1` 경로를 유지합니다. 새로운 기능 (검증 로직) 을 별도의 API 버전 (예: `/api/v2/audit`) 으로 노출하지 않거나, 기존 `/api/v1` 내부의 비동기 백엔드 작업으로 처리합니다.
*   **결과**: 클라이언트는 `/api/v1` 엔드포인트를 호출했을 때, 기존과 동일한 스키마와 응답 구조를 반환받으므로 깨지지 않습니다.

### 2. 신구 병행 운영 (Parallel Operation)
*   **이유**: "DDL 실행·API 컷오버는 인간 승인 후에만"이라는 제약 조건과 "v1 자산 무손상" 원칙 때문입니다.
*   **조치**:
    1.  **준비 단계**: 새로운 검증 로직 (격리 SQL) 을 백엔드 코드에 배포하되, 실제 데이터베이스에 DDL을 적용하지는 않습니다.
    2.  **검증 단계**: 인간 (운영자) 이 격리 SQL 을 실행하여 "유입된 이벤트가 0 개인지" 확인합니다.
        *   SQL: `SELECT count(*) FROM event_store WHERE (stream_id, attempt_num) IN (...)`
    3.  **승인 단계**: 인간이 "0 개 (정상)" 또는 "유입됨 (수정 필요)" 결과를 확인하고 승인합니다.
    4.  **적용 단계**: 인간 승인이 완료되면, 해당 DDL (필요시) 이나 설정을 적용하여 프로덕션으로 전환합니다.
*   **결과**: 클라이언트가 API 를 호출하는 동안 백엔드 내부에서 검증 로직이 적용되는지 여부는 클라이언트에게 투명하게 처리됩니다.

### 3. 마이그레이션 및 컷오버 절차
*   **이유**: "식별자 전체 단어" 및 "PK 유지" 제약과 데이터 무결성 때문입니다.
*   **조치**:
    1.  **데이터 격리**: `insert.file.failed` 로 거절된 파일 (`반려동물용품_CR01_강아지공룡알장난감_02004`, `02005`) 에 대한 이벤트가 `event_store` 에 존재하는지 확인합니다.
    2.  **결과 처리**:
        *   **Case A (0 건)**: 이벤트가 유입되지 않았으므로, Read Model (`read_grip_result`, `read_multimodal`) 에 해당 키의 데이터가 생성되지 않았습니다. 이는 **정상적인 상태**이므로, 클라이언트가 해당 ID 로 조회했을 때 "데이터 없음 (404 또는 null)"을 반환하면 됩니다. 기존 v1 클라이언트는 이 경우를 처리할 수 있어야 합니다.
        *   **Case B (N > 0 건)**: 이벤트가 유입되었다면, 이는 **데이터 오염**입니다. 인간 승인이 필요하며, 승인 후 해당 이벤트를 `event_store` 에서 삭제하거나, Zod 스키마를 완화하여 (Non-Goal 이므로 권장되지 않음) 처리해야 합니다.
    3.  **컷오버**: 인간이 "Case A"를 확인하고 승인하면, 해당 배치 처리를 완료하고 다음 배치로 넘어갑니다. API 응답은 기존 v1 로 유지됩니다.

### 요약: API 클라이언트 무결성 보장 방안

1.  **API Contract 불변**: 이번 변경 사항 (Zod 강화, 검증 로직 추가) 은 **API 응답 스키마와 엔드포인트 경로를 변경하지 않습니다**.
2.  **내부 로직 격리**: 추가된 검증 로직은 API 호출 경로가 아닌, **배치 적재 (Batch Insert) 후, 투영 (Projection) 전**의 백엔드 내부 프로세스입니다.
3.  **클라이언트 영향 최소화**:
    *   유효한 데이터: 정상적으로 조회됨.
    *   무효한 데이터 (Zod 거절): 이벤트 스토어에 안 들어감 -> Read Model 에 없음 -> API 조회 시 "없음" 반환 (기존 v1 로 처리 가능).
    *   예외 상황 (유입된 무효 데이터): 인간 승인 전까지 API 에는 노출되지 않거나, 인간 승인 후에도 해당 데이터는 시스템에서 격리/삭제되므로 클라이언트가 깨지거나 잘못된 데이터를 신뢰할 위험이 줄어듭니다.

**결론**: 버전 경로를 변경하지 않고 (`/api/v1` 유지), 추가된 검증 로직은 백엔드 내부의 **인간 승인 게이트**로 격리하여 운영하면, 기존 v1 API 클라이언트는 깨지지 않습니다.
