제공된 자료 (로그 및 스키마) 에 따르면, 현재 시스템은 `insert.file.failed` 로그를 발생시키고 있으며, 이는 Zod 검증 실패로 인해 이벤트가 저장소 (Event Store) 에 적재되지 않았음을 의미합니다.

**중요한 사실 확인:**
제공된 자료에는 **기존 v1 API 클라이언트의 구조, v2 API 의 정의, 또는 두 버전 간의 호환성 요구사항**에 대한 정보가 전혀 포함되어 있지 않습니다.
- `read_grip_result` 및 `read_multimodal` 테이블의 스키마는 제공되었으나, 이를 통해 노출되는 API 엔드포인트의 버전 (v1, v2 등) 이나 필드명 변경 사항이 명시되지 않았습니다.
- `insert.file.failed` 로직이 API 응답에 어떻게 반영되는지 (예: 200 OK 로 성공 처리하되 에러 코드를 포함하거나, 400 에러를 반환하는지) 에 대한 정의가 없습니다.

따라서 "기존 v1 API 클라이언트가 깨지지 않게 하려면"이라는 전제에 대한 구체적인 답변 (버전 경로 변경, 마이그레이션 절차 등) 을 자료에 근거하여 작성할 수 없습니다.

**해결을 위한 요청:**
다음과 같은 추가 정보가 필요합니다.
1. **v1 API 의 응답 스키마/구조:** 현재 v1 API 가 어떤 필드를 반환하는가?
2. **예상되는 v2 API 의 변경 사항:** 새로운 로직 (예: 실패 처리 로직 변경) 에 따라 API 응답이 어떻게 달라져야 하는가?
3. **클라이언트 의존성:** 클라이언트가 API 응답의 어떤 필드에 강하게 의존하고 있는가?

### [가상의 시나리오 기반] 일반적인 마이그레이션 전략

만약 자료에 없는 일반적인 상황 (예: API 응답 필드 추가 또는 에러 처리 방식 변경) 이라고 가정하여, **기존 클라이언트 호환성을 유지하는 표준 절차**를 제안합니다.

#### 1. 버전 경로 전략 (Versioning Strategy)
API 엔드포인트에 버전을 명시하는 것이 가장 안전합니다.
- **기존:** `GET /api/v1/read_grip_result`
- **신규:** `GET /api/v2/read_grip_result`
- **이유:** 클라이언트 코드 수정 없이 새 버전을 호출할 수 있으며, 기존 v1 클라이언트는 v1 엔드포인트로 계속 작동합니다.

#### 2. 신구 병행 운영 (Parallel Operation)
- **데이터 동기화:** 이벤트 소싱 아키텍처에서 Read Model 을 업데이트하는 프로세스는 버전과 무관하게 동일한 이벤트 스토어에서 읽으므로, v1 과 v2 Read Model 은 자연스럽게 동기화됩니다.
- **트래픽 분할:**
    - 신규 클라이언트: v2 엔드포인트 호출.
    - 기존 클라이언트: v1 엔드포인트 호출.
    - 백엔드: 두 개의 별도 컨트롤러/라우터 구현.

#### 3. 마이그레이션 및 컷오버 절차 (Migration & Cutover)
자료에 없는 구체적인 필드 변경 사항이 없으므로, 일반적인 단계로 구성합니다.

**Step 1: v2 API 개발 및 테스트**
- `read_grip_result` 및 `read_multimodal` 스키마를 기반으로 v2 API 응답을 정의합니다.
- **호환성 체크:** v1 API 응답 필드가 v2 API 에 포함되는지 확인합니다. (필요시 v2 에 기본값을 추가하거나, v1 필드를 v2 에 포함)
- **에러 처리 시나리오 테스트:** `insert.file.failed` 로직이 v2 API 에 어떻게 노출되는지 (예: `status: "failed"`, `error_detail` 필드 포함) 테스트합니다.

**Step 2: 병행 배포 (Blue-Green 또는 Canary)**
- **환경 준비:** v1 API 와 v2 API 를 동시에 배포합니다.
- **라우팅:** Load Balancer 또는 API Gateway 에서 트래픽을 분할합니다.
    - `GET /api/v1/...` -> v1 로직
    - `GET /api/v2/...` -> v2 로직
- **기존 클라이언트 영향:** 기존 클라이언트는 v1 엔드포인트를 계속 호출하므로 **절대 깨지지 않습니다**.

**Step 3: 데이터 마이그레이션 (필요시)**
- v2 API 가 새로운 필드 (예: `insert.file.failed` 관련 상세 정보) 를 반환하도록 Read Model 을 업데이트해야 한다면, 해당 필드를 포함하는 새로운 이벤트 스키마를 정의하고, 과거 데이터에 해당 필드가 없으면 `null` 또는 기본값으로 처리되도록 쿼리를 작성합니다.
- **Postgres 쿼리 예시 (가상):**
    ```sql
    -- v2 API 가 필요로 하는 새로운 필드가 없으면 기존 데이터는 그대로 조회됨
    SELECT 
        scene_key, 
        attempt_num, 
        object_name, 
        grip_succeed, 
        gripper_type, 
        occurred_at, 
        grip_2d_pose, 
        grip_3d_pose, 
        robot_tf, 
        human_annotation_grasp, 
        stream_id, 
        global_seq
    FROM read_grip_result
    WHERE scene_key = 'target_scene' AND attempt_num = 1;
    ```

**Step 4: 컷오버 (Cutover)**
- **기존 클라이언트 업데이트:** 신규 클라이언트 배포 후, 기존 클라이언트 개발자가 v1 API 를 v2 API 로 변경하는 코드 수정을 진행합니다.
- **트래픽 전환:** API Gateway 에서 v1 엔드포인트 라우팅을 v2 엔드포인트로 변경합니다.
- **v1 엔드포인트下线:** v1 API 로직을 제거합니다.

**Step 5: 모니터링 및 롤백**
- v2 API 응답 속도와 에러율 (특히 `insert.file.failed` 관련 에러) 를 모니터링합니다.
- 문제가 발생하면 즉시 Load Balancer 설정을 v1 로 되돌립니다.

### 결론
자료에 **API 버전별 응답 구조의 차이**에 대한 정보가 없으므로, 구체적인 "깨지지 않게 하는 방법"을 코드 레벨로 제시할 수 없습니다. **API 버전화 (`/v1`, `/v2`) 와 트래픽 분할**이 유일한 안전한 접근법입니다.
