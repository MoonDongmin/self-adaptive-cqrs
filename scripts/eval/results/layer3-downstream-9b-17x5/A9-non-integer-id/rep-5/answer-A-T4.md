제공된 자료에 따르면, 이번 변경은 **Read Model 생성 SQL**이 필요하지 않으며, **격리 (Containment)** 단계만 수행해야 합니다.

1.  **권고 내용 분석**: "Read Model 생성 SQL" 섹션에서 명시적으로 "신규 Read Model DDL 불필요, 결함 데이터 무해화가 조치다"라고 되어 있습니다.
2.  **API 버전 영향**: "API 버전 변경 없음"으로 명시되어 있습니다.
3.  **결론**: 기존 v1 API 클라이언트는 변경 사항 (DDL 실행 없음, API 경로 변경 없음) 을 전혀 인지하지 못하므로, **어떤 추가 작업도 수행할 필요가 없습니다**. 기존 API 클라이언트는 그대로 정상 작동하며, 데이터 유입이 차단될 뿐입니다.

따라서 구체적인 단계별 절차는 다음과 같습니다.

### 1. 버전 경로 (Versioning Strategy)
*   **전략**: **비파괴적 격리 (Non-destructive Containment)**
*   **이유**: 자료에 따르면 DDL 변경이나 API 컷오버가 없으므로, 버전 관리 (예: `/v1` -> `/v2` 병행) 가 불필요합니다. 기존 `/v1` 엔드포인트를 유지하며, 해당 엔드포인트에서 결함 데이터에 대한 조회를 차단하거나 빈 값을 반환하는 로직만 강화하면 됩니다.

### 2. 신구 병행 운영 (Parallel Operation)
*   **필요성**: **없음**
*   **이유**: API 스키마 변경이 없으므로, 새 버전 API를 배포하여 기존 클라이언트를 점진적으로 전환할 필요가 없습니다.

### 3. 마이그레이션 및 컷오버 절차 (Migration & Cutover)
*   **DDL 실행**: **무시 (Skip)**
    *   자료에 명시된 `SELECT count(*)` 쿼리는 검증용이며, 실제 테이블 구조를 변경하는 `CREATE/ALTER` DDL은 실행하지 않습니다.
*   **API 컷오버**: **인간 승인 후 즉시 적용 (Human-in-the-loop Cutover)**
    *   **준비 단계**:
        1.  격리 SQL (`SELECT count(*) ...`) 을 실행하여 `rejected_event_count` 가 0 이나 기대치에 부합하는지 확인합니다. (자료에 따르면 2 개의 파일이 거절되었으므로, 해당 stream_id 와 attempt_num 조합의 이벤트가 event_store 에 없음을 확인해야 합니다.)
        2.  검증이 통과되면, 해당 로그 (docId: `analysis-7a4d68a1-3b98-4a36-b959-42062ac6ee0b`) 를 승인합니다.
    *   **실행 단계**:
        1.  승인 후, **적재 파이프라인의 Zod 검증 로직**을 수정하여 해당 필드 타입 (`int` vs `number`) 에 대한 허용 범위를 확장하거나, 타입 변환 로직을 추가합니다. (DDL 변경 없음)
        2.  수정된 파이프라인을 재시작하여, 이전에 거절되었던 2 개의 파일 (`반려동물용품_CR01_강아지공룡알장난감_02022`, `반려동물용품_CR01_강아지공룡알장난감_02023`) 을 다시 적재합니다.
        3.  적재가 성공하면, 해당 데이터는 자동으로 `read_grip_result` 와 `read_multimodal` 테이블에 INSERT 됩니다.
    *   **결과**: 기존 v1 API 클라이언트는 변경 없이 그대로 사용되며, 이제 거절되었던 데이터가 정상적으로 조회 가능해집니다.

### 요약
기존 v1 API 클라이언트를 깨뜨리지 않으려면 **API 엔드포인트 경로를 변경하지 않고**, **데이터 파이프라인의 입력 검증 (Zod) 로직만 수정**하여 해당 파일들의 적재 성공률을 높이는 것만 수행하면 됩니다. 별도의 마이그레이션 스크립트나 API 버전 업그레이드 절차는 불필요합니다.
