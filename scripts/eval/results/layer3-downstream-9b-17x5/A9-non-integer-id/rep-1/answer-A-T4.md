제공된 자료에 따르면, 이번 변경은 **Read Model 생성 SQL**이 필요하지 않으며, **격리 (Containment) SQL**만 실행하여 Zod 검증 실패로 인해 Event Store 에 유입되지 않았음을 확인하는 단계입니다.

자료의 'Decision Outcome'에 명시된 대로 "거절 유지 + 원천 데이터 수정 요청"이 선택되었으며, "API 버전 변경 없음"으로 결정되었습니다. 따라서 기존 v1 API 클라이언트는 **버전 경로 변경 없이 그대로 사용**할 수 있습니다.

구체적 단계는 다음과 같습니다:

1.  **격리 SQL 실행**: 제공된 격리 SQL 을 실행하여, 검증 실패로 인해 Event Store 에 해당 이벤트가 실제로 존재하지 않음을 데이터베이스 수준에서 확인합니다.
    ```sql
    SELECT count(*) AS rejected_event_count FROM event_store WHERE (stream_id, attempt_num) IN (('grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02022', 1), ('grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02023', 1));
    ```
    *   **기대 결과**: `rejected_event_count` 가 `0` 이어야 합니다. 이는 해당 시도의 이벤트가 저장소에 없음을 의미하며, Read Model 에 해당 레코드가 생성되지 않았음을 보장합니다.

2.  **API 클라이언트 영향 평가**:
    *   **버전 경로**: 변경 없음 (`/api/v1/...` 유지).
    *   **데이터 반환**: 해당 시도의 데이터는 Read Model 에 존재하지 않으므로, 해당 시도를 조회하는 API 호출 시 해당 레코드에 대한 응답은 없을 것입니다 (404 또는 빈 배열 포함). 이는 원본 데이터가 적재되지 않았으므로 정상적인 동작입니다.
    *   **기존 클라이언트 호환성**: 스키마 변경이 없고 API 엔드포인트도 변경되지 않았으므로, 기존 v1 API 클라이언트는 추가 수정 없이 정상적으로 작동합니다.

3.  **Human-in-the-loop 승인**: 위 SQL 실행 결과 (`count(*) = 0`) 가 확인되면, 인간 운영자가 "격리 조치 승인"을 합니다.

4.  **원천 데이터 수정 요청**: 승인 후, 개발자에게 Zod 검증 실패 원인 (float 가 int 로 변환 필요) 을 인지하고, 원천 파일 (`반려동물용품_CR01_강아지공룡알장난감_02022_01_20230923.json`, `반려동물용품_CR01_강아지공룡알장난감_02023_01_20230923.json`) 을 수정하여 재적재 (Retry) 를 요청합니다.

5.  **재적재 및 투영**: 원천 파일이 수정되면, 다음 배치에서 `insert.file.ok` 로 성공적으로 적재되고, Projection 을 통해 Read Model (`read_grip_result`, `read_multimodal`) 에 정상 레코드가 생성됩니다.

6.  **컷오버**: 원천 데이터 수정이 완료되고, 재적재된 데이터가 투영되어 Read Model 에 정상적으로 반영된 것을 확인한 후, 해당 격리 SQL 을 제거하거나 (필요시) 현재 상태를 유지합니다. API 컷오버는 발생하지 않습니다.

**요약**: 기존 v1 API 클라이언트는 깨지지 않습니다. 변경 사항은 **Event Store 에 해당 이벤트가 없는지 확인하는 SQL**만 실행하고, **API 엔드포인트나 스키마는 변경하지 않으며**, **원천 데이터 수정**을 통해 문제를 해결하는 것입니다.
