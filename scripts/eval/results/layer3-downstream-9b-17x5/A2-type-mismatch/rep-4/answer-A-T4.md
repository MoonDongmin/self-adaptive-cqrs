제공된 자료에 따르면, 이번 변경은 **Zod 스키마 정의 변경**과 **Read Model DDL 변경**이 필요하지 않으며, **무유입 검증용 격리 SQL**만 실행하는 것으로 결정되었습니다.

따라서 기존 v1 API 클라이언트가 깨지지 않도록 보장하는 핵심은 **API 계약 (Contract) 의 불변성**입니다. 자료의 'Decision Outcome'에 "Zod 스키마·엔드포인트·Read Model 테이블 정의가 그대로 유지"라고 명시되어 있으므로, API 경로 변경이나 새로운 엔드포인트 추가 없이, 기존 요청/응답 구조를 그대로 유지하며 내부 데이터 무결성만 점검하는 절차로 진행해야 합니다.

구체적 단계는 다음과 같습니다.

### 1. 버전 경로 전략: 기존 v1 경로 유지 (Backward Compatibility)
*   **이유**: 자료의 'Decision Outcome'에 "변경 없음"이 명시되어 있고, 'Non-Goals'에 "API 컷오버"가 포함되어 있습니다.
*   **조치**: 클라이언트가 호출하는 엔드포인트 경로 (예: `/api/v1/read-grip-result`) 를 변경하지 않습니다. 새로운 버전 (예: `/api/v2/...`) 을 생성하거나 기존 경로를 리디렉션하지 않습니다.

### 2. 신구 병행 운영: 불필요
*   **이유**: Read Model 구조 (`read_grip_result`) 와 스키마 정의가 변경되지 않으므로, 새로운 스키마를 위한 별도의 API 응답 포맷을 만들 필요가 없습니다.
*   **조치**: 기존 v1 API 로직을 그대로 사용합니다.

### 3. 마이그레이션 및 컷오버 절차: 격리 SQL 실행 후 즉시 컷오버
*   **이유**: 이번 변경의 유일한 실행 대상은 '격리 (Containment) SQL'입니다. 이는 실패한 데이터가 Event Store 에 유입되지 않았음을 확인하는 검증 쿼리입니다. DDL 변경이 없으므로 마이그레이션 스크립트 (ALTER TABLE 등) 가 필요 없습니다.
*   **절차**:
    1.  **준비**: 실행할 SQL 쿼리를 준비합니다. (자료 2-절 제공)
    2.  **인간 승인 (Human-in-the-loop)**: SQL 실행 전, 해당 쿼리가 `event_store` 에서 실패한 시퀀스 ID 가 0 개를 반환하는지 확인하여 승인합니다.
    3.  **격리 SQL 실행**: 승인 후 아래 SQL 을 실행하여 데이터 무결성을 검증합니다.
    4.  **컷오버**: 검증이 성공하면 (기대값 0), 해당 배치 처리를 완료하고 정상 운영 상태로 전환합니다. API 는 변경 없이 그대로 작동합니다.

### 적용할 SQL 코드

```sql
SELECT count(*) AS rejected_event_count FROM event_store WHERE (stream_id, attempt_num) IN (('grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02002', 1), ('grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02003', 1));
```

### 요약
기존 v1 API 클라이언트를 보호하기 위해 **엔드포인트 경로를 변경하지 않고**, **Read Model 스키마를 변경하지 않으며**, **실패한 이벤트가 DB 에 남지 않았음을 검증하는 격리 SQL 만 실행**하는 것이 유일한 변경 사항입니다.
