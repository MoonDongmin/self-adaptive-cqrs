제공된 자료 (로그 및 스키마) 에 따르면, 현재 시스템은 `insert.file.failed` 로직이 **이벤트 소싱 (Event Sourcing)** 단계에서 실패한 경우, 해당 이벤트를 **생성하지 않고 (Append Skip)** 로그만 남기는 것으로 보입니다.

자료에 명시된 `insert.file.failed` 로그 (`reason=[...]`) 는 Zod 검증 실패를 의미하며, `insert.file.ok` 로그가 없는 경우 해당 `stream_id` 와 `global_seq` 를 가진 이벤트가 이벤트 스토어에 저장되지 않습니다.

이러한 상황 (이벤트 누락) 에서 기존 v1 API 클라이언트가 깨지지 않게 하려면, **Read Model (DB) 에 해당 레코드가 존재하지 않는 상태**를 유지해야 합니다. CQRS 아키텍처에서 이벤트가 생성되지 않았으므로, Projection (프로젝터) 은 해당 이벤트를 읽지 못해 DB 에 행을 생성하지 않습니다. 따라서 기존 API 는 "데이터 없음" 상태를 반환하게 되며, 이는 클라이언트 측에서 "데이터가 아직 안 올랐다" 또는 "404 Not Found"를 처리하는 기존 로직과 호환됩니다.

따라서 **추가적인 마이그레이션 절차나 버전 경로 변경은 불필요**하며, **신구 병행 운영도 필요 없습니다**.

구체적 단계는 다음과 같습니다:

1.  **이벤트 생성 로직 수정 (필수)**
    *   현재 `insert.file.failed` 로직을 확인하여, Zod 검증 실패 시 `insert.file.failed` 로그만 남기고 `insert.file.ok` 로직을 바로 종료하도록 유지해야 합니다.
    *   **주의:** 만약 현재 로직이 `insert.file.failed` 발생 시에도 `insert.file.ok` 로그를 남기거나, 해당 `stream_id` 를 가진 이벤트를 강제로 생성하는 경우, DB 에 잘못된 데이터 (예: 검증 실패한 데이터지만 성공으로 기록됨) 가 생성되어 기존 API 가 깨질 수 있습니다.
    *   **조치:** `insert.file.failed` 발생 시 `insert.file.ok` 로그를 발행하지 않도록 코드를 수정하여, **이벤트 스토어에 아무 이벤트도 기록하지 않게** 하세요.

2.  **Read Model 상태 확인 (기존 동작 유지)**
    *   해당 `stream_id` (예: `grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02002`) 에 대한 이벤트가 생성되지 않으므로, Projection (`multimodal-projector`) 은 해당 시퀀스 (`global_seq`) 를 읽지 못합니다.
    *   결과적으로 `read_grip_result` 와 `read_multimodal` 테이블에 해당 `scene_key` 와 `attempt_num` 조합의 행이 **생성되지 않습니다**.
    *   기존 v1 API 는 해당 키로 조회 시 **NULL** 또는 **404**를 반환하게 되며, 이는 "데이터 적재 실패"라는 사실을 클라이언트에 알리는 정상적인 동작입니다.

3.  **버전 관리 및 마이그레이션 (불필요)**
    *   **버전 경로:** 변경 사항이 없으므로 API 버전 (`/api/v1/...`) 을 유지합니다.
    *   **신구 병행 운영:** 데이터 모델 (스키마) 이 변경되지 않았으므로 (이벤트가 안 생기는 것뿐, DB 스키마는 동일), 별도의 병행 운영이 필요 없습니다.
    *   **마이그레이션/컷오버:** 데이터 스키마 변경이 없으므로 마이그레이션 스크립트나 컷오버 절차는 수행하지 않습니다.

4.  **클라이언트 측 대응 (선택 사항, 권장)**
    *   클라이언트 측에서는 해당 `scene_key` 와 `attempt_num` 조합에 대해 API 호출 시 **404 Not Found** 또는 **null** 응답을 처리하는 로직을 유지해야 합니다.
    *   만약 클라이언트가 "데이터가 없으면 예외 발생" 로 동작한다면, 현재 로직 (이벤트 누락) 은 이를 자연스럽게 처리합니다.

**결론:**
자료에 따르면 검증 실패 시 이벤트가 생성되지 않으므로, **DB 에 해당 레코드가 생성되지 않게 막는 것**만으로도 기존 v1 API 클라이언트는 깨지지 않습니다. 별도의 API 버전 변경이나 마이그레이션 절차는 필요 없습니다.
