제공된 자료에 따르면, 이번 변경은 **Read Model DDL 생성**이 아닌 **Zod 스키마 유지 및 원천 데이터 수정 워크플로우 강화**로 결정되었습니다. 따라서 Read Model 테이블 구조나 API 엔드포인트의 스키마는 변경되지 않습니다.

기존 v1 API 클라이언트가 깨지지 않도록 보장하기 위한 구체적인 단계는 다음과 같습니다.

### 1. 버전 경로 전략: 새 버전 생성 (v1 유지)
*   **이유**: 자료의 "Decision Outcome"에서 "Zod 스키마 완화", "Read Model 스키마·엔드포인트 불변", "API 계약 그대로 유지"로 명시되어 있습니다.
*   **조치**: 기존 `v1` 경로의 API 엔드포인트와 스키마를 **절대 수정하지 않습니다**.
*   **결과**: 기존 v1 클라이언트는 현재와 동일한 엔드포인트 (`/api/v1/...`) 와 동일한 요청/응답 스키마를 사용하여 정상적으로 작동합니다.

### 2. 신구 병행 운영: 불필요함
*   **이유**: API 스키마와 엔드포인트가 변경되지 않으므로, 새 버전 (예: `v2`) 을 만들어 병행 운영하는 것은 불필요하며 오히려 트래픽 분산과 유지보수 오버헤드를 초래합니다.
*   **조치**: `v1` 경로만 계속 사용하며, 새로운 버전 생성 단계는 건너뜁니다.

### 3. 마이그레이션 및 컷오버 절차: 인간 승인 (Human-in-the-loop)
*   **이유**: "DDL 실행·API 컷오버는 인간 승인 후에만"이라는 제약 조건과, 이번 변경이 "Read Model DDL 불필요"로 결정되었기 때문입니다.
*   **조치**:
    1.  **코드 변경**: `src/insert/insert.service.ts` 에 `catch` 블록을 추가하여 Zod 검증 실패 시 에러를 로깅하고 (`insert.file.failed` 로그 생성), 에러를 상향 (upstream) 으로 리소스 (예: CI/CD 알림, Slack, Jira) 로 전달하는 로직만 추가합니다.
    2.  **검증 (SQL)**: 변경 사항 적용 전, 격리 SQL 을 실행하여 Zod 거절된 파일들이 이벤트 스토어에 유입되지 않았음을 확인합니다.
        ```sql
        SELECT count(*) AS rejected_event_count FROM event_store WHERE (stream_id, attempt_num) IN (('grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02002', 1), ('grip-attempt:반려동물용품_CR01_강아지공룡알장난감_02003', 1));
        ```
        *   기대값: `0` (유입된 건수가 0 개여야 함).
    3.  **인간 승인**: 위 SQL 쿼리 결과가 `0` 이 확인되면, 변경 사항 (코드 로직 추가) 을 승인합니다.
    4.  **배포**: 승인된 코드를 배포합니다.
    5.  **컷오버**: **API 컷오버는 수행하지 않습니다**. 기존 v1 클라이언트와 새 로직이 동일한 스키마를 사용하므로, 즉시 배포 후에도 클라이언트 호환성이 깨지지 않습니다.

### 요약
*   **버전 경로**: `v1` 유지 (새 버전 생성 X)
*   **신구 병행**: 불필요 (스키마 변경 없음)
*   **마이그레이션**: 없음 (스키마 변경 없음)
*   **컷오버**: 불필요 (API 스키마 변경 없음)
*   **필수 조치**: 코드 로직 보강 (에러 처리 및 알림) + 인간 승인 (SQL 검증 통과 후)
