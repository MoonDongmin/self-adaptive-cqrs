제공된 로그와 스키마 정보를 바탕으로, 적재 검증 실패 (Zod 거부) 로 인해 `read_grip_result` 테이블에 저장되지 않은 데이터를 분석하고, 이를 집계하는 SQL 을 작성합니다.

### 1. 분석 및 판단 근거

1.  **실패 데이터 추출**:
    *   로그의 `insert.file.failed` 행에서 실패한 파일명을 추출합니다.
    *   파일명: `반려동물용품_CR01_강아지공룡알장난감_02002_01_20230923.json` (reason: `invalid_type`)
    *   파일명: `반려동물용품_CR01_강아지공룡알장난감_00003_01_20230923.json` (reason: `too_big`)

2.  **필드 추출 규칙**:
    *   **scene_key**: 파일명에서 `_01_` 또는 `_02_` 등의 시도 번호와 날짜 부분을 제거하여 추출합니다.
        *   예: `반려동물용품_CR01_강아지공룡알장난감_02002_01_20230923.json` -> `반려동물용품_CR01_강아지공룡알장난감_02002`
    *   **attempt_num**: 파일명에서 `_` 기호 뒤에 오는 숫자 (시도 번호) 를 추출합니다.
        *   예: `_02002_01_` -> `2` (파일명 구조: `scene_key`_`attempt_num`_`date`)
        *   예: `_00003_01_` -> `3`
    *   **failure_reason**: `detail` 컬럼의 `reason` 배열 중 첫 번째 요소 전체를 문자열로 추출합니다.
    *   **원본 값 (Original Value)**: 제공된 로그에는 Zod 에 의해 거부된 값의 원본 (예: `string` 또는 `2`) 이 명시적으로 `detail` 필드에 포함되어 있지 않습니다. `reason` 객체 내부의 `expected` 와 `code` 만 있습니다. 따라서 "원본 값"을 직접 추출할 수 없으므로, **거부 사유 (reason)** 를 통해 간접적으로 원본 값의 타입을 유추하거나, 제공된 자료에 없는 사실은 지을 수 없으므로 **거부 사유 (reason)** 만을 집계 기준으로 삼습니다.
        *   *주의*: 질문에서 "원본 값"을 요구했으나, 제공된 로그 자료 (`detail` 컬럼) 에는 `reason` 객체만 있고, 실제 거부된 값 (예: `"grip_succeed": "string"`) 은 없습니다. 따라서 "원본 값"은 **추출 불가**이며, 대신 **거부 사유 (reason)** 를 필드로 포함합니다.

3.  **집계 기준**:
    *   **건수**: 실패한 파일 개수 (각각 1 개씩).
    *   **위반 필드명**: `reason` 객체의 `path` 배열의 첫 번째 요소 (예: `["grip_succeed"]` -> `grip_succeed`).
    *   **거부 사유**: `reason` 객체의 `code` (예: `invalid_type`, `too_big`).

### 2. 백필 SQL (필요 시)

제공된 로그에는 실패한 데이터만 포함되어 있으며, 성공한 데이터 (`read_grip_result`) 와의 비교나 백필 (백업 복원) 이 필요한 상황은 아닙니다. 실패 로그만 존재하므로 별도의 백필 SQL 은 생략하고, 바로 집계 쿼리로 넘어갑니다.
