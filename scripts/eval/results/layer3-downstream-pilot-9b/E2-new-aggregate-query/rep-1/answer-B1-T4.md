제공된 자료 (로그 컨텍스트, Read Model 스키마) 에 따르면, 요청하신 "객체별 파지 성공률 (시도 수, 성공 수, 성공률)"을 조회하기 위해 필요한 데이터는 `read_grip_result` 테이블의 `object_name`, `attempt_num`, `grip_succeed` 필드입니다.

하지만 **기존 v1 API 클라이언트가 깨지지 않게 하려면**는 제공된 자료에는 정보가 없습니다. 자료에는 `insight.card.request` 와 `insight.card.miss` 로그만 있으며, 기존 API 의 응답 구조나 필드 명칭, 버전 관리 정책 (API Versioning Strategy) 에 대한 정의가 포함되어 있지 않습니다.

따라서 "버전 경로", "신구 병행 운영", "마이그레이션·컷오버 절차"와 같은 구체적인 변경 사항에 대한 답변은 **자료에 근거할 수 없습니다**.

자료에 명시된 사실만 근거하여 다음과 같이 답변드립니다.

### 1. 데이터 소스 확인
요청한 "객체별 파지 성공률"을 조회하려면 `read_grip_result` 테이블을 쿼리해야 합니다.
- **필요한 필드**: `object_name`, `attempt_num`, `grip_succeed`
- **필요한 집계**: `object_name` 기준으로 `COUNT(*)` (시도 수), `SUM(grip_succeed)` (성공 수) 를 계산하여 비율을 구해야 합니다.

### 2. API 응답 데이터 구조
기존 v1 API 클라이언트가 깨지지 않게 하려면 **기존 API 의 응답 스키마 (Response Schema) 와 필드 명칭이 무엇인지** 알아야 합니다.
- 제공된 자료에는 `insight.card.request` 로그가 있으나, 해당 요청에 대한 **기존 API 의 반환 값 (Response Body)** 구조는 정의되어 있지 않습니다.
- 따라서 "버전 경로" (예: `/v1/...` vs `/v2/...`) 나 "신구 병행 운영" (예: 두 엔드포인트 동시 노출) 을 제안할 근거가 없습니다.

### 3. 결론
제공된 `<logging_context>` 와 `<insight_read_db>` 자료만으로는 **기존 v1 API 클라이언트 호환성을 보장하는 변경 절차 (버전 경로, 병행 운영, 마이그레이션) 를 구체적으로 설계할 수 없습니다.**

이 작업을 수행하시려면 **기존 v1 API 의 응답 스키마 정의** 또는 **기존 API 엔드포인트 명칭**이 추가로 필요합니다.
