## 1. 권고 (Recommendation)

### Status

### Context (근거)
- (level 40, `insert.file.failed`) toy-data 파일 적재 실패 ← 트립 앵커 → grip_succeed 필드의 타입 또는 범위 위반으로 검증 파이프라인이 중단되며, 단일 이벤트 오류가 배치 전체의 적재 실패로 이어짐을 드러냄. 현재 Read Model 투영 구조가 이상 페이로드에 대한 격리 또는 폴백 메커니즘을 제공하지 않음. [corr:2fe263d7-04f1-4937-961a-ff1eebd64d36]
- (level 40, `insert.file.failed`) toy-data 파일 적재 실패 → 배치 완료 전 검증 예외가 트립 앵커로 작용하여 적재 프로세스가 중단됨을 확인. [corr:2fe263d7-04f1-4937-961a-ff1eebd64d36]
- src/insert/dto/toy-data.dto.ts의 검증 스키마는 grip_succeed: z.number().int().min(0).max(1)으로 엄격히 정의되어, 문자열 입력이나 1 초과 값이 들어오면 즉시 예외를 발생시킴.
- src/projection/projector/grip-result.projector.ts의 GripResultProjector.map() 메서드는 검증 스키마 파싱 호출 시 예외를 던지며, 이는 read_grip_result의 gripSucceed: smallint 컬럼에 데이터가 적재되지 못하게 함.
- read_grip_result 스키마에는 검증 실패 이력이나 폴백 상태를 기록할 컬럼이 존재하지 않아, 배치 처리 중 단일 이벤트의 검증 오류가 insert.batch.done 전에 전체 프로세스를 실패 상태로 만듦.

### Decision Drivers
- 배치 연속성 (단일 이벤트 오류로 전체 적재 중단 방지)
- 데이터 정합성 (원본 값 보존 vs 폴백 적용의 트레이드오프)
- 운영 복잡도 (신규 모델 도입에 따른 유지보수 부담)
- 조회 호환성 (기존 클라이언트 레이어 변경 최소화)

### Considered Options

### Decision Outcome
검증 상태 필드 추가 (기존 Read Model 보강)

### Consequences
- (+) 단일 이벤트 검증 오류로 인한 배치 전체 중단 현상 제거
- (+) 기존 클라이언트 및 조회 API 변경 없이 폴백 값(0)과 상태 플래그(WARN)로 이상 데이터 식별 가능
- (+) 스키마 확장만 필요하여 마이그레이션 비용 최소화
- (−) 원본 입력값(string 또는 >1)이 손실되어 추후 원인 분석 시 추가 로그 추적 필요
- (−) 조회 시 gripSucceed가 0으로 표시된 행이 실제 실패인지 폴백 적용인지 구분해야 하는 운영 부담 발생
- (−) validationStatus 컬럼에 대한 인덱스 추가 및 백필 작업 필요

### Non-Goals
- 검증 스키마 자체의 도메인 규칙 변경 (원칙 유지)
- 기존 read_multimodal Read Model의 미디어 URI 매핑 로직 수정
- 배치 처리 프레임워크 또는 커서 관리 구조 변경
