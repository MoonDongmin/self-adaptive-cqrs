- read_grip_result 테이블은 object_name, grip_succeed 컬럼을 보유하며, (objectName, occurredAt) 및 (gripSucceed, occurredAt) 인덱스가 이미 정의되어 있어 객체별 집계 쿼리에 물리적으로 유리한 상태임.
- GripResultProjector의 map() 메서드(파일: src/projection/projector/grip-result.projector.ts)는 이벤트 1건을 행 1개로 매핑할 뿐, object_name 기준 GROUP BY 집계를 수행하지 않음.
- 시스템에 read_grip_success_rate_by_object 관련 Drizzle 테이블 정의나 Projector 구현이 존재하지 않으며, ProjectionService.catchUpAll()에도 해당 투영 루틴이 등록되어 있지 않음.
- Insight 카드 조회 아키텍처가 사전 계산된 Read Model 매칭을 전제로 하므로, 집계 전용 Read Model 추가가 기존 CQRS/Projector 패턴과 가장 일관되게 부합함.

### Considered Options
#### 신규 집계 Read Model (read_grip_success_rate_by_object) 도입
- 접근: src/shared/database/schema/service/read-grip-success-rate.ts에 Drizzle 테이블 정의, src/projection/projector/grip-success-rate.projector.ts에 집계 프로젝터 구현. 기존 read_grip_result의 데이터를 매 batch마다 object_name 기준 GROUP BY 집계하여 upsert. ProjectionService에 catchUp 루틴 추가.
- 제안 필드: objectName, totalAttempts, successCount, successRate
- 트레이드오프: Insight 카드 조회 시 O(1) 응답 보장 및 읽기 성능 최적화. 대신 projection latency 증가, 재투영 시 집계 일관성 검증 로직 추가 필요.

#### PostgreSQL Materialized View 활용
- 접근: 기존 read_grip_result 테이블에 CREATE MATERIALIZED VIEW 생성. Insight 서비스 쿼리 대상만 뷰로 변경. 투영 코드 변경 불필요.
- 제안 필드: object_name, total_attempts, success_count, success_rate
- 트레이드오프: 투영 파이프라인 변경 비용 제로, 유지보수 용이. 다만 뷰 리프레시 주기(REFRESH MATERIALIZED VIEW)에 따른 최신성 지연 발생 가능.
```typescript
CREATE MATERIALIZED VIEW mv_read_grip_success_rate_by_object AS SELECT object_name, COUNT(*) as total_attempts, SUM(grip_succeed) as success_count, CASE WHEN COUNT(*) > 0 THEN (SUM(grip_succeed)::decimal / COUNT(*)) ELSE 0 END as success_rate FROM read_grip_result GROUP BY object_name;
```
