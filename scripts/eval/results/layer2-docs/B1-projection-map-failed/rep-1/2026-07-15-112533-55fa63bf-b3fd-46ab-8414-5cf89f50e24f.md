## 1. 권고 (Recommendation)

### Status
proposed

### Context (근거)
- (level 50, `projection.map.failed`) objects 비어 있음 → GripResultProjector가 빈 배열을 fatal error로 처리하여 배치 트랜잭션을 중단시킴. [corr:55fa63bf-b3fd-46ab-8414-5cf89f50e24f]
- (level 50, `db.error`) 투영 트랜잭션 실패 → 단일 poison event로 인해 정상 매핑된 52개 행이 함께 롤백됨. [corr:55fa63bf-b3fd-46ab-8414-5cf89f50e24f]
- (level 50, `-`) grip-result map: empty objects in event a93f3e33-d9a9-4120-a505-ed9765878d14 → read_grip_result의 object_name 필드가 objects[0].class_name을 요구하여 빈 객체 이벤트와 도메리 정합성 충돌 발생. [corr:55fa63bf-b3fd-46ab-8414-5cf89f50e24f]
- GripResultProjector.map() 코드에서 payload.objects.length === 0 조건 시 throw new Error(...)를 호출하여 트랜잭션 전체를 실패시킨다.
- read_grip_result 스키마의 object_name: varchar는 payload.objects[0].class_name에서 파생되므로, 빈 배열 이벤트에 대해 매핑 자체가 불가능한 구조적 제약이 존재한다.
- CatchUpRunner는 프로젝트터의 예외를 전체 배치 트랜잭션 롤백으로 처리하는 정책이 적용되어 있어, poison event에 대한 격리(isolation) 메커니즘이 부재하다.
- read_multimodal의 image_2d_uri, video_uri는 현재 null로 하드코딩되어 있으나, 이번 롤백 문제와 직접적인 연관은 없으나 향후 URI 매핑이 필요함을 시사한다.

### Decision Drivers
- 배치 트랜잭션 무결성 보장 (정상 이벤트 유실 방지)
- poison event 격리 용이성 (실패 행과 성공 행 분리 처리)
- Read Model 정합성 유지 및 검증 로직 보존
- 운영 오버헤스 최소화 (재투영 비용, 런타임 부하)

### Considered Options
#### GripResultProjector 내 skip 처리 및 null 허용 (In-Place Enhancement)
- 접근: GripResultProjector.map()에서 빈 배열 시 예외 대신 null 반환 또는 skip 플래그 전달. read_grip_result의 object_name을 nullable로 변경하거나, 매핑 시 기본값/NULL 처리. 배치 트랜잭션 내 예외 발생을 방지하여 정상 이벤트 보존.
- 제안 필드: read_grip_result.object_name (nullable), GripResultProjector.map() 반환 타입/로직
- 트레이드오프: 재투영 비용 없음, 리스크 낮음. 다만 object_name이 NULL인 행이 생성되어 조회 시 null 처리 로직 필요.
```typescript
if (payload.objects.length === 0) { this.logger.warn({ action: LogAction.MAP_FAILED, [LogContext.EVENT_ID]: event.eventId }, "objects 비어 있음 - skip"); return null; }
```

#### CatchUpRunner 이벤트 단위 격리 실패 처리 (Runner Level Isolation)
- 접근: GripResultProjector의 throw 로직은 유지하되, CatchUpRunner가 배치 내 개별 이벤트 매핑 실패 시 해당 이벤트만 스킵하고 나머지 트랜잭션은 커밋하도록 수정.
- 제안 필드: CatchUpRunner 배치 처리 루프, ProjectionService
- 트레이드오프: 프로젝터 코드 변경 최소화. 다만 런타임 오버헤스 증가, 실패 이벤트 추적용 별도 테이블/로그 관리 필요.
```typescript
try { row = projector.map(event); } catch (error) { logger.warn({ action: LogAction.MAP_FAILED, [LogContext.EVENT_ID]: event.eventId }, "이벤트 매핑 실패 - skip"); continue; }
```

### Decision Outcome
CatchUpRunner 이벤트 단위 격리 실패 처리 (Runner Level Isolation)

### Consequences
- (+) 정상 이벤트 유실 방지 및 배치 트랜잭션 커밋 안정화
- (+) 프로젝터 검증 로직 변경 불필요 (도메인 규칙 일관성 유지)
- (+) 실패 이벤트 추적 용이 (별도 skip 로그/저장 구조로 poison event 관리 가능)
- (−) 런타임 오버헤스 증가 (배치 내 try-catch 격리 처리로 인한 CPU/메모리 부하)
- (−) 실패 이벤트 관리용 별도 로깅/저장 구조 필요 (운영 모니터링 복잡도 상승)

### Non-Goals
- read_multimodal URI 매핑 구현 (본안과 무관한 별도 작업)
- 기존 ES 이벤트 스키마 변경 (GripAttemptRecorded payload 구조 수정)
- 배치 크기 조정 또는 커서 정책 변경
