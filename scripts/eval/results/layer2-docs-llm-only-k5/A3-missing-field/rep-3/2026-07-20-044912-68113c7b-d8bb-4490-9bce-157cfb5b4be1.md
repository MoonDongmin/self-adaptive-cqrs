- 트레이드오프: Read Model 스키마 변경으로 API 버전 관리가 필요하나, 결함 데이터를 명시적으로 격리하여 정상 데이터 조회 시 오염을 방지. 정합성 검사 연동으로 시스템 신뢰도 향상.
```typescript
export const readGripResult = pgTable("read_grip_result", { ..., validationStatus: varchar("validation_status").default("valid"), ... }); ... try { payload = toyDataSchema.parse(event.payload); } catch (error) { this.logger.error({ action: LogAction.MAP_FAILED, error }, "이벤트 매핑 검증 실패"); return { ..., validationStatus: "failed", grip2dPose: null, robotTf: null, ... }; }
```

### Decision Outcome
결함 격리용 Read Model 컬럼 추가 및 정합성 검사 연동

### Consequences
- (+) 결함 이벤트가 Read Model에 격리되어 정상 조회 시 오염 데이터 유입 방지
- (+) 정합성 검사 인터페이스와 연동하여 시스템 전반의 데이터 신뢰도 향상
- (+) 투영 파이프라인 중단 없이 batch 처리가 완료되어 가용성 유지
- (−) Read Model 스키마 확장으로 기존 클라이언트에서 신규 컬럼 처리 로직 필요
- (−) 데이터 마이그레이션 및 커서 초기화 작업으로 인한 일시적 운영 부하 발생
- (−) 격리된 결함 데이터의 사후 분석을 위한 별도 모니터링 파이프라인 구축 필요

### Non-Goals
- upstream 데이터 생성 로직 수정 또는 검증 스키마 완전 재설계
- API 엔드포인트 경로 변경 또는 버전 분리
- read_multimodal Read Model의 미디어 URI 매핑 로직 수정

## 3. API Versioning

### 버전 영향

Read Model에 validationStatus 컬럼 추가 시 하위 호환성을 유지하므로 API 버전 변경은 불필요함. 기존 엔드포인트는 그대로 동작하며, 클라이언트 단에서 신규 컬럼을 무시하거나 기본값으로 처리하면 변경 없음. 스키마 확장이므로 응답 구조에 null 필드가 추가되나 기존 파싱 로직을 깨뜨리지 않음.
