# 제 III 장 Self-Adaptive CQRS 설계 및 구현

## 3.1 제안 시스템 개요 및 설계 원칙

본 장에서는 제 II 장에서 확인한 연구 공백, 즉 Read Model의 설계 의사결정이 개발자의 수작업에 의존하는 문제를 완화하기 위해 제안하는 Self-Adaptive CQRS 아키텍처의 설계와 구현을 기술한다. 자가 적응 시스템 분야에서는 적응의 대상이 되는 기존 시스템을 관리 대상 시스템(managed system), 이를 관측하고 조정하는 별도의 계층을 관리 시스템(managing system)이라 부른다[12]. 제안 시스템은 기존의 이벤트 소싱·CQRS 구조를 관리 대상 시스템으로 두고, 그 위에 LLM 기반의 분석 영역을 관리 시스템으로 결합한다. 관리 대상 시스템의 코드와 데이터 모델은 변경하지 않으며, 관리 시스템은 관리 대상 시스템이 운영 중에 남기는 로그와 데이터를 관측하여 Read Model의 재생성이 필요한 상황을 감지하고, 그 조치 방안을 단일 문서(이하 Docs)로 산출한다. 그림은 제안 시스템의 구성도로, 하나의 NestJS 프로세스 안에 배치된 기능 모듈과 외부 인프라(데이터베이스, 메시지 브로커, 로컬 LLM 서버, 파일 시스템)의 관계를 나타낸 것이다.

> [그림 3-1] `fig3-01-system-architecture.svg` — Self-Adaptive CQRS 시스템 구성도

제안 시스템은 네 개의 영역으로 구성된다. 첫 번째는 기존의 이벤트 소싱·CQRS 영역이다. 쓰기 측의 적재 서비스가 Physical AI 파지 시도 데이터를 검증하여 이벤트 스토어에 불변 이벤트로 기록하고, 읽기 측의 프로젝션이 이벤트를 조회 목적별 Read Model에 반영한다. 두 번째는 관측 계층이다. 모든 구성 요소는 정해진 형식의 로그를 남기며, 이 로그는 메시지 브로커와 로그 데이터베이스로 동시에 전달된다. 프로젝션이 Read Model에 반영한 센서 값은 오류가 아닌 데이터이므로 로그와 별도의 채널로 전달된다. 세 번째는 본 연구가 추가한 LLM 영역이다. 관측 계층으로 유입되는 로그와 데이터 가운데 정상 동작에서 벗어난 것을 이하 이상 신호라 한다. 이상 신호는 먼저 미리 정한 규칙과 소형 언어 모델(SLM)이 1차로 선별하고, 선별된 신호에 대해서만 LLM 기반의 진단 에이전트가 근본원인 분석, 조치 결정, 산출물 생성의 순서로 Docs를 생성한다. 1차 선별에서 Docs 생성까지의 이 처리 흐름을 이하 진단 파이프라인이라 한다. 네 번째는 LLM 컨텍스트의 원천이다. 개발자의 구조화된 로그를 축적한 로그 데이터베이스(이하 Log DB)와, 시스템이 보유한 이벤트와 Read Model의 스키마 정보를 관리하는 Insight Read DB가 진단 파이프라인에 판단의 근거를 제공한다. 생성된 Docs는 사람의 승인을 거쳐 관리 대상 시스템에 적용되고, 이때 신규 Read Model의 스키마 정보가 Insight Read DB에 함께 등록되어 다음 분석의 컨텍스트로 순환한다. 이 순환이 제안 시스템에서 자가 적응을 이루는 피드백 루프이다.

제안 시스템의 설계는 다섯 가지 원칙을 따른다. 첫째는 판단과 실행의 분리이다. 본 논문에서는 LLM이 아니라 미리 작성된 프로그램 규칙에 따라 같은 입력에 항상 같은 결과를 내는 처리를 규칙 기반 처리라 부른다. LLM은 어떤 이상이 왜 발생하였는지, 어떤 조치가 필요한지, 신규 Read Model의 컬럼을 어떻게 구성할지와 같이 도메인 이해와 생성 능력이 필요한 판단만 담당하고, 이상 신호의 선별, 산출물의 검증, SQL과 코드를 정해진 형식으로 완성하는 일, 문서를 정해진 순서로 구성하는 일은 규칙 기반 처리가 담당한다. 이는 LLM 산출물의 불확실성[24]과 소형 로컬 모델을 사용해야 하는 배포 환경의 제약[17]을 함께 고려한 결정이다. 둘째는 이상의 명명은 자유롭게, 조치는 정해진 범위에서 다루는 것이다. 근본원인 분석이 판정하는 이상 유형은 미리 정한 목록에 제한하지 않고 진단 에이전트가 자유롭게 명명하도록 하여 사전에 예상하지 못한 이상도 다룰 수 있게 한다. 반면 이후의 조치는 API 버전 전환, 권고 문서, 신규 Read Model, 데이터 품질 권고의 네 가지 가운데에서만 선택된다. 전통적인 자가 적응 기법은 적응 행동을 설계 시점에 모두 정해 두므로 예상하지 못한 상황을 다루지 못하고[10, 30], LLM 기반 접근은 적응 행동을 실행 시점에 생성하므로 예측 가능성이 낮아지는데[24], 제안 시스템은 감지의 유연성과 조치의 예측 가능성을 이와 같이 분리하여 두 접근의 장점을 취한다. 셋째는 단일 산출물의 완전성이다. Docs는 권고 문서, Read Model 생성 SQL, API 버저닝 전략의 세 요소를 항상 함께 담으며, 신규 Read Model이 선택되면 권고와 버전 전환이 반드시 동반되도록 규칙으로 강제한다. 근거가 부족하여 채울 수 없는 요소는 생략하지 않고 근거 부족임을 명시하는 표시로 채워 문서의 형태를 유지한다. 넷째는 2단계 선별에 의한 비용 통제이다. 모든 로그와 데이터에 대해 실행되는 1차 선별은 규칙 기반 처리와 SLM으로 구성하고, 추론과 도구 호출을 반복하는 고비용의 LLM 분석은 선별을 통과한 소수의 신호에 대해서만 실행한다. 다섯째는 사람의 승인(human-in-the-loop)과 루프의 안정성이다. DDL 실행과 API 전환은 사람의 승인 이후에만 이루어지며, 진단 파이프라인 자신이 남기는 로그는 다시 이상 신호로 유입되지 않도록 정보(info) 수준으로만 기록한다. 표는 각 원칙이 구현된 위치를 정리한 것이다.

| 설계 원칙 | 내용 | 구현 위치 |
| --- | --- | --- |
| 판단과 실행의 분리 | LLM은 진단·조치 선택·설계만 담당, 선별·검증·SQL과 코드 완성·문서 구성은 규칙 기반 처리 | 사전 판정, 검증 단계, 문서 구성 (3.4절, 3.5절) |
| 자유로운 명명·정해진 조치 | 이상 유형은 자유 명명, 조치는 4종 가운데 선택 | 근본원인·조치 결정의 출력 형식 (3.5절) |
| 단일 산출물의 완전성 | 3요소 항상 동반, 신규 Read Model이면 권고와 버전 전환 동반, 근거 부족 표시 | 조치 결정 규칙, 문서 구성의 완전성 검사 (3.4절, 3.5절) |
| 2단계 선별 비용 통제 | 규칙 + SLM의 1차 선별, 이상 판정 시에만 LLM 분석 | 로그 경로·센서 경로의 1차 선별 (3.5절) |
| 사람의 승인·루프 안정성 | 승인 후 적용, 파이프라인 로그의 수준 제한, 로컬 LLM 구동 | Docs 실행 안내문, 로깅 규약 (3.4.4항, 3.6절) |

## 3.2 이벤트 스토어와 목적별 Read Model

관리 대상 시스템은 Physical AI 도메인의 로봇 파지 시도(grip attempt) 데이터를 이벤트 소싱·CQRS 구조로 관리한다. 데이터는 로봇이 물건을 파지하는 한 번의 시도를 하나의 JSON 파일로 기록한 것으로, 2D·3D 이미지와 비디오의 파일명, 카메라 내부 파라미터, 2D·3D 파지 포즈, 로봇의 회전 행렬과 이동 벡터(robot TF), 대상 객체와 사람의 파지 주석, 파지 성공 여부의 11개 최상위 키로 구성된다. 파일명은 카테고리, 카메라 코드, 객체명, 장면 번호, 시도 번호, 촬영 일자를 담는 규약을 따르며, 적재 서비스는 여기서 장면 식별 키(scene key)와 시도 번호를 추출한다. 하나의 장면은 하나의 이벤트 스트림(`grip-attempt:<scene key>`)에 대응하고, 각 시도는 스트림 안에서 시도 번호로 구분되는 하나의 `GripAttemptRecorded` 이벤트가 된다.

적재 서비스는 파일마다 파일명 파싱, JSON 파싱, 스키마 변화 감지, 스키마 검증, 이벤트 추가의 순서로 동작한다. 스키마 검증은 zod 스키마로 수행되며 스키마에 정의되지 않은 키는 검증 과정에서 제거되므로, 새로운 센서가 추가되어 스키마가 알지 못하는 키가 유입되면 그 값은 이벤트 스토어에 기록되지 않고 유실된다. 이를 관측하기 위해 검증 이전의 원본 JSON에서 알려진 키 목록에 없는 최상위 키를 찾아내고, 배치가 끝날 때 새로운 키의 목록과 값의 표본을 담은 경고 로그(`payload.schema.drift`)를 남긴다. 이 로그가 제 I 장에서 문제로 정의한 "스키마에 정의되지 않은 필드의 유입"을 시스템이 스스로 관측하는 첫 번째 신호이다. 이벤트 추가는 스트림과 시도 번호의 고유 제약에 대해 충돌 시 무시하는 방식으로 수행되어 같은 파일을 다시 적재하더라도 결과가 달라지지 않는다. 표는 이벤트 스토어의 스키마를 정리한 것이다.

| 컬럼 | 자료형 | 의미 |
| --- | --- | --- |
| global_seq | bigserial (PK) | 전역 순번, 프로젝션 커서의 기준 |
| event_id | uuid (unique) | 이벤트 식별자 |
| stream_id, attempt_num | varchar, integer | 스트림 식별자(`grip-attempt:<scene key>`)와 시도 번호 (함께 고유) |
| event_type | varchar(64) | 이벤트 유형 (`GripAttemptRecorded`) |
| occurred_at, recorded_at | timestamptz | 사건 발생 시각(촬영 일자)과 기록 시각 |
| payload | jsonb | 원본 JSON 전체 |

읽기 측에는 조회 목적별로 두 개의 Read Model이 놓인다. `read_grip_result`는 장면별 파지 결과의 조회를 목적으로 객체명, 파지 성공 여부, 그리퍼 유형, 포즈, 로봇 TF, 파지 주석을 담고, `read_multimodal`은 장면별 미디어 링크의 조회를 목적으로 2D 이미지와 비디오의 파일명 및 저장 위치를 담는다. 두 Read Model은 모두 `(scene_key, attempt_num)`을 기본 키로 가지며, 어느 이벤트에서 만들어진 행인지 추적할 수 있도록 원천 이벤트의 스트림 식별자와 전역 순번을 보존한다. 표는 두 Read Model의 스키마를 정리한 것이다.

| Read Model | 목적 | 컬럼 | 인덱스 |
| --- | --- | --- | --- |
| read_grip_result | 장면별 파지 결과 조회 (성공 여부·포즈·그리퍼) | scene_key, attempt_num, object_name, grip_succeed, gripper_type, occurred_at, grip_2d_pose, grip_3d_pose, robot_tf, human_annotation_grasp, stream_id, global_seq (12) | (object_name, occurred_at), (grip_succeed, occurred_at) |
| read_multimodal | 장면별 2D 이미지·비디오 링크 조회 | scene_key, attempt_num, occurred_at, image_2d_file_name, image_2d_uri, video_file_name, video_uri, stream_id, global_seq (9) | 없음 |

그림은 관리 대상 시스템의 이벤트 스토어, Read Model, 프로젝션 커서와 관리 시스템이 사용하는 Log DB, Insight Read DB의 테이블을 함께 나타낸 데이터 모델이다. Read Model의 행은 원천 이벤트의 전역 순번으로 논리적으로 추적되며, 물리적 외래 키 제약은 Insight Read DB의 두 테이블 사이에만 둔다.

프로젝션은 이벤트를 Read Model의 행으로 바꾸는 프로젝터(projector)와, 아직 반영되지 않은 이벤트를 순서대로 읽어 프로젝터에 넘기는 캐치업 실행기(catch-up runner)로 구성된다. 프로젝터는 이벤트를 행으로 변환하는 `map`과 행을 저장하는 `upsert`를 반드시 구현하고, 반영된 행이 의미상 올바른지 검사하는 `checkIntegrity`와 행에서 센서 값을 추출하는 `toSensorValueMessages`를 선택적으로 구현하는 인터페이스이다. 캐치업 실행기는 프로젝터별로 마지막에 반영한 전역 순번을 커서로 기록해 두고, 커서 이후의 이벤트를 500건 단위로 읽어 한 배치의 변환·저장과 커서의 전진을 하나의 트랜잭션으로 처리한다. 변환 과정에서 스키마 검증에 실패하는 이벤트, 즉 변환할 수 없는 이벤트가 발견되면 오류 로그(`projection.map.failed`)를 남기고 예외를 발생시켜 해당 배치 전체를 되돌린다. 이는 결함 이벤트를 건너뛰어 조용히 누락시키는 대신 커서를 멈추어 문제를 드러내는 정책으로, 이후의 대응을 사람과 진단 파이프라인에 맡기기 위한 설계이다. 배치가 저장된 뒤에는 트랜잭션 밖에서 두 가지 후처리가 수행된다. 하나는 의미 검사로, 예를 들어 `read_multimodal`은 미디어 파일명이 규약대로 해석되는지와 파일명에 담긴 장면·시도 번호가 행의 키와 일치하는지를 검사하여 위반 시 오류 로그(`projection.integrity.violation`)를 남긴다. 다른 하나는 센서 값의 발행으로, `read_grip_result`에 반영된 행의 포즈·TF·성공 여부를 메시지로 변환하여 별도의 채널에 발행한다. 발행이 실패하더라도 이미 저장된 Read Model은 되돌리지 않으며, 이 값은 3.5절의 센서 경로에서 물리적 타당성을 검사하는 입력이 된다. 그림은 적재와 프로젝션의 처리 순서, 그리고 각 단계에서 이상 신호가 로그와 채널로 나가는 지점을 나타낸 시퀀스 다이어그램이다.

> [그림 3-3] `fig3-03-seq-ingest-projection.svg` — 적재·프로젝션 시퀀스 다이어그램과 이상 신호 발생 지점

이 구조에서 주목할 점은 관리 대상 시스템의 각 단계가 자신의 실패와 이상을 정해진 형식의 로그와 메시지로 밖에 알리도록 설계되었다는 것이다. 관리 대상 시스템은 관리 시스템을 위한 별도의 인터페이스를 갖지 않으며, 로그와 데이터라는 통상적인 관측 수단만으로 관리 시스템과 연결된다. 이 신호들이 다음 절에서 설명하는 LLM 컨텍스트의 원천이 된다.

## 3.3 LLM 컨텍스트 모델

LLM은 대상 시스템의 상태, 스키마 및 이력을 학습 과정에서 알 수 없으므로, 판단에 필요한 정보를 실행 시점에 입력으로 제공받아야 한다(2.3.1항). 이렇게 LLM에 제공되는 입력 정보 전체를 컨텍스트라 하며, 제안 시스템의 컨텍스트는 두 원천으로 구성된다. 개발자 Logging 기반 컨텍스트는 "시스템에서 무슨 일이 일어났는가"를, Insight Read DB 기반 컨텍스트는 "시스템이 무엇을 보유하고 있는가"를 담당한다. 전자가 이상의 존재와 앞뒤 상황을 알려준다면, 후자는 그 이상에 대응하여 어떤 Read Model을 어떤 컬럼으로 설계할지 판단할 때 대조할 스키마 지식을 제공한다.

### 3.3.1 개발자 Logging 기반 컨텍스트

개발자 Logging을 컨텍스트로 활용하려면 로그가 LLM이 해석할 수 있을 만큼 구조화되어야 한다. 이를 위해 제안 시스템은 네 가지 로깅 규약을 정의한다. 첫째, 모든 로그는 JSON 레코드로 기록되며 `insert.file.failed`, `projection.map.failed`, `insight.card.miss`와 같이 영역과 사건을 이어 붙인 행위명(action)을 갖는다. 행위명은 코드 전체에서 하나의 목록으로 관리되어 같은 사건이 항상 같은 이름으로 기록된다. 둘째, 하나의 요청에서 발생한 모든 로그는 요청마다 부여되는 상관관계 식별자(correlation ID)를 공유한다. 식별자는 요청 헤더에서 받거나 자동으로 생성되며 미들웨어를 통해 서비스 계층의 로거에 전달되므로, 요청의 수신부터 완료까지의 궤적을 하나의 식별자로 추적할 수 있다. 셋째, 이상 신호는 모두 경고(warn, 수준 40) 이상의 수준으로 기록한다. 이 규약 하나로 로그로 전달되는 모든 이상 신호가 한 곳으로 모이므로, 새로운 탐지 기능을 추가할 때 진단 파이프라인을 수정할 필요 없이 경고 로그 한 줄을 남기는 것으로 충분하다. 넷째, 진단 파이프라인 자신이 남기는 로그는 정보(info) 수준으로만 기록한다. 파이프라인의 로그도 같은 경로로 다시 유입되므로, 분석 결과를 경고 수준으로 기록하면 그 로그가 새로운 이상 신호로 인식되어 분석이 끝없이 반복되기 때문이다. 표는 관리 대상 시스템이 내보내는 이상 신호를 정리한 것이다.

| 신호 | 행위명 | 수준 | 발생 지점 | 의미 |
| --- | --- | --- | --- | --- |
| S1 스키마 변화 | payload.schema.drift | warn | 적재 서비스 | 스키마에 없는 새 키 유입, 적재 시 유실 (신규 Read Model 후보) |
| S2 적재 거절 | insert.file.failed | warn | 적재 서비스 | 스키마 검증 실패, 이벤트 미기록 (원천 데이터 결함) |
| S3 변환 실패 | projection.map.failed | error | 프로젝터 | 변환할 수 없는 이벤트, 배치 되돌림·커서 정지 |
| S4 의미 검사 위반 | projection.integrity.violation | error | 캐치업 실행기 | 구조는 유효하나 의미 규칙 위반 |
| S5 스키마 정보 누락 | insight.card.drift | warn | 누락 감시기 | 스키마 정보가 등록되지 않은 Read Model 테이블 존재 |
| S6 조회 실패 | insight.card.miss | warn | Insight 서비스 | 존재하지 않는 스키마 정보 조회 (사용자 조회 요구의 표출) |
| S7 HTTP 이상·반복 요청 | (요청 완료 로그) | warn/error | HTTP 로거 | 4xx/5xx 응답, 동일 요청 반복, 순서 이상 |
| S8 센서 값 이탈 | (sensor-values 채널) | — | 캐치업 실행기 | 값 자체는 오류가 아니므로 로그가 아닌 별도 채널로 전달 |

이 가운데 S6은 본 연구의 문제 정의와 직접 연결되는 신호이다. 사용자가 원하는 데이터를 기존 Read Model이 제공하지 못하는 상황은 시스템 내부의 오류로 나타나지 않는다. 제안 시스템은 Insight Read DB의 스키마 정보를 조회하는 경로를 조회 요구의 진입점으로 두고, 존재하지 않는 항목에 대한 조회를 경고 로그로 기록한다. 조회 대상의 이름에는 "객체별 파지 성공률을 한 번에 조회하고 싶다"와 같은 자연어 질의가 그대로 담기며, 같은 질의가 반복되면 단발성 오타가 아니라 조회 요구가 실제로 존재한다는 신호로 해석된다.

로그는 두 경로로 전달된다. 하나는 로거의 TCP 전송이 수집기(fluent-bit)를 거쳐 메시지 브로커(Kafka)의 `log-events` 토픽으로 흐르는 실시간 경로로, 1차 선별의 입력이 된다. 다른 하나는 로그 파일을 주기적으로 읽어 Log DB의 `log_event` 테이블에 적재하는 경로로, 분석 시점에 이상의 앞뒤 상황을 조회하는 데 쓰인다. `log_event`는 시각을 기준으로 분할되는 시계열 테이블이며, 수준·행위명·상관관계 식별자·스트림 식별자·전역 순번·장면 키처럼 조회에 쓰이는 필드는 별도 컬럼으로, 원본 레코드 전체는 JSON 컬럼으로 보존한다. 두 경로를 분리한 이유는 메시지 브로커가 배치 단위의 실시간 선별에 적합한 반면, 특정 시각을 기준으로 앞뒤의 로그를 정확히 조회하는 작업에는 시각 인덱스를 갖춘 데이터베이스가 필요하기 때문이다.

진단 파이프라인에 입력되는 로그 컨텍스트는 이상 로그 구간이라는 단위로 만들어진다. 1차 선별이 이상으로 판정한 상관관계 식별자로 해당 요청의 로그를 모두 조회하고, 그 가운데 첫 번째 경고 이상 로그를 기준 로그로 정한다. 기준 로그의 앞뒤 20행씩을 취한 뒤, 경고 이상이거나 이상 판정된 식별자를 공유하는 로그를 신호 로그로 보고 각 신호 로그의 앞 4행과 뒤 6행만 남기는 방식으로 잡음을 제거하며, 최종적으로 80행 이내로 제한한다. 여기에 기준 로그 이전 1시간 동안의 행위명·수준별 발생 횟수를 함께 붙인다. 각 행은 시각, 수준, 행위명, 상관관계 식별자, 스트림 식별자, 시도 번호, 전역 순번, 메시지, 그리고 원본 레코드의 이유·파일명·이벤트 식별자·새 키를 모은 상세 열로 구성되고 기준 로그에는 표시가 붙는다. 상세 열을 별도로 두는 이유는 LLM이 결함 데이터를 격리하는 SQL의 조건절을 작성할 때 실제로 존재하는 이벤트 식별자와 장면 키를 인용하도록 하기 위함이다. 그림은 로그의 수집에서 1차 선별, 로그 구간 조립, 진단 파이프라인 호출과 Docs 저장에 이르는 로그 경로의 처리 순서를 나타낸 시퀀스 다이어그램이다.

> [그림 3-4] `fig3-04-seq-log-lane.svg` — 로그 경로 시퀀스 다이어그램 (수집 → 1차 선별 → 로그 구간 조립 → 분석 → Docs)

### 3.3.2 Insight Read DB 기반 컨텍스트

Insight Read DB는 시스템이 보유한 이벤트와 Read Model의 스키마와 의미를 LLM이 참조할 수 있는 형태로 관리하는 메타데이터 저장소이다. LLM의 SQL 생성 품질은 스키마 정보를 어떻게 제공하는지에 크게 좌우되며[14-17], 본 논문이 다루는 DDL 생성은 개별 테이블의 컬럼 정보를 넘어 이벤트의 의미와 기존 Read Model의 목록·용도까지 필요로 한다. Insight Read DB는 이 요구를 항목 단위의 스키마 정보로 충족한다. 하나의 스키마 정보는 하나의 대상(이벤트 또는 Read Model)을 설명하며, 대상의 이름·종류·용도·키 컬럼을 담는 `insight_entity` 한 행과 각 필드의 이름·자료형·의미·예시 값·표시 순서를 담는 `insight_field` 여러 행으로 구성된다. 대상의 종류는 현재 조회 가능한 완성품인 Read Model과 아직 Read Model로 구체화되지 않은 재료인 이벤트의 두 가지이다. 초기에는 두 Read Model(12필드, 9필드)과 원천 이벤트 `GripAttemptRecorded`(23필드)의 스키마 정보가 등록되며, 이벤트의 스키마 정보는 payload의 중첩 구조를 `camera_info.camera_name`, `objects[].class_name`과 같은 경로 표기로 펼쳐서 기술하므로 LLM은 어떤 원천 필드가 아직 어떤 Read Model에도 반영되지 않았는지를 두 스키마 정보의 대조만으로 파악할 수 있다.

스키마 정보는 LLM에 입력될 때 Text-to-SQL 연구에서 제안된 M-Schema 표현[16]으로 변환된다. M-Schema는 테이블을 `(필드명:자료형, 의미, 기본 키 여부, 예시 값)`의 튜플 목록으로 기술하는 표현 방식으로, 컬럼의 의미와 예시를 함께 담아 LLM이 질의와 관련된 컬럼을 찾는 정확도를 높이면서도 DDL 원문보다 토큰 소비가 적다. 변환기는 대상의 종류에 따라 `## ReadModel:` 또는 `## Event:` 제목을 붙이고 용도와 키 컬럼을 기술한 뒤 튜플 목록을 코드 블록으로 출력하며, 기본 키 여부는 키 컬럼 정의로부터 규칙에 따라 판정한다. 그림은 Insight Read DB의 스키마 정보 구조와 M-Schema 변환의 예를 나타낸 그림이다.

> [그림 3-5] `fig3-05-insight-read-db.svg` — Insight Read DB의 스키마 정보 구조와 M-Schema 변환

Insight Read DB는 컨텍스트의 원천인 동시에 두 이상 신호의 발생 지점이다. 존재하지 않는 항목에 대한 조회는 조회 실패 신호(S6)를 발생시키고, 누락 감시기는 60초마다 데이터베이스의 실제 테이블 목록에서 인프라 테이블과 스키마 정보가 등록된 테이블을 제외한 나머지를 계산하여, 스키마 정보 없이 존재하는 Read Model 테이블을 발견하면 테이블별로 1시간에 한 번만 누락 신호(S5)를 발생시킨다. 후자는 사람이 신규 Read Model을 만들고 스키마 정보의 등록을 잊었을 때 Insight Read DB와 실제 스키마의 불일치를 시스템이 스스로 드러내는 장치이다.

### 3.3.3 컨텍스트 조합 및 주입 전략

두 원천의 컨텍스트는 두 방식으로 진단 파이프라인에 전달된다. 하나는 파이프라인이 분석을 시작할 때 미리 넣어 주는 사전 주입(push)이고, 다른 하나는 진단 에이전트가 분석 도중 필요할 때 도구를 호출하여 가져오는 도구 조회(pull)이다. 사전 주입에서는 이상 로그 구간(로그 경로) 또는 센서 이상 판정 결과(센서 경로) 가운데 하나와 Insight Read DB의 스키마 정보 전체가 입력으로 전달된다. 스키마 정보를 관련성에 따라 골라내지 않고 전부 주입하는 것은, 신규 Read Model의 설계가 기존 Read Model 전체와의 대조를 필요로 하고 스키마 정보의 총량이 LLM 입력 한도 안에 충분히 들어오기 때문이다. 도구 조회에서는 근본원인을 분석하는 진단 에이전트가 다섯 가지 도구로 Log DB, Insight Read DB, 센서 기준값 문서, 소스 코드를 직접 조회한다. 표는 진단 도구를 정리한 것이다.

| 도구 | 역할 | 입력 | 제한 |
| --- | --- | --- | --- |
| search_logs | Log DB 조회: 상관관계 식별자로 요청 궤적 추적, 행위명·수준으로 반복 패턴 확인, 오류 스택 상단 6줄 발췌 | correlationId, action, sceneKey, minLevel, limit | 최대 40행 |
| list_insight_cards | 등록된 스키마 정보의 대상 이름 목록 | 없음 | — |
| get_insight_card | 스키마 정보 한 항목의 M-Schema 표현 | entityName | — |
| get_sensor_baseline | 센서 값의 규칙명·기대 범위·분포 통계를 담은 기준값 문서 | 없음 | — |
| read_source_code | 소스 파일을 행 번호와 함께 열람 | filePath, startLine, endLine | 저장소 안의 `src/`·`dist/`만 허용, 한 번에 최대 120행 |

모든 도구의 결과는 4,000자에서 잘리며, 잘렸을 때는 조건을 좁혀 다시 조회하라는 안내가 덧붙는다. 이는 잘못된 근거가 아니라 지나치게 많은 근거로부터 판정 품질을 보호하는 장치이다. 사전 주입은 모든 분석에 공통으로 필요한 최소 컨텍스트를 예측 가능한 비용으로 보장하고, 도구 조회는 오류 스택이 가리키는 소스 코드의 특정 행이나 특정 스키마 정보의 상세처럼 이상의 유형에 따라 달라지는 추가 근거를 필요할 때만 가져오게 하여, 두 방식은 서로 보완한다.

진단 파이프라인 안에서는 처리 단계마다 서로 다른 컨텍스트가 구성된다. 근본원인 분석 단계는 로그 구간 또는 센서 판정 결과를 근거 텍스트로 받고 도구로 근거를 보강한다. 조치 결정 단계는 근본원인 분석의 결과에 로그 구간 표와 스키마 정보를 더하여 받는데, 이는 조회 실패의 반복 횟수처럼 요약된 근본원인만으로는 알 수 없는 사실을 원문에서 확인하기 위함이다. 산출물 생성 단계는 여기에 기존 프로젝터·스키마·컨트롤러의 소스 코드 발췌를 추가로 받아 생성되는 코드가 실제 코드의 형식과 스타일을 따르도록 한다. 특히 신규 Read Model이 선택된 경우에는 먼저 확정된 설계(테이블명, 키, 필드 목록, DDL)가 이후의 권고 문서, 버전 전환, 데이터 품질 단계에 "확정된 설계이므로 그대로 재사용하라"는 안내와 함께 입력된다. 이는 생성 단계마다 스키마를 제각기 만들어 문서의 각 절이 서로 다른 테이블을 가리키던 자기모순을 막기 위한 장치로, 처리 순서와 함께 3.5절에서 다시 설명한다.

컨텍스트 구성에는 두 가지 규칙이 적용된다. 첫째, LLM에 입력되는 스키마 정보에서는 예시 값을 제거하고, 예시 값을 실제 값처럼 인용하지 말라는 주의를 덧붙인다. 예시 값이 있으면 소형 모델이 이를 실제 관측 값으로 오인하여 SQL의 조건절에 사용하는 오류가 관찰되었기 때문이다. 다만 원천 필드가 실제로 존재하는지를 스키마 정보 원문과 대조해야 하는 투영 매핑 단계만 예시 값을 포함한 원문을 받는다. 둘째, 컨텍스트의 각 요소에는 상한이 있다. 로그 구간 80행, 센서 분석 입력 16건, 도구 결과 4,000자, 소스 열람 120행의 상한은 소형 로컬 모델의 입력 한도 안에 가장 관련성이 높은 근거가 남도록 정한 값이다. 그림은 두 원천의 컨텍스트가 사전 주입과 도구 조회로 각 처리 단계에 구성되는 과정을 나타낸 그림이다.

## 3.4 단일 산출물 Docs 설계

진단 파이프라인의 최종 산출물은 하나의 마크다운 문서인 Docs이다. Docs는 개발자가 읽고 곧바로 Read Model을 재생성할 수 있어야 한다는 요구와, 이 문서가 다시 소형 LLM의 입력으로 쓰일 수 있어야 한다는 요구를 동시에 만족하도록 설계되었다. 후자 때문에 Docs는 고정된 구성과 분량 한도를 갖는다. 문서는 맨 앞의 머리말(YAML front-matter), 제목과 한 문장 결론, 근거 블록, 세 개의 필수 절, 선택 절, 맨 끝의 제약 조건 순으로 구성된다. 결론을 맨 앞에, 제약 조건을 맨 끝에 두는 배치는 긴 입력의 중간에 놓인 정보를 LLM이 잘 활용하지 못하는 현상[36]에 대응한 것이고, 근거 블록을 결론 바로 뒤이자 권고보다 앞에 고정한 것은 결론을 먼저 내리고 근거를 나중에 맞추는 사후 합리화를 구조적으로 막기 위한 배치이다. 그림은 Docs의 구성을 나타낸 그림이다.

### 3.4.1 Read Model 재생성 권고 문서

권고 문서는 어떤 Read Model을 왜 재생성 또는 보강해야 하는지에 대한 근거와 판단을 담는다. 이 절은 소프트웨어 설계 결정을 배경, 검토한 대안, 결정, 결과의 순서로 기록하는 아키텍처 의사결정 기록(Architecture Decision Record, ADR)[38]의 구조를 따라 Status, Context, Decision Drivers, Considered Options, Decision Outcome, Consequences, Non-Goals의 소절로 구성된다. ADR 구조를 채택한 이유는 권고가 단일 결론이 아니라 기각된 대안과 장단점을 함께 남겨야 개발자가 LLM의 판단을 검토하고 다른 선택을 할 수 있기 때문이다. Context에는 근거가 되는 로그 행이 수준, 행위명, 인용문, 해석의 형태로 나열되며 각 항목은 `[corr:<상관관계 식별자>]` 형식으로 출처를 밝힌다. 이 출처 표시는 머리말의 근거 출처 목록과 대조되어, 실제로 없는 로그를 근거로 삼는 오류를 사후 검사에서 잡아낼 수 있게 한다. Considered Options에는 두 개 이상의 대안이 접근 방식, 제안 필드, 장단점, 코드 조각과 함께 제시되고, Decision Outcome은 채택된 대안과 이유를 서술한다.

권고 문서는 이상의 유형에 따라 세 형태로 나뉜다. 신규 Read Model이 함께 선택된 경우 Decision Outcome은 확정된 설계의 채택을 서술하고 제안 필드는 그 설계의 필드와 일치한다. 적재 거절이나 변환 불가 이벤트처럼 원천 데이터의 결함이 원인인 경우 권고 문서는 단독으로 생성되며 격리(containment) SQL을 동반한다. 격리 SQL은 결함 이벤트를 찾아내는 조회, 오염된 Read Model 행을 무해하게 만드는 갱신 또는 삭제, 결함 이벤트가 이벤트 스토어에 들어오지 않았음을 확인하는 조회의 세 형태로 정형화되어 있으며, 프로젝션 커서를 임의로 옮겨 결함 이벤트를 건너뛰는 SQL은 정합성을 조용히 훼손하므로 생성이 금지된다. 센서 경로에서 발생한 데이터 품질 이상의 경우 권고는 ADR 대신 데이터 품질 권고의 형태를 취하여, 심각도와 그 근거, 기대 값과 실측 값의 차이를 장면 키·시도 번호·전역 순번·영향 컬럼·관측 값·기준값 규칙으로 기술한 근거 목록, 영향 범위, 근본원인의 경로(상류 센서의 물리적 불가능, 프로젝션 결함, 기준값의 노후화), 그리고 격리·수정·강화(contain, fix, harden)의 단계별 대안으로 구성된다.

### 3.4.2 Read Model 생성 SQL(DDL)

두 번째 절은 신규 Read Model을 실제로 만드는 데 필요한 산출물을 담는다. 절의 첫머리에는 이하의 변경이 사람의 승인 후에만 적용됨을 알리는 실행 안내문이 고정된다. 본문은 대상 테이블명, 키 컬럼, 원천 이벤트를 밝힌 뒤 테이블과 인덱스를 생성하는 DDL을 SQL 코드 블록으로 제시하고, 필드 목록을 스키마 정보와 같은 M-Schema 튜플로 기술한다. 표는 신규 Read Model 생성 단계가 산출하는 항목과 각 항목에 적용되는 검증을 정리한 것이다.

| 항목 | 내용 | 검증 |
| --- | --- | --- |
| proposedName | `read_` 접두의 스네이크 케이스 테이블명 | 명명 규칙, Drizzle 스키마의 테이블명과 일치 |
| purpose, rationale | 용도와 신규 설계의 근거 (기준 로그 인용) | — |
| sourceEvents, keyColumns | 원천 이벤트 유형과 키 컬럼 | 키 컬럼이 필드 목록에 존재 |
| fields[] | 컬럼명(snake_case)·자료형·의미 | camelCase 자동 교정 |
| migrationSql | CREATE TABLE + CREATE INDEX | 실제 PostgreSQL에서 트랜잭션 실행 후 되돌림 |
| drizzleSchema, projectorCode | Drizzle 스키마와 프로젝터 구현 | `tsc --noEmit` 컴파일, payload 키의 실재 |
| controllerWiring | 스키마 내보내기, 캐치업 메서드, 라우트, 모듈 등록 | 새 키에 대한 zod 스키마 확장의 실재 |

DDL만으로는 빈 테이블이 만들어질 뿐이므로 이 절에는 테이블을 실제로 채우기 위한 두 부속 산출물이 함께 실린다. 첫째는 투영 매핑 명세로, 원천 이벤트의 어떤 payload 필드가 어떤 컬럼으로 어떤 변환을 거쳐 반영되는지를 표로 기술하고, payload에서 유래하지 않는 파생 컬럼과 갱신 키, 이벤트를 처음부터 다시 반영할 때 프로젝션 커서를 초기화해야 한다는 주의를 함께 담는다. 이 명세는 별도의 LLM 단계가 확정된 설계를 보고 생성하되, 대상 컬럼이 설계의 필드에 실제로 있고 원천 필드가 스키마 정보 원문에 실제로 있는 행만 남기는 근거 대조를 거친다. 둘째는 스키마 정보 등록 SQL이다. 신규 Read Model의 산출 항목(테이블명, 용도, 키 컬럼, 필드 목록)은 Insight Read DB의 스키마 정보와 같은 구조이므로, LLM을 다시 호출하지 않고 `insight_entity`와 `insight_field`에 대한 INSERT 문으로 규칙에 따라 변환된다. 개발자가 DDL과 이 INSERT를 함께 적용하면 다음 분석부터 신규 Read Model이 Insight Read DB에 포함되며, 이것이 3.1절의 피드백 루프를 완성하는 구체적인 장치이다. 신규 Read Model이 선택되지 않은 문서에서는 이 절에 격리 SQL 또는 위반 레코드의 확인 SQL이 실리고, 그마저 없으면 근거 부족 표시로 대체된다.

### 3.4.3 API 버저닝 전략

세 번째 절은 Read Model의 교체가 조회 API에 미치는 변경을 다룬다. 제안 시스템의 버전 전략은 기존 자산의 보존을 불변 규칙으로 삼는다. 신규 Read Model은 기존 테이블을 고치는 대신 `_v2` 접미의 새 테이블로 만들어지고, 이를 채우는 프로젝터와 노출하는 라우트도 `V2` 접미와 `/v2/` 경로의 새 자산으로 추가되며, 기존 파일의 수정은 모듈 등록이나 내보내기 추가와 같은 한 줄 추가로 제한된다. 이는 새 버전을 기존 버전과 나란히 준비한 뒤 검증이 끝나면 트래픽을 옮기는 블루-그린 배포[40]의 원리를 Read Model 수준에 적용한 것으로, Read Model을 언제든 다시 만들 수 있다는 이벤트 소싱의 성질과 결합하여 v2 테이블을 이벤트 재생으로 채운 뒤 검증하고 전환하며 문제가 있으면 v1으로 즉시 되돌릴 수 있게 한다. 절의 본문은 변경 이력을 Added, Changed, Deprecated, Removed, Fixed, Security의 범주로 기록하는 Keep a Changelog 형식[41]을 따라 Unreleased 항목 아래에 변경을 기술하고, 하위 호환 변경과 파괴적 변경의 구분, 전환 전 테스트, 되돌림 조건으로 구성된 마이그레이션 절차를 제시한다. 신규 Read Model이 동반된 경우 절차에는 스키마 정보 등록 단계가 포함된다. 코드 변경은 파일 경로, 변경 종류(추가 또는 수정), 설명, 코드 조각의 목록으로 산출되며, 확정된 설계가 있을 때는 코드 조각의 라우트와 프로젝터 클래스명이 확정 설계와 일치하는지 검사되어, 버전 전환 단계가 다른 이름의 사본을 만들어 문서가 어긋나는 것을 막는다. 버전 전환이 선택되지 않은 문서에서는 API 버전에 미치는 영향의 서술로 대체된다.

### 3.4.4 Docs 저장 및 활용 워크플로

생성된 Docs는 기준 로그의 발생 시각과 문서 식별자를 조합한 파일명(`<날짜>-<시각>-<docId>.md`)으로 저장소의 `llm-docs/` 디렉터리에 저장된다. 저장 직후 문서 형식 검사가 머리말의 존재, 세 필수 절의 고정 순서, 제약 조건의 존재, 근거 충분성 플래그와 근거 부족 표시의 일치, 본문의 출처 표시가 머리말의 근거 출처에 실제로 있는지, 선택 절을 제외한 핵심 부분의 분량 한도(목표 8,000, 상한 20,000토큰)를 검사한다. 검사 결과는 로깅 규약에 따라 정보 수준으로만 기록되며 재실행을 일으키지 않는다.

Docs의 활용은 사람의 검토에서 시작된다. 개발자는 결론과 근거 블록으로 이상의 성격을 파악하고 권고 문서의 대안과 장단점을 검토하여 채택 여부를 결정한다. 채택하는 경우 두 번째 절의 DDL과 스키마 정보 등록 SQL을 실행하고, 선택 절의 프로젝터와 연결 코드를 저장소에 추가한 뒤 캐치업으로 신규 테이블을 이벤트 재생으로 채우며, 세 번째 절의 절차에 따라 v2 라우트를 검증하고 전환한다. 이 과정에서 시스템은 세 가지 피드백 루프로 자가 적응을 유지한다. 첫 번째는 스키마 정보 순환 루프로, 승인 후 등록된 스키마 정보가 다음 분석의 컨텍스트에 자동으로 포함되어 시스템이 새로 갖게 된 Read Model을 인지하는 경로이다. 두 번째는 등록 누락 감시 루프로, 개발자가 DDL만 적용하고 스키마 정보 등록을 잊으면 누락 감시기가 이를 경고 신호로 내보내고 로그 경로가 등록을 권고하는 Docs를 생성하여 누락을 회수한다. 세 번째는 자기 유발 방지 루프로, 진단 파이프라인의 로그를 정보 수준으로 제한하는 규약을 통해 분석 결과가 새로운 분석을 일으키는 악순환을 차단한다. 그림은 Docs의 저장에서 개발자의 검토와 승인, 적용, 그리고 다음 분석 사이클로 이어지는 순서와 등록 누락 감시의 개입을 나타낸 시퀀스 다이어그램이다.

## 3.5 LLM 파이프라인 구현

제안 시스템은 NestJS 기반의 단일 애플리케이션으로 구현되었으며, 이벤트 소싱·CQRS 영역, 관측 계층, LLM 영역이 기능 모듈로 나뉘어 있다. 진단 파이프라인의 분석 부분은 NestJS 모듈이 아닌 순수 라이브러리로 구현되어, 로그 경로와 센서 경로의 두 모듈이 각자 진단 도구 구현체를 넘겨주어 인스턴스를 만든다. 표는 구현 환경을 정리한 것이다.

| 구분 | 구현 |
| --- | --- |
| 애플리케이션 | NestJS 11, TypeScript 5.9 (strict, `any` 금지), Drizzle ORM |
| 데이터베이스 | PostgreSQL 17 (TimescaleDB 2.17, `log_event`는 하루 단위로 분할되는 시계열 테이블) |
| 메시지 브로커 | Apache Kafka 3노드 KRaft 클러스터 (`log-events`, `sensor-values` 토픽), fluent-bit TCP 수집기 |
| 로깅 | Pino (nestjs-pino), 콘솔·파일·TCP 소켓의 3중 전송 |
| LLM 오케스트레이션 | LangGraph 상태 그래프[42], OpenAI 호환 채팅 클라이언트, zod 출력 스키마 |
| LLM 런타임 | LM Studio 로컬 서버, 1차 선별 qwen3.5-9b, 분석 qwen3.6-27b 계열, temperature 0 |

그림은 애플리케이션을 구성하는 NestJS 모듈과 라이브러리, 그리고 이들 사이의 의존 관계를 나타낸 컴포넌트 다이어그램이다. 관리 대상 시스템의 모듈과 관리 시스템의 모듈은 직접 호출로 묶이지 않고 Kafka 토픽과 로그라는 비동기 채널로만 연결되며, 두 경로의 모듈은 각자 진단 도구 구현체를 넘겨주어 분석 라이브러리의 인스턴스를 만든다.

> [그림 3-9] `fig3-09-module-components.svg` — NestJS 모듈 컴포넌트 다이어그램

**1차 선별.** 로그 경로의 소비자는 `log-events` 토픽을 5초마다 읽어 최대 500건의 배치를 만들되, 정상 적재 로그와 상관관계 식별자가 없는 정보 수준의 프레임워크 로그는 제외한다. 배치에 경고 이상의 레코드가 하나라도 있으면 규칙 기반 사전 판정이 LLM을 호출하지 않고 즉시 이상으로 판정하고 해당 레코드의 상관관계 식별자를 반환한다. 이 사전 판정은 초기 구현에서 SLM이 큰 배치 안의 경고 로그를 놓치는 경우가 관찰되어 도입되었다. 경고 이상의 레코드가 없는 배치만 SLM의 판정으로 넘어가며, 판정 프롬프트는 하나의 상관관계 식별자가 요청 수신에서 정상 완료로 끝나는 궤적을 확실한 정상으로, 시작만 있고 완료가 없는 순서 이상, 400 이상의 응답 코드, 요청 처리 실패, 동일 요청의 반복을 이상으로 정의하고, 판단이 모호하면 이상으로 간주하도록 지시한다. 배치는 표로 요약하지 않고 원본 JSON 행 그대로 전달하여 맥락 필드의 손실을 막는다.

센서 경로는 `sensor-values` 토픽을 8건 단위로 읽으며, 각 묶음은 SLM에 앞서 네 층의 규칙 기반 표시를 받는다. 물리(physical) 층은 파지 성공 여부의 정의역 위반, 회전 행렬의 직교성·행렬식 조건 위반, 0 이하의 파지 깊이, 이미지 범위를 벗어난 2D 포즈처럼 단독으로 불가능한 값을, 정합성(consistency) 층은 파지에 성공하였다고 기록된 시도의 이동 벡터와 깊이가 작업 공간을 벗어나는 모순을, 급변(jump) 층은 같은 장면에서 직전 시도 대비 평균 깊이가 0.1m를 넘게 변하는 경우를, 통계(stat) 층은 관측 분포에서 robust-z 3.5를 넘어 벗어나는 값을 표시한다. 표시가 하나도 없는 묶음은 LLM을 호출하지 않고 정상으로 확정되고, 표시가 있는 묶음만 SLM이 수기로 작성한 기준값 문서와 함께 해석하며, 물리·정합성 층의 확정 위반은 SLM의 판정과 무관하게 이상으로 반영된다. 이상으로 판정된 묶음은 하나의 물리적 사건을 이루는 단위로 묶여 관리되어, 정상 묶음이 이어지거나 15초간 입력이 없거나 64건에 이르면 마감되면서 지목된 장면을 우선하여 16건 이내로 줄인 뒤 한 번만 진단 파이프라인으로 넘어간다. 이는 같은 사건에 대해 문서가 반복 생성되는 것을 막는다. 이 방식은 규칙 기반 표시 없이 SLM만으로 판정하는 모드로 설정에서 전환할 수 있어 제 IV 장의 비교 실험에 사용된다. 그림은 센서 값의 발행에서 규칙 기반 표시, SLM 판정, 사건 단위 묶음을 거쳐 진단 파이프라인으로 넘어가는 센서 경로의 처리 순서를 나타낸 시퀀스 다이어그램이다.

> [그림 3-10] `fig3-10-seq-sensor-lane.svg` — 센서 경로 시퀀스 다이어그램 (발행 → 규칙 기반 표시 → SLM 판정 → 사건 단위 묶음 → 분석)

**분석 처리 흐름.** 1차 선별을 통과한 입력은 LangGraph의 상태 그래프로 구현된 분석 처리 흐름에 전달된다. 상태 그래프는 처리 단계를 노드로, 단계 사이의 흐름을 간선으로 정의하고 모든 노드가 하나의 공유 상태를 읽고 쓰는 실행 모델이다. 공유 상태는 입력(이상 로그 구간 또는 센서 판정 결과, 스키마 정보), 진단 결과(근본원인, 도구 호출 기록), 조치 결정, 생성 단계별 산출물, 최종 문서로 구성되며, 생성 산출물 채널은 병렬로 실행된 노드의 결과를 합치는 규칙을 갖는다. 그림은 분석 처리 흐름을 LLM이 판단하는 구획과 규칙 기반 처리가 담당하는 구획으로 나누어 나타낸 활동 다이어그램이다.

> [그림 3-11] `fig3-11-act-analysis-graph.svg` — 분석 처리 흐름 활동 다이어그램 (LLM 판단 / 규칙 기반 처리 구획)

첫 노드는 근본원인을 분석하는 진단 에이전트이다. 진단 에이전트는 추론과 도구 호출을 번갈아 수행하는 ReAct 방식[25]으로 동작하며, 도구 호출 4회, 최종 출력 재요청 2회, 전체 LLM 호출 8회의 세 겹 상한을 갖는다. 상한에 이르면 지금까지의 근거로 최종 판정을 출력하라는 메시지가 주입된다. 출력은 이상 유형, 요약, 시간순 재구성, 실패한 요청의 의도, 의심되는 Read Model의 부족으로 구성되며, 이상 유형은 3.1절의 원칙에 따라 자유 형식의 문자열이다. 프롬프트는 적재 단계의 검증 거절과 프로젝션 단계의 변환 실패를 인과 관계 위에서 구분하고, 반복된 조회 실패의 자연어 질의를 실패한 요청의 의도로 그대로 옮기도록 지시한다. 그림은 진단 에이전트의 도구 호출 반복과, 도구 호출이 끝난 뒤 다른 노드와 공유하는 출력 검증·재요청 규약을 나타낸 시퀀스 다이어그램이다.

> [그림 3-12] `fig3-12-seq-diagnosis-agent.svg` — 진단 에이전트 시퀀스 다이어그램 (도구 호출 반복과 출력 검증 규약)

조치 결정 노드는 근본원인 분석의 결과로부터 네 가지 조치 유형 가운데 최대 세 개를 고르며, LLM의 선택 앞뒤에 규칙 기반 처리가 배치된다. 선택 이전의 두 사전 판정은, 기준 로그가 조회 실패 한 번뿐이고 다른 이상이 없으면 조회 요구가 아직 드러나지 않았으므로 LLM을 호출하지 않고 조치 불필요로 확정하고, 기준 로그가 적재 거절이면 결함 이벤트가 이벤트 스토어에 들어오지 않았으므로 격리 권고 단독으로 확정한다. 스키마 변화, 변환 불가 이벤트, 센서 이상, 두 번 이상 반복된 조회 실패처럼 조치의 근거가 분명한데 LLM이 빈 선택을 반환하면 모순을 지적하여 다시 요청하고, 그래도 비어 있으면 기준 로그별로 정해진 기본 조치로 대체한다. 선택 이후의 두 규칙은 산출물(신규 Read Model 또는 버전 전환)이 선택되었는데 권고가 없으면 권고 문서를, 신규 Read Model이 선택되면 버전 전환을 강제로 동반시킨다. 표는 기준 로그별 처리와 기본 조치를 정리한 것이다.

| 기준 로그 | 처리 | 확정 또는 기본 조치 |
| --- | --- | --- |
| 조회 실패 1회 (단독) | 사전 판정, LLM 미호출 | 조치 불필요 |
| 적재 거절 (변환 불가 이벤트 없음) | 사전 판정, LLM 미호출 | 권고 문서 (격리 SQL 동반) |
| 변환 불가 이벤트 | LLM 선택 → 재요청 → 기본 조치 | 권고 문서 |
| 스키마 변화, 조회 실패 2회 이상 | LLM 선택 → 재요청 → 기본 조치 | 신규 Read Model + 권고 문서 + 버전 전환 |
| 센서 이상 | LLM 선택 → 재요청 → 기본 조치 | 데이터 품질 권고 + 신규 Read Model + 버전 전환 |

산출물 생성 단계는 신규 Read Model, 투영 매핑, 권고 문서, 버전 전환, 데이터 품질 권고의 다섯 노드로 이루어지며 실행 순서는 두 가지로 나뉜다. 신규 Read Model이 선택되면 다른 노드를 병렬로 실행하는 대신 신규 Read Model 노드와 투영 매핑 노드를 먼저 차례로 실행하여 설계를 확정하고, 확정된 설계를 입력받은 나머지 노드를 다음 단계에서 병렬로 실행한다. 신규 Read Model이 선택되지 않았으면 선택된 노드를 곧바로 병렬 실행한다. 설계를 먼저 확정하는 이 순서는 3.3.3항에서 언급한 절 사이의 자기모순을 막기 위한 것으로, 병렬 실행만 사용하였던 초기 구현의 품질 검토에서 가장 잦았던 결함이 노드마다 서로 다른 테이블명과 컬럼을 만들어 내는 것이었다는 결과에 근거한다. 마지막 문서 구성 노드는 LLM을 호출하지 않고 생성 산출물을 3.4절의 구성으로 배치하며, 산출물만 있고 권고가 없는 자기모순이 생성 노드의 실패로 생기면 규칙에 따라 만든 대체 권고로 메우거나 산출물을 보류한다.

**프롬프트 구조.** 진단 에이전트를 제외한 모든 노드는 하나의 호출 규약을 공유한다. 시스템 메시지에는 노드의 역할, 판단 규칙, 출력 JSON 형식을 담은 역할 프롬프트가, 사용자 메시지에는 3.3.3항의 규칙으로 구성된 근거 텍스트가 놓인다. 모델은 자유로운 산문으로 추론한 뒤 마지막에 JSON 코드 블록을 출력하고, 파이프라인은 마지막 코드 블록만을 추출하여 zod 스키마로 검증한다. 출력 형식을 문법으로 강제하는 구조화 출력 기능 대신 산문 추론 후 JSON 출력을 택한 것은, 형식 강제가 소형 모델의 추론 품질을 떨어뜨린다는 보고[39]에 근거한다. 표는 각 노드의 프롬프트 구성을 정리한 것이다.

| 노드 | 역할 프롬프트의 핵심 규칙 | 근거 텍스트 | 출력 |
| --- | --- | --- | --- |
| 근본원인 분석 | 시간순 재구성, 실패 지점의 인과 구분, 이상 유형의 자유 명명, 도구 결과 우선 | 로그 구간 또는 센서 판정 결과 (+도구 결과 누적) | anomalyKind, summary, timeline, failedIntent, suspectedReadModelGap |
| 조치 결정 | 4개 조치의 정의, 신호별 규칙, 조치 불필요로 판정해야 하는 경우 | 근본원인 + 로그 구간 표 + 스키마 정보 | selected[], reasoning |
| 신규 Read Model | `read_` 접두 명명, payload에서 얻을 수 있는 컬럼만, 집계 요구는 집계 기준을 키로, 프로젝터 형식, 새 키의 zod 확장 | 근본원인 + 근거 + 스키마 정보 + 소스 발췌 | 3.4.2항의 산출 항목 |
| 투영 매핑 | 실재 필드만, 변환 없음은 그대로 표기, 파생 컬럼 분리, 재생 시 주의 | 근거 + 스키마 정보 원문 + 확정 설계 | rows[], derivedColumns[], upsertKey, replayNote |
| 권고 문서 | ADR 구조, `[corr:]` 출처 표시, 격리 SQL 3형, 커서 조작 금지 | 근본원인 + 조치 결정 + 근거 + 스키마 정보 + 확정 설계 + 소스 발췌 | ADR 항목, containmentSql, apiVersionImpact |
| 버전 전환 | 기존 자산 보존 규칙, Keep a Changelog 범주, 확정 설계의 클래스명·라우트 준수 | 근본원인 + 확정 설계 + 소스 발췌 | codeChanges[], changelogEntries[], 절차 항목 |
| 데이터 품질 권고 | 근거 우선 항목 순서, 정해진 값만 사용, 격리·수정·강화 단계 규칙 | 센서 판정 결과 + 근본원인 + 스키마 정보 + 기준값 + 확정 설계 | 심각도, sensorEvidence[], 대안, containmentSql |

**응답 검증.** LLM의 응답이 Docs에 실리기까지는 일곱 단계의 검증을 거친다. 앞의 세 단계는 실패하면 직전 출력과 오류 내용을 대화에 덧붙여 모델이 자신의 오류를 보고 고치게 하는 재요청(re-ask)으로 되돌린다. temperature 0에서 같은 프롬프트를 다시 보내면 같은 실패가 그대로 반복되므로, 단순 재시도 대신 오류를 보여 주는 재요청을 택한 것이다. 재요청은 1회로 제한되며, 시간 초과와 같은 전송 실패는 별도의 예산(3회)으로 관리되어 재요청 예산을 소모하지 않는다. 표는 검증 단계를 정리한 것이다.

| 단계 | 검증 | 잡는 결함 | 실패 시 |
| --- | --- | --- | --- |
| ① 형식 | zod 스키마 검증 | JSON 파싱 실패, 항목 누락, 자료형 불일치, 명명 규칙 위반 | 재요청 |
| ② 문자 오염 | 한자(CJK) 혼입 검사 | 로컬 모델의 한자 혼입 (정상 한국어에는 한자가 없어 오탐 없음) | 재요청 |
| ③ 실행 가능성 | 실제 PostgreSQL에서 트랜잭션 실행 후 되돌림, `tsc --noEmit` 컴파일, 새 키의 zod 확장·payload 키·라우트·클래스명의 실재 | 실행되지 않는 SQL, 컴파일되지 않는 코드, payload에 없는 키 접근 | 재요청, 소진 시 ⑤ |
| ④ 근거 대조 | 관측 값이 근거 텍스트에 실재, 매핑 행의 대상 컬럼·원천 필드가 실재 | 입력에 없는 값의 지어냄 | 행 제거, 근거가 하나도 없으면 출력 폐기 |
| ⑤ 규칙 기반 합성 | 검증된 필드·키로부터 DDL, Drizzle 스키마, 프로젝터, 권고, 버전 전환을 정해진 틀로 생성 | 재요청 후에도 남은 컴파일 불가 코드 | 틀로 교체, 얻을 수 없는 컬럼은 null + TODO |
| ⑥ 완전성 검사 | 권고 없이 DDL·API만 남은 자기모순 | 생성 노드의 부분 실패 | 대체 권고 생성, 불가 시 산출물 보류 |
| ⑦ 문서 형식 검사 | 머리말, 3절 순서, 제약 조건, 근거 부족 표시의 일치, 출처 표시의 실재, 분량 한도 | 형식 위반 | 기록만 (재실행 없음) |

세 번째 단계의 실행 가능성 검증은 본 구현의 특징적인 부분이다. 생성된 DDL은 실제 데이터베이스의 트랜잭션 안에서 실행된 뒤 되돌려져 문법이 아니라 실행 가능성이 검증되고, 생성된 프로젝터와 스키마 코드는 저장소 소스를 복사한 임시 디렉터리에 놓여 실제 컴파일러로 검사되며, 알려진 오류 유형에는 수정 힌트가 재요청 메시지에 함께 실린다. 이 단계가 잡는 것은 "그럴듯하지만 실행되지 않는 SQL"과 "payload에 없는 키를 읽어 모든 컬럼이 비는 프로젝터"처럼 형식이 아니라 내용이 잘못된 출력이며, 이는 LLM은 설계를 판단하고 실행 가능성은 규칙 기반 처리가 보장한다는 3.1절의 첫 번째 원칙을 구체화한 것이다. 그림은 검증 단계의 흐름과 실패 시의 재요청·합성 분기를 나타낸 활동 다이어그램이다.

> [그림 3-13] `fig3-13-act-validation.svg` — LLM 응답 검증 활동 다이어그램

LLM 호출에는 로컬 모델을 안정적으로 운용하기 위한 세 가지 장치가 있다. 분석 처리 흐름의 모든 LLM 호출은 프로세스 전체에서 하나씩 순서대로 처리되는 큐를 거치는데, 노드를 병렬로 실행하면서 하나의 로컬 서버에 동시에 요청을 보내면 서로의 시간 초과를 일으키는 연쇄가 관찰되었기 때문이다. 추론 과정을 함께 출력하는 모델에는 추론 출력을 끄는 옵션을 전달하여 출력 예산이 추론에 소모되지 않도록 하고, JSON 추출은 응답의 마지막 코드 블록을 취하되 파싱에 실패하면 복구 라이브러리로 교정을 시도한다. 이 장치들은 외부 API를 사용할 수 없는 환경에서 소형 로컬 모델로 파이프라인을 안정적으로 구동하기 위한 것이다.

## 3.6 MAPE-K 관점의 자가 적응 루프 분석

본 절에서는 제안 시스템을 MAPE-K 참조 모델[29]에 대응시켜 자가 적응 루프로서의 구조를 분석한다. MAPE-K는 관리 대상 시스템을 관측하는 Monitor, 적응의 필요성을 판단하는 Analyze, 대응 방안을 세우는 Plan, 방안을 적용하는 Execute의 네 단계와 이들이 공유하는 지식 베이스(Knowledge)로 구성된다. 표는 각 단계에 대응하는 제안 시스템의 구성 요소를 정리한 것이다.

| MAPE-K 단계 | 제안 시스템의 구성 요소 | 판단 주체 |
| --- | --- | --- |
| Monitor | 로깅 규약과 이상 신호 목록(S1~S8), TCP·파일의 두 전달 경로, Log DB 적재, 센서 값 발행, 등록 누락 감시기 | 규칙 기반 처리 |
| Analyze | 로그 경로의 필터·사전 판정·SLM 판정, 센서 경로의 규칙 기반 표시·SLM 판정·사건 단위 묶음, 진단 에이전트의 근본원인 분석 | 규칙 기반 처리 + SLM, 진단 에이전트(LLM + 도구) |
| Plan | 조치 결정 노드(사전 판정·LLM 선택·동반 규칙), 생성 노드 5종, 검증 단계 ①~⑥, 문서 구성 | LLM(설계 판단) + 규칙 기반 처리(검증·합성·구성) |
| Execute | Docs 저장과 문서 형식 검사, 사람의 승인, DDL 실행·프로젝터 연결·이벤트 재생·스키마 정보 등록·API 전환 | 사람 (human-in-the-loop) |
| Knowledge | Insight Read DB(스키마 정보), Log DB(이력), 센서 기준값·규칙 문서, 기존 소스 코드 발췌 | — |

Monitor 단계는 전적으로 규칙 기반 처리이다. 관리 대상 시스템은 관리 시스템을 위한 별도의 센서를 갖지 않으며, 로깅 규약을 따르는 로그와 센서 값 채널이 센서의 역할을 한다. 이는 센서와 실행기를 관리 대상 시스템에 새로 붙이는 통상의 방식[12]과 비교할 때 기존 시스템의 관측 수단을 그대로 센서로 재사용하여 관리 대상 시스템의 변경을 최소화한다. Analyze 단계는 두 층으로 나뉜다. 1차 선별은 모든 배치에 대해 실행되므로 규칙 기반 처리와 SLM으로 비용을 제한하고, 근본원인 분석은 선별을 통과한 소수의 신호에 대해서만 도구 호출을 동반한 진단 에이전트가 수행한다. 전통적인 접근에서 Analyze가 규칙이나 모델에 대한 위반 탐지로 구현되는 것과 달리, 제안 시스템의 Analyze는 이상의 유형을 자유롭게 명명하고 근본원인을 자연어로 설명한다.

Plan 단계는 제안 시스템이 전통적인 자가 적응 기법과 가장 크게 구별되는 지점이다. Rainbow와 같은 기존 접근[30]에서 Plan은 미리 정의된 적응 전략 가운데 하나를 고르는 것이지만, 제안 시스템의 Plan은 신규 Read Model의 스키마, DDL, 프로젝터 코드, API 버전 전환 절차처럼 설계 시점에 미리 열거할 수 없는 산출물을 실행 시점에 생성한다. 다만 어떤 종류의 산출물을 만들 것인가의 선택은 네 가지 조치 유형으로 제한되므로, 제안 시스템의 적응 범위는 조치의 종류에서는 고정되어 있고 조치의 내용에서는 열려 있는 이중 구조를 갖는다. 이 구조 안에서 LLM의 판단은 사전 판정, 동반 규칙, 일곱 단계의 검증으로 둘러싸여 있으며, 검증을 통과하지 못한 판단은 규칙 기반 합성으로 대체되거나 보류된다.

Execute 단계는 자동화되지 않는다. 제안 시스템은 생성된 DDL과 코드를 스스로 적용하지 않고 Docs로 산출하는 데서 멈추며, 적용은 사람이 문서를 검토하고 승인한 뒤에 수행한다. 이것이 제안 시스템에서 사람이 개입하는 지점이며, 그 위치는 Plan과 Execute 사이의 경계이다. 이 지점을 사람에게 남긴 이유는 두 가지이다. LLM이 생성한 스키마는 문법적으로 유효하고 실행 가능하더라도 도메인의 관점에서 부적절할 수 있으며[24] 이를 판단하는 최종 권한은 도메인을 아는 사람에게 있어야 한다는 점, 그리고 DDL의 적용과 API 전환은 되돌리기 어려운 변경이므로 자동으로 적용하면 LLM 판단의 오류가 데이터 계층으로 번진다는 점이다. 제안 시스템은 이 위험을 기존 자산을 보존하는 버전 전략과 사람의 승인이라는 두 장치로 통제한다. 사람이 개입하는 두 번째 지점은 Knowledge의 갱신이다. 신규 Read Model의 스키마 정보는 사람이 DDL과 함께 등록하며, 시스템은 등록 누락 감시로 빠뜨린 등록을 회수할 뿐 Insight Read DB를 스스로 갱신하지 않는다. 그림은 제안 시스템을 MAPE-K 루프에 대응시킨 그림이다.

> [그림 3-14] `fig3-14-mape-k-mapping.svg` — MAPE-K 관점에서 본 Self-Adaptive CQRS의 자가 적응 루프와 사람의 개입 지점

Knowledge는 제안 시스템에서 자가 적응을 반복 가능하게 만드는 요소이다. 전통적인 접근에서 지식 베이스가 아키텍처 모델과 정책으로 구성되어 설계 시점에 대부분 확정되는 것과 달리, 제안 시스템의 Insight Read DB는 적응의 결과로 갱신된다. 한 번의 루프에서 생성된 신규 Read Model의 스키마 정보가 등록되면, 다음 루프의 Analyze와 Plan은 이를 기존 자산으로 인식하여 같은 조회 요구에 대해 신규 설계 대신 기존 Read Model의 활용을 판단하게 된다. 이 순환은 자율 컴퓨팅이 제시한 자기 구성(self-configuration)의 성질[9]을 Read Model 수명주기의 생성·진화 단계에서 구현한 것으로 볼 수 있다. 반면 루프의 안정성 측면에서 제안 시스템은 두 가지 한계를 갖는다. 문서 형식 검사에 실패한 Docs는 기록될 뿐 다시 생성되지 않으며, Execute 단계의 결과, 즉 개발자가 권고를 채택하였는지와 적용 후 조회 요구가 실제로 충족되었는지는 스키마 정보 등록의 유무 외에는 루프에 되돌아오지 않는다. 이 두 한계는 제 V 장에서 향후 연구로 다룬다.
