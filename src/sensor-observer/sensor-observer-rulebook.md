# 센서 이상값 판정 룰북 v2 (llm-only 관찰자용)

> 이 문서가 판정 권한의 전부다. 이상 판정의 근거는 아래 R1~R6 뿐이며, reason 에는
> 반드시 rule ID(R1~R6)를 인용한다. 여기와 베이스라인의 rule 에 없는 임계값·규칙을
> 발명하지 마라. 특히 베이스라인 하단 "분포 통계"의 관측 클러스터 수치(예: 0.1998)는
> 참고 정보일 뿐 임계값이 아니다 — 그것을 근거로 한 판정은 무효다.

## 판정 절차 — 전부 조용히 수행한다

**R1~R5 는 산문 0줄이 기본이다. 통과한 규칙·정상 레코드·검사 수행 과정을 한 글자도
서술하지 마라("모든 레코드에서 위반 없음" 같은 문장도 금지). 위반을 찾은 레코드만
위반 요약에 한 줄 쓴다.**

- R1 gripSucceed 도메인 — `gripSucceed` 가 0 또는 1 이 아니면 위반.
- R2 깊이 물리 하한 — `grip3dPose` 의 z1..z8 중 **0 이하**가 있으면 위반
  (깊이 ≤ 0 은 물리적으로 불가능).
- R3 2D 픽셀 이미지 범위 — `grip2dPose` 의 xl·xr 이 [0, 1920], yl·yr 이 [0, 1110]
  픽셀 밖이면 위반.
- R4 회전행렬 유효성 — `robotTf` 의 rotation_3x3(행우선 9개)에서 각 열의
  제곱합(L2 노름²)이 1±0.04 를 벗어나거나, 열 부호가 통째로 반전(반사행렬,
  det=-1)되거나 직교성이 깨졌으면 위반.
- R5 성공-포즈 정합 — `gripSucceed`=1(성공) 레코드만: `robotTfTranslation` 이
  워크스페이스(x [-0.50, 0.50], y [0.65, 0.95], z [0.95, 1.15] m) 밖이거나
  z1..z8 이 [0.01, 0.30] m 밖이면 위반(잡을 수 없는 위치/깊이에서 성공은 모순).
  translation 의 x,y,z 는 각각 자기 축의 범위와만 비교하라(필드 혼동 금지).
  `gripSucceed`=0(실패) 레코드의 범위 밖 값은 자연 노이즈일 수 있으므로 R5 를
  적용하지 않는다.
- R6 같은 scene 급변 — **sceneKey 문자열이 완전히 동일한** 레코드 쌍((C) 이월
  레코드 포함)에만 적용한다. R6 를 시작하기 전에 먼저 배치의 sceneKey 목록에서
  두 번 이상 등장하는 sceneKey 만 골라라. 그런 sceneKey 가 하나도 없으면 R6 는
  검사할 쌍이 없는 것이다 — R6-CHECK 를 0줄 쓰고 곧장 다음으로 넘어가라.
  sceneKey 가 다른 인접 레코드끼리의 비교·체인 비교는 절대 금지다(objectName 이
  같아도 scene 이 다르면 장면 자체가 다르므로 비교 대상이 아니다).
  같은 scene 쌍마다 아래 계산 라인을 정확히 한 줄씩 출력하라(생략 금지 — 이 라인이
  없으면 R6 판정 자체가 무효다. 수치는 소수 3자리로 반올림):
  `R6-CHECK <scene 끝 5자리>: <선행 z평균> → <후행 z평균>, Δ=<차이> vs 0.10`
  Δ > 0.10 m 이고 objectName 이 같으면 위반. objectName 전환 등 장면 변화로
  설명되면 정상. robotTfTranslation 의 attempt 간 이동은 마운트 변경으로 정상 —
  급변 근거 금지. **R6 위반 판정은 sceneKey 가 같은 두 레코드의 쌍에서만 가능하다.
  sceneKey 가 다른 레코드끼리의 비교에서 Δ > 0.10 이 나와도 절대 위반이 아니다 —
  scene 이 다르면 물체 배치가 달라 값대가 다른 것이 정상이다.**

## 오판 방지 (하나라도 어기면 그 판정은 무효)

1. 위반 주장 전, 관측값과 경계값을 나란히 놓고 **부등호가 참인지 재확인**하라
   (예: "0.178 > 0.1998" 은 거짓이므로 판정 불가). 부등호가 거짓이면 버려라.
2. '처음 보는 값(novelty)'은 이상이 아니다. 클러스터 밖·분포 밖이라는 이유만으로
   판정하지 마라(새 마운트·새 물체일 수 있다).
3. 인용할 관측값 숫자를 레코드에서 특정할 수 없으면 그 판정은 버려라.
4. 애매하면 정상(triggered=false)이다.

## 출력 계약

**응답의 첫 글자는 반드시 `R6-CHECK`(같은 scene 쌍이 있을 때) 또는 ```` ```json ````
(그 외 모든 경우)으로 시작한다. "R1 위반 —" 같은 서술형 문장으로 응답을 시작하는
것은 계약 위반이다 — 위반 요약은 R6-CHECK 라인들 뒤에만 올 수 있다.**

출력은 아래 세 부분이 전부이며 이 순서를 지킨다. 다른 산문은 전부 금지다.

1. R6-CHECK 계산 라인들 — 같은 scene 쌍이 있을 때만.
2. 위반 요약 — 위반된 레코드만 한 줄씩(rule ID + 관측값 인용 + 부등호 비교), 최대 8줄.
   위반이 하나도 없으면 이 부분을 통째로 생략한다.
3. JSON 코드블록 정확히 하나.

`offendingSceneKeys` 에는 위반 레코드의 `sceneKey` 값을 레코드 JSON 에서 **글자
그대로 복사**해 담는다(발명·요약·수정 금지). 위반 레코드를 특정할 수 없으면
트리거하지 마라.

### 출력 예시 A — 같은 scene 쌍 1개, R6 위반 (scene 번호는 가상의 예시)

R6-CHECK 99991: 0.066 → 0.177, Δ=0.111 vs 0.10
R6 위반 — sceneKey 예시카테고리_CR99_예시물체_99991, Δ=0.111 > 0.10 (suddenJump_withinScene, objectName 동일)
```json
{ "triggered": true, "reason": "R6 suddenJump_withinScene: 같은 scene 연속 attempt 간 z평균 0.066 → 0.177, Δ=0.111 > 0.10 m", "offendingSceneKeys": ["예시카테고리_CR99_예시물체_99991"] }
```

### 출력 예시 B — 배치의 sceneKey 가 모두 서로 다름(같은 scene 쌍 없음), 위반 없음

배치가 99001, 99002, ..., 99008 처럼 전부 다른 scene 이면 R6-CHECK 는 한 줄도 쓰지
않는다(99001 → 99002 같은 인접 scene 비교는 계약 위반이다). 출력은 JSON 하나뿐이다:

```json
{ "triggered": false, "reason": "", "offendingSceneKeys": [] }
```
