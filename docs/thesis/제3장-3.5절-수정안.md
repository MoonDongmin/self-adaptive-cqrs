## 3.5 LLM 파이프라인 구현

제안 시스템은 하나의 애플리케이션 안에 이벤트 소싱·CQRS 영역, 관측 계층, LLM 영역을 각각 별도의 모듈로 구현하였다. 관리 대상 시스템의 모듈과 관리 시스템의 모듈은 서로를 직접 호출하지 않고 로그와 메시지 브로커를 통해서만 연결된다. 진단 파이프라인의 분석 부분은 로그 경로와 센서 경로 어느 쪽에도 속하지 않는 공통 라이브러리로 분리하고, 각 경로가 3.3.3항의 진단 도구를 넘겨주어 사용한다. 따라서 새로운 이상 신호의 경로를 추가하더라도 분석 부분은 변경되지 않는다. 구현에는 NestJS와 TypeScript, PostgreSQL, Apache Kafka를 사용하였고, LLM은 로컬 서버에서 구동되는 소형 모델을 OpenAI 호환 인터페이스로 호출하며, 모델과 운영 파라미터의 구체적인 값은 4.2절에서 기술한다. 본 절은 진단 파이프라인을 1차 선별, 분석 처리 흐름, 호출 규약과 응답 검증의 순서로, LLM의 판단과 규칙 기반 처리가 어떻게 배치되는지에 초점을 두어 설명한다.

**1차 선별.** 1차 선별은 로그 경로와 센서 경로에서 같은 구조를 따른다. 메시지 브로커에서 일정 건수의 배치를 읽고, 규칙 기반 사전 판정이 확실한 경우를 먼저 확정하며, 사전 판정으로 결론이 나지 않는 배치만 SLM이 판정한다. 로그 경로는 정상 적재 로그와 상관관계 식별자가 없는 프레임워크 로그를 먼저 걸러낸 뒤, 배치에 경고 이상의 레코드가 하나라도 있으면 SLM을 호출하지 않고 그 레코드의 상관관계 식별자를 이상으로 확정한다. 이 사전 판정은 초기 구현에서 SLM이 큰 배치 안의 경고 로그를 놓치는 경우가 관찰되어 도입되었다. 경고 이상이 없는 배치는 맥락 필드가 손실되지 않도록 원본 JSON 행 그대로 SLM에 전달되며, 판정 프롬프트는 요청 수신에서 정상 완료로 끝나는 궤적을 정상으로, 완료가 없는 순서 이상과 오류 응답, 동일 요청의 반복을 이상으로 정의하고 판단이 모호하면 이상으로 간주하도록 지시한다.

센서 경로의 사전 판정은 네 층의 규칙 기반 표시로 구성된다. 물리 층은 회전 행렬의 조건 위반처럼 단독으로 불가능한 값을, 정합성 층은 파지 성공으로 기록되었으나 이동량이 작업 공간을 벗어나는 모순을, 급변 층은 같은 장면에서 직전 시도 대비 정해진 폭을 넘는 변화를, 통계 층은 관측 분포에서 크게 벗어난 값을 표시한다. 표시가 없는 묶음은 SLM을 호출하지 않고 정상으로 확정되고, 표시가 있는 묶음만 SLM이 기준값 문서와 함께 해석하되, 물리·정합성 층의 위반은 SLM의 판정과 무관하게 이상으로 반영된다. 이상으로 판정된 묶음은 하나의 물리적 사건 단위로 모아 두었다가 정상 묶음이 이어지거나 일정 시간 입력이 없거나 상한 건수에 이르면 마감하고, 지목된 장면을 우선하여 상한 이내로 줄인 뒤 한 번만 진단 파이프라인으로 넘겨 같은 사건에 대한 문서의 반복 생성을 막는다. 규칙 기반 표시는 설정으로 끌 수 있어 SLM만으로 판정하는 방식과의 비교가 가능하며, 이는 제 IV 장의 비교 실험에 사용된다.

**분석 처리 흐름.** 1차 선별을 통과한 입력은 상태 그래프로 구현된 분석 처리 흐름에 전달된다. 상태 그래프는 처리 단계를 노드로, 단계 사이의 흐름을 간선으로 정의하고 모든 노드가 하나의 공유 상태를 읽고 쓰는 실행 모델이다. 공유 상태에는 입력(이상 로그 구간 또는 센서 판정 결과, 스키마 정보), 근본원인, 조치 결정, 생성 단계별 산출물, 최종 문서가 놓인다. 그림은 이 흐름을 LLM이 판단하는 구획과 규칙 기반 처리가 담당하는 구획으로 나누어 나타낸 활동 다이어그램이다. LLM이 판단하는 노드는 근본원인 분석, 조치 결정, 다섯 개의 생성 노드이며, 그 사이에 놓인 사전 판정, 동반 규칙, 검증과 합성, 문서 구성은 모두 규칙 기반 처리이다.

첫 노드인 근본원인 분석은 진단 에이전트가 담당한다. 진단 에이전트는 추론과 도구 호출을 번갈아 수행하는 ReAct 방식[25]으로 3.3.3항의 다섯 도구를 사용하며, 도구 호출 횟수와 전체 LLM 호출 횟수에 상한을 두고 상한에 이르면 지금까지의 근거로 최종 판정을 출력하라는 메시지를 주입한다. 출력은 이상 유형, 요약, 시간순 재구성, 실패한 요청의 의도, 의심되는 Read Model의 부족으로 구성되며, 이상 유형은 3.1절의 원칙에 따라 자유 형식이다.

조치 결정 노드는 근본원인으로부터 네 가지 조치 유형 가운데 최대 세 개를 고르되, LLM의 선택 앞뒤를 규칙 기반 처리가 감싼다. 선택 이전에는 사전 판정이 확실한 경우를 LLM을 호출하지 않고 확정한다. 기준 로그가 조회 실패 한 번뿐이면 조회 요구가 아직 드러나지 않았으므로 조치 불필요로, 적재 거절이면 결함 이벤트가 이벤트 스토어에 들어오지 않았으므로 격리 권고 단독으로 확정한다. 선택 이후에는 동반 규칙이 산출물(신규 Read Model 또는 버전 전환)이 선택되었는데 권고가 없으면 권고 문서를, 신규 Read Model이 선택되면 버전 전환을 강제로 동반시킨다. 조치의 근거가 분명한데 LLM이 빈 선택을 반환하면 모순을 지적하여 한 번 다시 요청하고, 그래도 비어 있으면 기준 로그별로 정해진 기본 조치로 대체한다.

산출물 생성 단계는 신규 Read Model, 투영 매핑, 권고 문서, 버전 전환, 데이터 품질 권고의 다섯 노드로 이루어지며, 실행 순서는 선택 결과에 따라 달라진다. 신규 Read Model이 선택되지 않았으면 선택된 노드를 병렬로 실행한다. 선택되었으면 신규 Read Model 노드와 투영 매핑 노드를 먼저 차례로 실행하여 설계를 확정하고, 확정된 설계를 입력받은 나머지 노드를 다음 단계에서 병렬로 실행한다. 병렬 실행만 사용하였던 초기 구현에서 가장 잦았던 결함이 노드마다 서로 다른 테이블명과 컬럼을 만들어 문서의 절이 서로 어긋나는 것이었으므로, 설계를 먼저 확정하고 나머지 노드가 이를 그대로 재사용하는 순서를 택하였다(3.3.3항). 마지막 문서 구성 노드는 LLM을 호출하지 않고 생성 산출물을 3.4절의 구성으로 배치한다.

**호출 규약과 응답 검증.** 진단 에이전트의 도구 호출 반복을 제외하면 모든 노드는 하나의 LLM 호출 규약을 공유한다. 시스템 메시지에는 노드의 역할, 판단 규칙, 출력 형식을 담은 역할 프롬프트가, 사용자 메시지에는 3.3.3항의 규칙으로 구성된 근거 텍스트가 놓인다. 모델은 자유로운 산문으로 추론한 뒤 마지막에 JSON 코드 블록을 출력하고, 파이프라인은 마지막 코드 블록만을 추출하여 노드별로 미리 정의된 출력 스키마로 검증한다. 출력 형식을 문법으로 강제하는 구조화 출력 기능 대신 이 방식을 택한 것은, 형식 강제가 소형 모델의 추론 품질을 떨어뜨린다는 보고[39]에 근거한다. 검증에 실패하면 같은 프롬프트를 다시 보내는 대신 직전 출력과 오류 내용을 대화에 덧붙여 모델이 자신의 오류를 보고 고치게 하는 재요청(re-ask)을 한 번 수행한다. temperature 0에서는 같은 프롬프트가 같은 실패를 그대로 재현하기 때문이다. 시간 초과와 같은 전송 실패는 별도의 예산으로 관리되어 재요청 예산을 소모하지 않는다. 그림은 진단 에이전트의 도구 호출 반복과, 그 뒤에 이어지는 공통 호출 규약(산문 추론, JSON 추출, 스키마 검증, 재요청)을 나타낸 시퀀스 다이어그램이다.

!fig3-10-seq-llm-invocation.png

스키마 검증은 응답 검증의 첫 단계일 뿐이며, LLM의 응답이 Docs에 실리기까지는 표에 정리한 일곱 단계를 거친다. 앞의 세 단계는 실패하면 재요청으로 되돌리고, 뒤의 네 단계는 LLM을 다시 호출하지 않고 규칙 기반 처리가 결과를 고치거나 대체하거나 보류한다.

| 단계 | 검증 내용 | 실패 시 |
| --- | --- | --- |
| ① 형식 | 출력 스키마 검증 (JSON 파싱, 항목 누락, 자료형, 명명 규칙) | 재요청 |
| ② 문자 오염 | 로컬 모델 특유의 한자 혼입 검사 | 재요청 |
| ③ 실행 가능성 | DDL을 실제 데이터베이스의 트랜잭션 안에서 실행 후 되돌림, 생성 코드의 실제 컴파일, payload 키·라우트·클래스명의 실재 | 재요청, 소진 시 ⑤ |
| ④ 근거 대조 | 인용된 관측 값과 매핑의 원천 필드가 근거 텍스트·스키마 정보에 실재 | 해당 행 제거, 근거가 없으면 출력 폐기 |
| ⑤ 규칙 기반 합성 | 검증된 필드·키로부터 DDL, ORM 스키마, 프로젝션 로직을 정해진 틀로 생성 | 틀로 교체, 얻을 수 없는 컬럼은 null과 TODO 표시 |
| ⑥ 완전성 검사 | 권고 없이 DDL·API만 남은 자기모순 | 대체 권고 생성, 불가 시 산출물 보류 |
| ⑦ 문서 형식 검사 | 머리말, 절 순서, 제약 조건, 출처 표시의 실재, 분량 한도 (3.4.4항) | 기록만 |

이 가운데 세 번째 단계의 실행 가능성 검증이 본 구현의 특징적인 부분이다. 생성된 DDL은 문법 검사가 아니라 실제 데이터베이스의 트랜잭션 안에서 실행된 뒤 되돌려지고, 생성된 프로젝션 로직과 스키마 코드는 저장소 소스를 복사한 임시 디렉터리에서 실제 컴파일러로 검사되며, 알려진 오류 유형에는 수정 힌트가 재요청 메시지에 함께 실린다. 이 단계는 "그럴듯하지만 실행되지 않는 SQL"이나 "payload에 없는 키를 읽어 모든 컬럼이 비는 프로젝션 로직"처럼 형식이 아니라 내용이 잘못된 출력을 잡으며, 재요청 뒤에도 남는 결함은 다섯 번째 단계의 규칙 기반 합성이 LLM이 확정한 필드와 키만 취하여 정해진 틀로 다시 만든다. 무엇을 만들지는 LLM이 판단하고 그것이 실행 가능한 형태로 완성되는 것은 규칙 기반 처리가 보장한다는 점에서, 이는 3.1절의 첫 번째 원칙을 구현 수준에서 구체화한 것이다.
