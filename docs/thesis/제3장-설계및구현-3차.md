# 제 III 장 Self-Adaptive CQRS 설계 및 구현

본 장에서는 제 II 장에서 확인한 연구 공백, 즉 Read Model의 설계 의사결정이 개발자의 수작업에 의존하는 문제를 완화하기 위해 제안하는 Self-Adaptive CQRS 아키텍처의 설계와 구현에 관해 설명한다. 3.1절에서는 제안하는 시스템의 전체 구조와 각 구성 요소 사이의 데이터 흐름에 관해 설명한다. 3.2절에서는 적응의 대상이 되는 이벤트 스토어와 목적별 Read Model의 구조를 다룬다. 3.3절에서는 1차 선별에서 Docs 생성에 이르는 진단 파이프라인의 구현을, 3.4절에서는 진단 파이프라인에 판단의 근거를 제공하는 LLM 컨텍스트의 구성을, 3.5절에서는 진단 파이프라인의 최종 산출물인 Docs의 구성을 상세히 설명하고, 3.6절에서는 제안하는 시스템을 MAPE-K 참조 모델에 대응시켜 자가 적응 루프로서의 구조를 분석한다.

## 3.1 Self-Adaptive CQRS 아키텍처

자가 적응 시스템 분야에서는 적응의 대상이 되는 기존 시스템을 관리 대상 시스템, 이를 관측하고 조정하는 별도의 계층을 관리 시스템이라 부른다[12]. 제안하는 시스템은 기존의 이벤트 소싱·CQRS 구조를 관리 대상 시스템으로 두고, 그 위에 LLM 기반의 분석 영역을 관리 시스템으로 결합한다. 관리 대상 시스템의 코드와 데이터 모델은 변경하지 않으며, 관리 시스템은 관리 대상 시스템이 운영 중에 남기는 로그와 데이터를 관측하여 Read Model의 재생성이 필요한 상황을 감지하고, 그 조치 방안을 단일 문서(이하 Docs)로 산출한다. 제안하는 시스템의 전체 구조는 네 가지 영역으로 구분된다.

첫 번째는 이벤트 소싱·CQRS 영역이다. 이 영역은 Physical AI 도메인의 로봇 파지 시도 데이터를 관리하는 기존 시스템으로, 쓰기 측의 적재 서비스와 이벤트 스토어, 읽기 측의 프로젝션과 조회 목적별 Read Model로 구성된다. 적재 서비스는 파지 시도 데이터를 검증하여 이벤트 스토어에 불변 이벤트로 기록하고, 프로젝션은 기록된 이벤트를 순서대로 읽어 Read Model에 반영한다. 이 영역의 각 구성 요소는 스키마에 정의되지 않은 필드의 유입, 검증 실패, 변환 실패와 같이 자신이 처리하지 못한 상황을 로그로 남긴다.

두 번째는 관측 계층이다. 관측 계층은 모든 구성 요소가 남기는 로그를 수집하여 관리 시스템에 전달하는 역할을 한다. 로그는 메시지 브로커와 로그 데이터베이스(이하 LogDB)로 동시에 전달되는데, 메시지 브로커는 실시간 선별의 입력이 되고 LogDB는 분석 시점에 이상의 앞뒤 상황을 조회하는 데 쓰인다. 프로젝션이 Read Model에 반영한 센서 값은 오류가 아닌 데이터이므로 로그와 별도로 전달된다. 관측 계층으로 유입되는 로그와 데이터 가운데 정상 동작에서 벗어난 것을 이상 신호라 한다.

세 번째는 본 논문에서 추가한 LLM 영역으로, 관리 시스템에 해당한다. LLM 영역은 이상 신호를 선별하고 분석하여 Docs를 생성하는 역할을 하며, 로그를 입력으로 하는 로그 경로와 센서 값을 입력으로 하는 센서 경로의 두 진입점을 갖는다. 두 경로는 각각 미리 정한 규칙과 SLM으로 이상 신호를 1차 선별하고, 선별된 신호에 대해서만 분석 처리를 수행한다. 분석 처리 과정은 LLM 기반의 진단 에이전트가 근본원인을 분석하고, 조치를 결정하며, 산출물을 생성하는 순서로 구성되고, 생성된 산출물은 검증을 거쳐 하나의 Docs로 구성된다. 1차 선별에서 Docs 생성까지의 흐름을 진단 파이프라인이라 한다. 진단 파이프라인에서 LLM은 어떤 이상이 왜 발생하였는지, 어떤 조치가 필요한지, 신규 Read Model의 컬럼을 어떻게 구성할지와 같이 도메인 이해와 생성 능력이 필요한 판단을 담당한다. SLM과 LLM은 모두 내부 서버의 로컬 모델로 구동되며, 로그, 이벤트, 소스 코드는 어떤 단계에서도 시스템의 경계를 벗어나지 않는다.

네 번째는 LLM 컨텍스트이다. LLM 컨텍스트는 진단 파이프라인에 판단의 근거를 제공하는 역할을 하며, LogDB와 Insight Read DB로 구성된다. LogDB는 시스템에서 무슨 일이 일어났는지를 담은 개발자의 구조화된 로그를 축적하고, Insight Read DB는 시스템이 무엇을 보유하고 있는지를 담은 이벤트와 Read Model의 스키마 정보를 관리한다. 두 정보는 분석을 시작할 때 진단 파이프라인에 미리 주입되거나, 진단 에이전트가 분석 도중 도구를 호출하여 직접 조회하는 두 방식으로 전달된다. 진단 에이전트는 이 밖에 센서 기준값 문서와 관리 대상 시스템의 소스 코드도 도구로 조회할 수 있다. [그림 5]는 제안하는 시스템의 전체 구조를 나타낸 구성도이다.

그림 5. Self-Adaptive CQRS 시스템 아키텍처

네 영역 사이의 데이터 흐름은 다음과 같다. 이벤트 소싱·CQRS 영역의 적재 서비스와 프로젝션이 남긴 로그는 관측 계층을 거쳐 메시지 브로커의 로그 토픽과 LogDB로 전달되고, 프로젝션이 반영한 센서 값은 센서 값 토픽으로 발행된다. LLM 영역의 로그 경로와 센서 경로는 각 토픽을 배치 단위로 읽어 1차 선별을 수행하고, 이상으로 판정된 신호에 대해 LogDB에서 이상의 앞뒤 로그를, Insight Read DB에서 스키마 정보를 가져와 분석 처리 과정에 전달한다. 분석 처리 과정이 생성한 Docs는 파일 시스템에 저장되며, 개발자가 이를 검토하고 승인하면 Docs에 담긴 DDL과 코드가 이벤트 소싱·CQRS 영역에 적용되어 신규 Read Model이 만들어진다. 시스템은 이 적용을 스스로 수행하지 않으며, 사람의 승인이 관리 시스템과 관리 대상 시스템 사이에 놓인 유일한 적용 경로이다. 승인과 함께 신규 Read Model의 스키마 정보가 Insight Read DB에 등록되어 다음 분석의 컨텍스트로 순환하며, 이 순환이 제안하는 시스템에서 자가 적응을 이루는 피드백 루프이다. [표 4]는 네 영역을 구성하는 요소와 이를 기술하는 절을 정리한 것이다.

## 3.2 이벤트 스토어와 목적별 Read Model

관리 대상 시스템은 Physical AI 도메인의 로봇 파지 시도 데이터를 이벤트 소싱·CQRS 구조로 관리한다. 데이터는 로봇이 물건을 파지하는 한 번의 시도를 하나의 JSON 파일로 기록한 것으로, 이미지·비디오의 파일명, 카메라 파라미터, 파지 포즈, 로봇의 자세, 파지 주석, 파지 성공 여부 등을 담는다. 파일명에는 대상 객체, 카메라 코드, 장면 번호, 시도 번호, 촬영 일자가 정해진 규약으로 기록되어 있으며, 적재 서비스는 여기서 장면 식별 키(scene key)와 시도 번호, 발생 시각을 추출한다. 하나의 장면은 하나의 이벤트 스트림에 대응하고, 각 시도는 스트림 안에서 시도 번호로 구분되는 하나의 이벤트가 된다. 이벤트 스토어는 모든 이벤트에 전역 순번을 부여하여 보관하며, 이 순번이 프로젝션의 진행 위치를 나타내는 기준이 된다.

쓰기 측의 적재 서비스는 파일마다 파일명 파싱, JSON 파싱, 스키마 변화 감지, 스키마 검증, 이벤트 추가의 순서로 동작한다. 스키마 검증은 미리 정의된 스키마에 따라 값의 형식을 확인하고 스키마에 없는 키를 제거하기 때문에, 새로운 센서가 추가되어 스키마가 알지 못하는 키가 유입되면 그 값은 이벤트 스토어에 기록되지 않는다. 이를 관측하기 위해 적재 서비스는 검증 이전의 원본에서 알려진 키 목록에 없는 최상위 키를 찾아, 배치가 끝날 때 새로운 키의 목록과 값의 표본을 담은 경고 로그를 남긴다. 이 로그가 제 I 장에서 문제로 정의한 "스키마에 정의되지 않은 필드의 유입"을 시스템이 스스로 관측하는 첫 번째 신호이다.

읽기 측에는 조회 목적별로 두 개의 Read Model이 놓인다. 하나는 장면별 파지 결과의 조회를 위한 read_grip_result이고, 다른 하나는 장면별 이미지·비디오 링크의 조회를 위한 read_multimodal이다. 두 Read Model은 장면 식별 키와 시도 번호를 기본 키로 공유하며, 각 행이 어느 이벤트에서 만들어졌는지 추적할 수 있도록 원천 이벤트의 전역 순번을 보존한다. [그림 6]은 관리 대상 시스템의 이벤트 스토어, Read Model, 프로젝션 커서와 관리 시스템이 사용하는 LogDB, Insight Read DB의 관계를 나타낸 데이터 모델이다.

그림 6. 관리 대상 시스템과 관리 시스템의 데이터 모델

프로젝션은 이벤트를 행으로 변환하여 저장하는 변환 로직과, 아직 반영되지 않은 이벤트를 순서대로 읽어 변환 로직에 적용하는 배치 반영 처리로 구성된다. 변환 로직은 Read Model마다 하나씩 두며, 저장된 행의 무결성 검사와 센서 값 추출은 필요한 Read Model에만 둔다. 배치 반영 처리는 Read Model별로 마지막에 반영한 순번을 기록해 두고, 그 이후의 이벤트를 일정 건수 단위로 읽어 변환·저장과 순번의 갱신을 하나의 트랜잭션으로 처리한다. 쓰기 측은 프로젝션의 진행과 무관하게 이벤트를 계속 기록하기 때문에 유입 속도가 반영 속도를 앞서더라도 쓰기는 지연되지 않으며, 프로젝션은 다음 실행에서 밀린 이벤트를 순서대로 반영한다. 변환할 수 없는 이벤트가 발견되면 오류 로그를 남기고 해당 배치 전체를 되돌린다. 이는 결함 이벤트를 건너뛰어 누락시키는 대신 순번을 멈추어 문제를 드러내고, 이후의 조치를 사람과 진단 파이프라인에 맡기기 위한 설계이다.

배치가 저장된 뒤에는 트랜잭션 밖에서 두 가지 후처리가 수행된다. 하나는 센서 값의 전달이다. read_grip_result에 새로 저장된 행에는 로봇이 파지를 시도할 때 측정된 값, 즉 파지 위치와 로봇 자세, 그리고 파지의 성공 여부가 담겨 있다. 프로젝션은 이 값들을 행마다 하나의 메시지로 만들어 메시지 브로커에 보내며, 3.3절의 센서 경로가 이를 가져가 측정값이 타당한지를 검사한다. 다른 하나는 저장된 행의 무결성 검사로, 예를 들어 read_multimodal은 미디어 파일명에 담긴 장면·시도 번호가 행의 키와 일치하는지를 검사하여 위반 시 오류 로그를 남긴다. 두 처리는 실패하더라도 저장된 Read Model에 영향을 주지 않는다. [그림 7]은 적재와 프로젝션의 처리 순서와 각 단계에서 이상 신호가 로그와 센서 값 토픽으로 나가는 지점을 나타낸 시퀀스 다이어그램이다.

그림 7. 적재와 프로젝션의 처리 순서 및 이상 신호 발생 지점

이 구조에서 주목할 점은 관리 대상 시스템이 관리 시스템의 존재를 알지 못한 채 동작한다는 것이다. 적재 서비스와 프로젝션은 처리 중에 발생한 문제를 로그와 메시지로 남길 뿐, 그것이 어디로 전달되어 어떻게 분석되는지에는 관여하지 않는다. 관리 시스템은 이 로그와 메시지를 메시지 브로커를 통해 받아 볼 뿐이므로, 분석이 느려지거나 멈추더라도 프로젝션은 영향을 받지 않는다. 이렇게 남겨진 로그와 메시지가 다음 절에서 설명하는 진단 파이프라인의 입력이 된다.

## 3.3 진단 파이프라인 구현

제안하는 시스템은 하나의 애플리케이션 안에 이벤트 소싱·CQRS 영역, 관측 계층, LLM 영역을 각각 별도의 모듈로 구현하였다. 관리 대상 시스템의 모듈과 관리 시스템의 모듈은 서로를 직접 호출하지 않고 로그와 메시지 브로커를 통해서만 연결된다. 진단 파이프라인의 분석 부분은 로그 경로와 센서 경로 어느 쪽에도 속하지 않는 공통 모듈로 분리하고, 각 경로가 진단 도구를 넘겨주어 사용한다. 따라서 새로운 이상 신호의 경로를 추가하더라도 분석 부분은 변경되지 않는다. 구현에는 NestJS와 TypeScript, PostgreSQL, Apache Kafka를 사용하였고, LLM은 로컬 서버에서 구동되는 소형 모델을 OpenAI 호환 인터페이스로 호출하며, 모델과 운영 파라미터의 구체적인 값은 4.2절에서 기술한다. 본 절에서는 진단 파이프라인을 1차 선별, 분석 처리 흐름, 호출 규약과 응답 검증의 순서로, LLM의 판단과 규칙 기반 처리가 어떻게 배치되는지에 초점을 두어 설명한다.

1차 선별은 로그 경로와 센서 경로 모두 규칙 기반 사전 판정 뒤에 SLM 판정을 두는 2단 구조이다. SLM은 한 번에 읽을 수 있는 입력 길이가 제한되어 있기 때문에, 메시지 브로커에 쌓인 로그를 한꺼번에 읽지 않고 일정 건수의 배치로 나누어 읽는다. 로그 경로는 먼저 배치에서 정상 적재 로그와 상관관계 식별자가 없는 로그를 제외한다. 남은 레코드 가운데 경고 이상의 수준을 가진 것이 하나라도 있으면, 로깅 규약에 따라 그 레코드 자체가 이미 이상 신호이므로 SLM을 호출하지 않고 곧바로 이상으로 판정한다. 이때 이상으로 판정된 것은 레코드 한 줄이 아니라 그 레코드가 속한 요청 전체이며, 요청을 식별하는 상관관계 식별자가 다음 단계인 로그 구간 조립에 전달된다. 이 사전 판정은 초기 구현에서 SLM이 큰 배치 안에 섞인 경고 로그를 놓치는 경우가 관찰되어 도입되었다. 경고 이상의 레코드가 없는 배치만 SLM에 전달된다. 이 경우 이상은 레코드 하나가 아니라 여러 레코드의 순서와 조합에서 드러나므로, 배치를 표로 요약하지 않고 원본 JSON 행 그대로 전달하여 판단에 필요한 필드가 사라지지 않게 한다. 판정 프롬프트는 요청 수신에서 정상 완료로 끝나는 흐름을 정상으로, 시작만 있고 완료가 없는 순서 이상, 오류 응답, 요청한 자원이 존재하지 않는 조회 실패, 동일 요청의 반복을 이상으로 정의하고, 판단이 모호하면 이상으로 간주하도록 지시한다.

센서 경로는 오류가 아닌 데이터 값에서 이상을 찾는 경로이기 때문에, 무엇이 비정상인지에 대한 도메인 지식이 필요하다. 제안하는 시스템은 이 지식을 두 형태로 받는다. 하나는 값의 타당성을 검사하는 규칙 기반 표시이고, 다른 하나는 SLM이 참고하는 기준값 문서이다. 규칙 기반 표시는 어느 도메인에서든 같은 네 층으로 구성된다. 첫째 층은 값 하나만으로 불가능함이 판정되는 위반, 둘째 층은 여러 값 사이의 모순, 셋째 층은 같은 대상에서 시간에 따른 급격한 변화, 넷째 층은 관측 분포에서의 통계적 이탈이다. 앞의 두 층은 도메인의 물리 법칙이나 값의 제약 조건에서 나오므로 위반이면 확정 이상이고, 뒤의 두 층은 정상일 수도 있는 변화이므로 SLM의 해석 대상이 된다. 파지 시도 데이터에서는 첫째 층에 회전 행렬의 직교성 위반이나 0 이하의 파지 깊이가, 둘째 층에 파지 성공으로 기록되었으나 이동량이 작업 공간을 벗어나는 모순이, 셋째 층에 같은 장면에서 직전 시도 대비 깊이의 급변이, 넷째 층에 분포에서 크게 벗어난 자세 값이 해당하며, 기준값 문서에는 각 값의 기대 범위와 분포 통계가 실린다. 다른 도메인에 적용할 때 바뀌는 것은 각 층에 들어가는 규칙과 기준값 문서의 내용뿐이고, 층의 구조와 SLM과의 역할 분담은 그대로 유지된다.

처리 순서는 표시가 없는 묶음은 SLM을 호출하지 않고 정상으로 확정하고, 표시가 있는 묶음만 SLM이 기준값 문서를 참고하여 판정하되, 첫째·둘째 층의 위반은 SLM의 판정과 관계없이 이상으로 처리한다. 센서 값의 이상은 여러 묶음에 걸쳐 이어지는 경우가 많으므로, 이상으로 판정된 묶음은 바로 분석하지 않고 하나의 사건으로 모아 둔다. 정상 묶음이 다시 나타나거나 일정 시간 새 입력이 없으면 사건이 끝난 것으로 보고 분석 처리 흐름으로 넘긴다.

1차 선별을 통과한 입력은 LangGraph[39]의 상태 그래프(StateGraph)로 구현된 분석 처리 흐름에 전달된다. LangGraph를 채택한 이유는 진단 파이프라인의 처리 구조가 단순한 순차 호출이 아니기 때문이다. 근본원인 분석 결과에 따라 어떤 산출물을 만들지가 실행 시점에 정해지고, 선택된 산출물 가운데 일부는 병렬로, 일부는 앞 단계의 결과를 받아 순서대로 만들어져야 하며, 각 단계는 앞 단계까지 쌓인 결과를 모두 볼 수 있어야 한다. 상태 그래프는 처리 단계를 노드로, 실행 순서를 간선으로 정의하고, 모든 노드가 하나의 공유 상태를 읽고 쓰는 실행 모델이므로 이러한 요구를 그대로 표현할 수 있다. 조건부 간선은 조치 결정의 결과에 따라 실행할 생성 노드를 고르고, 공유 상태의 산출물 항목은 병합 규칙을 두어 병렬로 실행된 노드의 결과가 서로 덮어쓰지 않고 합쳐지게 한다.

분석 처리 흐름은 근본원인 분석, 조치 결정, 산출물 생성, 문서 구성의 네 단계로 이어지며, 이하 각 처리 단계를 노드라 부른다. 공유 상태에는 입력(이상 로그 구간 또는 센서 판정 결과, 스키마 정보), 근본원인, 조치 결정, 생성 단계별 산출물, 최종 문서가 놓이고, 각 노드는 앞 노드가 공유 상태에 써 둔 결과를 읽어 자기 결과를 덧붙인다. [그림 8]은 이 흐름을 LLM 판단 구획과 규칙 기반 처리 구획으로 나누어 나타낸 활동 다이어그램이다. 그림에서 LLM이 판단하는 것은 왼쪽 구획의 근본원인 분석, 조치 결정, 다섯 개의 생성 노드뿐이며, 오른쪽 구획의 사전 판정, 동반 규칙, 검증과 합성, 문서 구성은 모두 규칙 기반 처리이다. 흐름은 두 구획을 번갈아 지나간다. 즉, LLM이 판단을 내면 규칙 기반 처리가 그 판단을 검사하고 빠진 것을 채운 뒤 다음 LLM 판단으로 넘기는 구조이며, 어느 LLM 노드가 실패하더라도 규칙 기반 처리가 정해진 기본값으로 흐름을 이어 가므로 문서가 통째로 비는 일은 없다.

그림 8. 분석 처리 흐름의 활동 다이어그램

각 노드의 역할은 다음과 같다. 근본원인 분석 노드는 진단 에이전트가 담당한다. 진단 에이전트는 추론과 도구 호출을 번갈아 수행하는 ReAct 방식[34]으로 [표 5]의 다섯 도구를 사용하여 LogDB, Insight Read DB, 센서 기준값 문서, 소스 코드를 직접 조회한다. 도구 호출 왕복은 4회, 최종 출력의 재요청은 2회를 상한으로 두고 상한에 이르면 지금까지 수집한 근거만으로 최종 판정을 출력하라는 메시지를 주입한다. 출력은 이상 유형, 요약, 시간순 재구성, 실패한 요청의 의도, 의심되는 Read Model의 부족으로 구성되며, 이상 유형은 미리 정하지 않고 에이전트가 자유롭게 명명한다.

표 5. 진단 에이전트의 도구

| 도구 | 역할 | 입력 |
|---|---|---|
| search_logs | LogDB 조회, 상관관계 식별자로 요청을 추가하거나 행위명·수준으로 반복 패턴 확인 | correlationId, action, sceneKey, minLevel, limit |
| list_insight_cards | 등록된 스키마 정보의 대상 이름 목록 조회 | 없음 |
| get_insight_card | 스키마 정보 한 항목의 M-Schema 표현 조회 | entityName |
| get_sensor_baseline | 센서 값의 규칙명·기대 범위·분포 통계를 담은 기준값 문서 조회 | 없음 |
| read_source_code | 소스 파일을 행 번호와 함께 열람 | filePath, startLine, endLine |

조치 결정 노드는 근본원인을 보고 네 가지 조치 유형(권고 문서, 신규 Read Model, API 버전 전환, 데이터 품질 권고) 가운데 무엇을 만들지를 고른다. LLM이 고르는 것은 이 선택뿐이고, 선택의 앞뒤는 규칙 기반 처리가 감싼다. 선택 이전의 사전 판정은 로그만 보아도 답이 정해지는 경우를 LLM을 호출하지 않고 확정하고, 선택 이후의 동반 규칙은 산출물이 선택되었으면 그 근거가 되는 권고 문서를, 신규 Read Model이 선택되었으면 API 버전 전환을 반드시 함께 선택되게 한다. 이상 신호가 분명한데 LLM이 아무것도 고르지 않으면 모순을 지적하여 한 번 다시 묻고, 그래도 비어 있으면 이상 신호의 종류별로 정해 둔 기본 조치로 대체한다. 이렇게 하면 Docs가 항상 세 요소를 갖춘다는 3.5절의 명세가 LLM의 선택에 흔들리지 않는다.

산출물 생성 단계는 신규 Read Model, 필드 매핑, 권고 문서, API 버전 전환, 데이터 품질 권고의 다섯 노드로 이루어지며, 조치 결정에서 선택된 노드만 실행된다. 실행 순서는 신규 Read Model이 선택되었는지에 따라 달라진다. 선택되지 않았으면 선택된 노드를 병렬로 실행하고, 선택되었으면 신규 Read Model 노드와 필드 매핑 노드를 먼저 차례로 실행하여 테이블명·키·필드 목록을 확정한 뒤, 확정된 설계를 입력으로 받은 나머지 노드를 병렬로 실행한다. 병렬 실행만 사용하였던 초기 구현에서 노드마다 서로 다른 테이블명과 컬럼을 만들어 문서의 절이 서로 어긋나는 결함이 가장 잦았으므로, 설계를 한 곳에서 먼저 확정하고 나머지 노드가 이를 그대로 재사용하는 순서를 택하였다. 마지막 문서 구성 노드는 LLM을 호출하지 않고 생성 산출물을 3.5절의 구성으로 배치하며, 권고 없이 산출물만 남은 경우에는 규칙 기반으로 대체 권고를 만들어 채우고 그것도 불가능하면 산출물을 보류한다.

LLM을 호출하는 일곱 노드는 모두 같은 호출 규약을 따른다. 모델은 역할 프롬프트와 근거 텍스트를 받아 산문으로 추론한 뒤 마지막에 JSON 코드 블록을 출력하고, 파이프라인은 이를 노드별 출력 스키마로 검증한다. 근본원인 분석 노드만 이 규약 앞에 도구 호출 루프가 추가되어, 모델이 필요한 도구를 요청하고 그 결과를 받는 과정을 반복한 뒤 최종 JSON을 출력한다. 구조화 출력 대신 이 방식을 택한 것은 형식 강제가 소형 모델의 추론 품질을 떨어뜨린다는 보고[40]에 근거하며, 검증에 실패하면 직전 출력과 오류 내용을 덧붙여 모델이 스스로 고치게 하는 재요청을 한 번 수행한다.

스키마 검증은 응답 검증의 첫 단계일 뿐이며, LLM의 응답이 Docs에 실리기까지는 [표 6]에 정리한 일곱 단계를 거친다. 앞의 세 단계는 실패하면 재요청으로 되돌리고, 뒤의 네 단계는 LLM을 다시 호출하지 않고 규칙 기반 처리가 결과를 고치거나 대체하거나 보류한다.

표 6. LLM 응답 검증의 일곱 단계

| 단계 | 검증 내용 | 실패 시 |
|---|---|---|
| ① 형식 | 출력 스키마 검증(JSON 파싱, 항목 누락, 자료형, 명명 규칙) | 재요청 |
| ② 문자 오염 | 로컬 모델 특유의 한자 혼입 검사 | 재요청 |
| ③ 실행 가능성 | DDL을 실제 데이터베이스의 트랜잭션 안에서 실행 후 되돌림, 생성 코드의 실제 컴파일, payload 키·라우트·클래스명의 실재 | 재요청, 소진 시 ⑤ |
| ④ 근거 대조 | 인용된 관측 값과 매핑의 원천 필드가 근거 텍스트·스키마 정보에 실재 | 해당 행 제거, 근거가 없으면 출력 폐기 |
| ⑤ 규칙 기반 합성 | 검증된 필드·키로부터 DDL, ORM 스키마, 프로젝션 로직을 정해진 틀로 생성 | 틀로 교체, 얻을 수 없는 컬럼은 null과 TODO 표시 |
| ⑥ 완전성 검사 | 권고 없이 DDL·API만 남은 자기모순 | 대체 권고 생성, 불가 시 산출물 보류 |
| ⑦ 문서 형식 검사 | 머리말, 절 순서, 제약 조건, 출처 표시의 실재, 분량 한도(3.5절) | 기록만 |

이 가운데 세 번째 단계의 실행 가능성 검증은 Text-to-SQL과 코드 생성 연구의 실행 기반 평가[13, 14, 32]를 생성 시점의 검증으로 옮긴 것이다. 생성된 DDL은 문법 검사가 아니라 실제 데이터베이스의 트랜잭션 안에서 실행된 뒤 되돌려지므로 관리 대상 시스템의 데이터는 변하지 않고, 생성된 프로젝션 로직과 스키마 코드는 저장소 소스를 복사한 임시 디렉터리에서 실제 컴파일러로 검사되며, 알려진 오류 유형에는 수정 힌트가 재요청 메시지에 함께 실린다. 이 단계는 "그럴듯하지만 실행되지 않는 SQL"이나 "payload에 없는 키를 읽어 모든 컬럼이 비는 프로젝션 로직"처럼 형식이 아니라 내용이 잘못된 출력을 잡으며, 재요청 뒤에도 남는 결함은 다섯 번째 단계의 규칙 기반 합성이 LLM이 확정한 필드와 키만 취하여 정해진 틀로 다시 만든다.

## 3.4 LLM 컨텍스트 모델

LLM은 대상 시스템의 상태, 스키마, 이력을 학습 과정에서 알 수 없기 때문에 판단에 필요한 정보를 실행 시점에 입력으로 제공받아야 한다. 이렇게 LLM에 제공되는 입력 정보 전체를 컨텍스트라 한다. 제안하는 시스템의 컨텍스트는 3.1절에서 소개한 개발자 Logging을 축적한 LogDB와 스키마 정보를 관리하는 Insight Read DB로부터 만들어진다. LogDB 기반 컨텍스트는 시스템에서 무슨 일이 일어났는지, 즉 이상 현상이 언제 어디서 발생하였고 그 앞뒤에 무엇이 있었는지를 알려준다. Insight Read DB 기반 컨텍스트는 시스템이 무엇을 보유하고 있는지, 즉 어떤 이벤트와 Read Model이 어떤 필드로 존재하는지를 알려주어, 그 이상 현상에 대응하여 어떤 Read Model을 어떤 컬럼으로 설계할지 판단할 때 대조할 스키마 지식이 된다. 3.4.1항과 3.4.2항에서 두 컨텍스트가 각각 어떻게 만들어지는지를 설명하고, 3.4.3항에서 두 컨텍스트가 진단 파이프라인의 각 노드에 전달되는 방식을 설명한다.

### 3.4.1 개발자 Logging 기반 컨텍스트

로그는 개발자가 시스템을 운영하면서 이미 남기고 있는 기록이다. 적재가 실패한 파일, 검증을 통과하지 못한 이벤트, 반복된 요청과 그 응답 코드는 모두 로그에 남으며, 개발자는 문제가 생긴 뒤 이 로그를 확인하여 원인을 찾는다. 제 I 장에서 정의한 두 문제 상황인 스키마에 없는 필드의 유입과 기존 Read Model로 답할 수 없는 조회 요구의 발생도 예외가 아니다. 본 논문에서는 로그가 담고 있는 이 정보를 사람이 나중에 읽는 대신 LLM이 곧바로 읽도록 한다. 즉, 로그를 사후에 오류를 추적하는 용도에서 시스템이 변화를 감지하고 조치 방안을 준비하는 컨텍스트 용도로 넓힌다. 이렇게 하면 관리 대상 시스템에 관측을 위한 코드를 새로 넣지 않고도 개발자가 이미 남기는 로그만으로 관리 시스템에 입력을 공급할 수 있다.

이를 위해 로그에 요구하는 것은 세 가지이다. 로그를 JSON 레코드로 남기고, 정상에서 벗어난 상황은 경고 이상의 수준으로 기록하며, 하나의 HTTP 요청에서 발생한 로그는 같은 상관관계 식별자를 갖도록 하는 것이다. 이 규약만 지켜지면 관리 시스템은 수준으로 이상 신호를 고르고, 식별자로 한 요청의 로그를 묶을 수 있다.

로그는 두 경로로 수집된다. 하나는 실시간 경로로, 로그가 메시지 브로커의 log-events 토픽에 쌓이고 3.3절의 로그 경로가 이를 배치 단위로 읽어 이상 여부를 1차 선별한다. 다른 하나는 축적 경로로, 로그 파일을 수집 서비스가 주기적으로 읽어 LogDB에 적재한다. 경로를 둘로 나눈 이유는 선별과 분석이 로그를 다르게 쓰기 때문이다. 1차 선별은 새로 들어온 로그가 도착한 순서대로 한 번씩만 읽으면 되므로, 로그를 순서대로 쌓아 두고 소비자가 꺼내 가는 메시지 브로커를 쓴다. 반면 분석은 이상이 난 시각을 기준으로 그 앞뒤의 로그를 봐야 하므로, 로그를 조회할 수 있는 LogDB에 축적한다.

1차 선별이 어떤 요청을 이상으로 판정하면 그 요청의 상관관계 식별자로 LogDB를 조회하여 이상 로그 구간을 만든다. 이것이 LLM에 실제로 입력되는 Logging 기반 컨텍스트이다. 로그 전체가 아니라 구간을 만드는 것은 로컬 모델의 입력 한도 안에 이상과 관련된 행만 남기기 위해서이며, 다음과 같이 이루어진다. 먼저 해당 식별자의 로그를 모두 가져와 요청의 크기를 얻고, 그 가운데 첫 번째 경고 이상 로그를 기준 로그로 삼는다. 기준 로그의 시간을 중심으로 앞뒤 20행씩을 더하는데, 여기에는 다른 요청의 로그도 섞여 있어 이상이 나기 직전에 시스템이 무엇을 하고 있었는지가 드러난다. 그다음 기준 로그 이전 1시간 동안의 행위명·수준별 발생 횟수를 집계하여 붙인다. 같은 조회 실패가 몇 번 반복되었는지는 구간 안의 행으로는 알 수 없고, 이 빈도가 단발성 실수와 실제 조회 요구를 구분하는 근거가 되기 때문이다. 완성된 구간은 빈도 집계와 로그 목록의 두 부분으로 정리되어 진단 파이프라인에 전달되며, Docs의 근거 블록에도 같은 형태로 실린다. [그림 9]는 로그가 수집되어 이상 로그 구간으로 조립되기까지의 과정을 나타낸 시퀀스 다이어그램이다.

### 3.4.2 Insight Read DB 기반 컨텍스트

로그는 시스템에서 무슨 일이 일어났는지를 알려주지만, 그 일에 어떻게 대응해야 하는지는 알려주지 않는다. 스키마에 없는 키가 버려졌다는 경고 하나로는 그 키가 어떤 의미의 값인지, 이미 있는 Read Model 가운데 그 값을 담기에 알맞은 것이 있는지, 없다면 어떤 컬럼으로 새 Read Model을 구성해야 하는지를 판단할 수 없다. 이 판단에는 시스템이 지금 어떤 데이터를 보유하고 있고 그 데이터가 어떤 모양인지에 대한 지식이 필요하다. 개발자라면 코드와 스키마 파일을 열어 확인할 지식을 LLM은 알지 못하므로 프롬프트에 담아 함께 넘겨야 하며, Text-to-SQL 연구들이 보여 주듯 LLM의 SQL 생성 품질은 이 스키마 정보를 프롬프트에 어떤 형태로 담느냐에 크게 좌우된다[14-17]. 본 논문에서는 이러한 시스템 지식을 LLM이 활용할 수 있는 형태로 관리하기 위해 Insight Read DB를 구성한다.

Insight Read DB는 시스템이 보유한 Read Model과 이벤트의 스키마 및 의미 정보를 저장하는 조회용 데이터베이스로, 크게 두 종류의 테이블로 구성된다. 첫 번째는 Read Model 또는 이벤트 자체를 기술하는 테이블로, 하나의 대상이 하나의 행에 대응하며 이름, 유형, 용도, 키 컬럼 등의 정보를 저장한다. 두 번째는 각 대상의 필드를 기술하는 테이블로, 하나의 필드가 하나의 행에 대응하며 필드명, 자료형, 의미, 실제 값의 예시를 저장한다.

데이터베이스가 이미 스키마를 알고 있는데도 이렇게 따로 적어 두는 이유는 두 가지이다. 첫째, 데이터베이스의 스키마에는 컬럼의 이름과 자료형만 있을 뿐 그 컬럼이 무엇을 뜻하는지는 없다. 본 논문이 사용하는 로컬 모델은 이름만으로 의미를 추론하는 능력이 약하기 때문에, 각 컬럼의 의미와 예시 값을 사람이 미리 적어 둔 정보가 프롬프트에 들어가야 한다. 둘째, 이벤트는 JSON 페이로드로 저장되어 있어 데이터베이스의 스키마에는 그 안의 구조가 드러나지 않는다. 그래서 이벤트의 스키마 정보는 페이로드 안에 중첩된 값까지 각각 하나의 필드로 펼쳐서 등록하며, 이를 Read Model과 같은 형식으로 나란히 두면 LLM은 두 스키마 정보를 대조하는 것만으로 이벤트에 있으나 어떤 Read Model에도 없는 필드를 찾아낼 수 있다. 이것이 신규 Read Model 설계의 출발점이 된다. 시스템을 처음 구축할 때는 두 Read Model과 이벤트 한 종의 스키마 정보를 개발자가 등록한다.

스키마 정보는 데이터베이스에 정형 테이블로 저장되지만, LLM에 보여줄 때는 그대로 넘기지 않는다. 진단 파이프라인이 프롬프트를 구성할 때 스키마 정보를 읽어 LLM이 읽기 좋은 텍스트로 바꾸어 넣는데, 이때 Text-to-SQL 연구에서 제안된 M-Schema 표현[16]을 따른다. M-Schema는 테이블을 (필드명: 자료형, 의미, 기본 키 여부, 예시 값)의 튜플 목록으로 기술하는 표현 방식으로, 컬럼의 의미와 예시를 함께 담아 LLM이 관련 컬럼을 찾는 정확도를 높이면서도 DDL 원문보다 토큰 소비가 적다. 저장 형식과 프롬프트 형식을 이렇게 분리하면 시스템은 조회하고 갱신하기 좋은 테이블을 쓰고 LLM은 읽기 좋은 텍스트를 받으며, 어느 한쪽을 바꾸어도 다른 쪽에 영향을 주지 않는다. 예를 들어 read_multimodal의 스키마 정보는 프롬프트에서 다음과 같은 형태가 된다.

```
## ReadModel: read_multimodal
용도: 장면별 2D 이미지·비디오 파일명 조회
키: (scene_key, attempt_num)
[
(scene_key:varchar, 장면 식별 키, Primary Key),
(attempt_num:smallint, 같은 장면 내 파지 시도 번호, Primary Key),
(occurred_at:timestamptz, 데이터 촬영 일자),
(image_2d_file_name:varchar, 2D 이미지 파일명),
(video_file_name:varchar, 비디오 파일명),
...
]
```

Insight Read DB는 LLM에 지식을 제공하는 것 외에 한 가지 역할을 더 한다. 제 I 장에서 문제로 정의한 상황 가운데 "기존 Read Model로 답할 수 없는 조회 요구의 발생"은 시스템 어디에서도 오류로 나타나지 않는다. 사용자가 원하는 데이터가 없다는 사실을 시스템이 알 방법이 없기 때문이다. 제안하는 시스템은 이를 Insight Read DB에서 잡아낸다. 사용자가 어떤 데이터를 조회하고 싶을 때 먼저 그 이름으로 스키마 정보를 찾아보게 하고, 해당 스키마 정보가 없으면 시스템은 경고 로그를 남긴다. 이 로그는 LLM의 프롬프트에 들어가므로, LLM은 사용자가 무엇을 조회하려다 실패했는지를 읽을 수 있다. 같은 이름의 조회 실패가 반복되면 단발성 오타가 아니라 그런 데이터를 원하는 요구가 실제로 있다는 뜻으로 해석된다. 이와 별도로, 스키마 정보와 실제 데이터베이스가 어긋나는 것도 감시한다. 개발자가 새 Read Model을 만들고 스키마 정보의 등록을 잊으면 LLM은 그 Read Model의 존재를 모른 채 판단하게 되므로, 시스템은 주기적으로 데이터베이스의 실제 테이블 목록과 등록된 스키마 정보를 대조하여 스키마 정보가 없는 Read Model 테이블이 있으면 경고 로그를 남긴다.

마지막으로 Insight Read DB는 적응이 일어날 때마다 그 결과가 등록되는 곳이다. 진단 파이프라인이 신규 Read Model을 제안하면, 그 Read Model의 스키마 정보를 등록하는 SQL이 테이블 생성 DDL과 함께 Docs에 실린다. 개발자가 Docs를 승인하고 두 SQL을 실행하면 새 Read Model이 만들어지는 동시에 그 스키마 정보가 Insight Read DB에 추가되고, 다음 분석부터 LLM은 이 Read Model을 이미 있는 것으로 알고 판단하게 된다.

### 3.4.3 컨텍스트 조합 및 주입 전략

진단 파이프라인은 컨텍스트를 두 가지 방식으로 전달받는다. 하나는 분석을 시작할 때 필요한 정보를 미리 넣어 주는 사전 주입이고, 다른 하나는 진단 에이전트가 분석 도중 필요한 정보를 3.3절의 도구로 직접 조회하는 도구 조회이다. 사전 주입은 모든 분석에 공통으로 필요한 최소한의 컨텍스트를 일정한 비용으로 보장하고, 도구 조회는 이상의 유형에 따라 달라지는 추가 근거를 필요할 때만 가져온다.

사전 주입에서는 이상이 감지된 로그 구간 또는 센서 이상 판정 결과 가운데 하나와 Insight Read DB의 스키마 정보 전체가 입력된다. 스키마 정보를 관련성에 따라 선별하지 않고 전부 주입하는 이유는 신규 Read Model을 설계할 때 기존 Read Model 전체와 대조해야 하기 때문이다.

파이프라인 안에서는 3.3절의 처리 단계마다 서로 다른 컨텍스트가 구성된다. 근본원인 분석 단계는 로그 구간 또는 센서 판정 결과를 근거로 받고 도구 조회로 이를 보강한다. 조치 결정 단계는 근본원인 분석 결과에 로그 구간과 스키마 정보를 더하여 받는다. 산출물 생성 단계는 여기에 기존 프로젝션 로직·스키마·컨트롤러의 소스 코드 발췌를 추가로 받아, 생성되는 코드가 실제 코드의 형식과 스타일을 따르도록 한다. 신규 Read Model이 선택된 경우에는 3.3절에서 설명한 순서에 따라 먼저 확정된 설계(테이블명, 키, 필드 목록, DDL)가 이후의 권고 문서, API 버전 전환, 데이터 품질 단계에 "확정된 설계이므로 그대로 재사용하라"는 안내와 함께 입력된다.

컨텍스트 구성에는 두 가지 규칙이 적용된다. 첫째, LLM에 입력되는 스키마 정보에서 예시 값을 제거하고, 예시 값을 실제 값처럼 인용하지 말라는 주의를 덧붙인다. 예시 값이 포함되면 로컬 모델이 이를 실제 관측 값으로 오인하여 SQL의 조건절에 사용하는 오류가 관찰되었기 때문이다. 둘째, 컨텍스트의 각 요소에는 상한을 둔다. 로그 구간 80행, 센서 분석 입력 16건, 도구 결과 4,000자, 소스 열람 120행의 상한은 로컬 모델의 입력 한도 안에 가장 관련성이 높은 근거가 남도록 정한 값이다. ## 3.5 단일 산출물 Docs 설계

진단 파이프라인의 최종 산출물은 하나의 마크다운 문서인 Docs이다. Docs는 두 가지 요구를 동시에 만족하도록 설계되었다. 하나는 개발자가 이 문서만 읽고 곧바로 Read Model을 재생성할 수 있어야 한다는 요구이고, 다른 하나는 이 문서가 다시 로컬 LLM의 입력으로 쓰일 수 있어야 한다는 요구이다. 후자 때문에 Docs는 고정된 구성과 분량 한도를 가진다. 문서는 맨 앞의 머리말(YAML front-matter), 제목과 한 문장 결론, 근거 블록, 세 개의 필수 절, 선택 절, 맨 끝의 제약 조건 순으로 구성되며, 이 순서와 절 제목은 문서마다 동일하다. 결론을 맨 앞에, 제약 조건을 맨 끝에 두는 배치는 긴 입력의 중간에 놓인 정보를 LLM이 잘 활용하지 못하는 현상[35]에 대응한 것이다. 문서의 조립은 LLM이 아니라 3.3절의 문서 구성 노드가 규칙 기반 처리로 수행하며, 이 단계에서 LLM의 요약이나 재작성은 일어나지 않는다. ### 3.5.1 Read Model 재생성 권고 문서

권고 문서는 어떤 Read Model을 왜 재생성하거나 보강해야 하는지에 대한 근거와 판단을 담는다. 이 절은 소프트웨어 설계 결정을 배경, 검토한 대안, 결정, 결과의 순서로 남기는 아키텍처 의사결정 기록[36]의 구조를 따라 Status, Context, Decision Drivers, Considered Options, Decision Outcome, Consequences, Non-Goals의 항목으로 구성된다. 이 구조를 채택한 이유는 권고가 하나의 결론만 제시하는 데 그치지 않고 기각된 대안과 그 장단점까지 함께 남겨야 개발자가 LLM의 판단을 검토하고 필요하면 다른 선택을 할 수 있기 때문이다.

Context에는 근거가 되는 로그 행이 수준, 행위명, 인용문, 해석의 형태로 나열되며 각 항목은 `[corr:<상관관계 식별자>]` 형식으로 출처를 밝힌다. 이 출처 표시는 로그를 근거로 삼는 오류를 사후 검사에서 잡아낼 수 있다. Considered Options에는 두 개 이상의 대안이 접근 방식, 제안 필드, 장단점, 코드 조각과 함께 제시되고, Decision Outcome은 채택된 대안과 그 이유를 서술한다.

권고 문서는 이상의 유형에 따라 세 형태로 나뉜다. 첫째, 신규 Read Model이 함께 선택된 경우 Decision Outcome은 확정된 설계의 채택을 서술하고 제안 필드는 그 설계의 필드와 일치한다. 둘째, 적재 거절이나 변환 불가 이벤트처럼 원천 데이터의 결함이 원인인 경우 권고 문서는 단독으로 생성되며 격리 SQL을 동반한다. 격리 SQL로 허용되는 것은 결함 이벤트를 찾아내는 조회, 오염된 Read Model 행을 무해하게 만드는 갱신 또는 삭제, 결함 이벤트가 이벤트 스토어에 들어오지 않았음을 확인하는 조회의 세 형태이다. 프로젝션 커서를 임의로 옮겨 결함 이벤트를 건너뛰는 SQL은 겉으로는 오류가 사라진 것처럼 보이지만 정합성을 조용히 훼손하므로 생성하지 않는다. 셋째, 센서 경로에서 발생한 데이터 품질 이상의 경우 권고는 아키텍처 의사결정 기록 대신 데이터 품질 권고의 형태를 취한다. 이 형태는 심각도와 그 근거, 근거 목록, 영향 범위, 근본원인의 경로, 단계별 대안으로 구성된다. 근거 목록의 각 항목은 장면 키, 시도 번호, 전역 순번, 영향 컬럼, 관측 값, 기준값 규칙으로 기대 값과 실측 값의 차이를 기술하고, 근본원인의 경로는 센서의 물리적 불가능, 프로젝션 결함, 기준값의 노후화 가운데 하나로 판정되며, 대안은 격리, 수정, 강화의 세 단계로 제시된다.

### 3.5.2 Read Model 생성 SQL

두 번째 절은 신규 Read Model을 실제로 만드는 데 필요한 것들을 담는다. 첫머리에는 아래의 변경이 사람의 승인 후에만 적용된다는 실행 안내문이 고정되고, 이어서 대상 테이블명과 키 컬럼, 테이블과 인덱스를 만드는 DDL, 그리고 각 컬럼의 이름·자료형·의미를 근거 블록과 같은 M-Schema 형식으로 적는다. 분량이 큰 코드는 선택 절로 보낸다.

이 절의 내용은 LLM이 출력한 설계(테이블명, 키 컬럼, 필드 목록)와 DDL, 프로젝션 로직에서 온다. LLM 출력은 그대로 실리지 않고 3.3절의 검증 단계에서 세 가지를 확인한다. 설계가 대상 시스템의 명명 규칙을 따르고 스스로 모순되지 않는지, DDL과 코드가 실제 데이터베이스와 컴파일러에서 실행되는지, 그리고 프로젝션 로직이 읽는 이벤트 필드가 실제 이벤트에 있는지이다. 확인에 실패하면 오류를 보여주고 다시 한 번 요청한다. 그래도 실패하는 것은 설계는 맞는데 그것을 SQL이나 TypeScript로 옮기는 과정에서 생긴 오류이므로, 이때는 LLM이 낸 코드를 버리고 검증을 통과한 설계를 템플릿에 넣어 규칙 기반 처리가 DDL과 프로젝션 로직을 직접 만들어 넣는다. 설계만 정확하면 코드는 규칙대로 만들 수 있기 때문이다. 이렇게 하면 LLM에는 어떤 테이블과 컬럼이 필요한지의 판단만 남고, 문서의 DDL과 컬럼 목록은 항상 같은 설계에서 나오므로 서로 어긋나지 않는다.

DDL만으로는 빈 테이블이 만들어질 뿐이므로 두 가지가 함께 실린다. 하나는 투영 매핑 명세로, 이벤트의 어떤 필드가 어떤 컬럼으로 들어가는지를 표로 적는다. 3.3절의 필드 매핑 노드가 확정된 설계를 보고 만들되, 컬럼이 설계에 있고 이벤트 필드가 근거 블록에 실제로 등장하는 행만 남긴다. 다른 하나는 스키마 정보 등록 SQL로, 실제의 테이블명·용도·키·필드 목록이 Insight Read DB의 저장 구조와 같으므로 LLM 없이 규칙 기반 처리가 INSERT 문으로 바꾼다. 개발자가 DDL과 이 INSERT를 함께 실행하면 신규 Read Model의 스키마 정보가 Insight Read DB에 등록되어 다음 분석의 컨텍스트로 순환한다. 3.1절에서 자가 적응의 피드백 루프라고 한 순환은 이 SQL로 이루어진다.

### 3.5.3 API Versioning 전략

세 번째 절은 Read Model의 교체가 조회 API에 미치는 변경을 다룬다. API 버전 전환의 원칙은 기존 자산을 건드리지 않는 것이다. 신규 Read Model은 기존 테이블을 고치는 대신 버전을 붙인 새 테이블로 만들고, 이를 채우는 프로젝션 로직과 조회 라우트도 새 버전으로 추가한다. 본 구현에서는 테이블에 _v2, 프로젝션 로직에 V2, 라우트에 /v2/를 붙인다. 이는 새 버전을 기존 버전 옆에 준비해 두고 검증 후 트래픽을 옮기는 블루-그린 배포[37]를 Read Model 수준에 적용한 것으로, 이벤트 재생으로 새 테이블을 채워 검증하고 전환하며 문제가 생기면 즉시 되돌릴 수 있다.

절의 본문은 실행 안내문 뒤에 변경 이력, 마이그레이션 절차, 사유와 호환성, 변경 파일 목록으로 구성된다. 변경 이력은 Keep a Changelog 형식[38]을 따라 Unreleased 항목 아래 Added, Changed, Deprecated, Removed, Fixed, Security의 범주로 기록하고, 마이그레이션 절차는 기존 클라이언트에 영향이 없는 변경과 기존 클라이언트를 깨뜨리는 변경을 나누어 적으며, 전환 전에 확인할 테스트와 문제가 생겼을 때 되돌리는 조건을 함께 제시하고, 신규 Read Model이 동반된 경우 스키마 정보 등록 단계가 추가된다. 신규 Read Model이 함께 선택된 경우 확정된 설계를 입력으로 받아 생성된다. 두 단계가 같은 것을 따로 만들면 한 문서 안에서 테이블명, 클래스명, 라우트가 서로 어긋나므로, 코드 변경의 라우트와 클래스명이 확정 설계와 일치하는지 검사하여 어긋나면 다시 요청하고, 확정 설계가 이미 만든 파일을 다시 만든 항목은 제거한다. LLM 호출이 끝내 실패하더라도 신규 Read Model이 확정되어 있으면 이 절을 비우지 않고 확정 설계에서 파이프라인이 변경 이력과 절차를 만들어 채운다. API 버전 전환이 선택되지 않은 문서에서는 권고 문서가 서술한 API 버전 영향이 실리고, 그것도 없으면 근거 부족 표시로 대체된다.

## 3.6 MAPE-K 관점의 자가 적응 루프 분석

본 절에서는 제안하는 시스템을 자가 적응 시스템의 참조 모델인 MAPE-K에 대응시켜, 제안하는 시스템이 자가 적응 루프로서 어떤 구조를 갖는지 분석한다. MAPE-K는 관리 대상 시스템을 관측하는 Monitor, 적응이 필요한지 판단하는 Analyze, 대응 방안을 세우는 Plan, 방안을 적용하는 Execute의 네 단계와, 네 단계가 함께 참조하는 지식(Knowledge)으로 구성된다. [표 8]은 각 단계에 대응하는 제안 시스템의 구성 요소와 그 단계의 판단을 누가 내리는지를 정리한 것이다.

표 8. MAPE-K 단계별 제안 시스템의 구성 요소와 판단 주체

| MAPE-K 단계 | 제안 시스템의 구성 요소 | 판단 주체 |
|---|---|---|
| Monitor | 로깅 규약과 이상 신호(3.4.1항), 로그의 실시간 경로와 LogDB 경로, 센서 값 채널, 등록 누락 감시 | 규칙 기반 처리 |
| Analyze | 1차 선별(사전 판정과 SLM 판정), 진단 에이전트의 근본원인 분석 | 규칙 기반 처리와 SLM, 진단 에이전트 |
| Plan | 조치 결정, 산출물 생성 노드 5종, 응답 검증, 문서 구성 | LLM(설계 판단)과 규칙 기반 처리(검증·합성·구성) |
| Execute | Docs의 검토와 승인, DDL 실행, 프로젝션 로직 추가, 이벤트 재생, 스키마 정보 등록, API 버전 전환 | 사람 |
| Knowledge | Insight Read DB(스키마 정보), LogDB(이력), 센서 기준값 문서, 기존 소스 코드 | — |

Monitor 단계는 전부 규칙 기반 처리이다. 통상의 자가 적응 시스템은 관리 대상 시스템에 관측을 위한 센서와 조치를 위한 실행기를 새로 붙이지만, 제안하는 시스템은 관리 대상 시스템이 이미 남기고 있는 로그와 데이터를 그대로 센서로 쓴다. 로깅 규약을 지키는 것만으로 관측이 이루어지기 때문에 관리 대상 시스템의 코드와 데이터 모델은 변경되지 않는다. 이는 기존 시스템을 고치지 않고 그 위에 관리 시스템을 얹는다는 전제가 MAPE-K의 Monitor 단계에서 어떻게 지켜지는지를 보여 준다.

Analyze 단계는 두 층으로 나뉜다. 1차 선별은 모든 배치에 대해 실행되므로 규칙 기반 처리와 SLM만으로 비용을 낮추고, 근본원인 분석은 1차 선별을 통과한 소수의 신호에 대해서만 도구 호출을 동반하는 진단 에이전트가 수행한다. 전통적인 접근에서 Analyze는 미리 정한 규칙이나 모델에 대한 위반을 탐지하는 것으로 구현되지만, 제안하는 시스템의 Analyze는 이상의 유형을 미리 정하지 않고 진단 에이전트가 자유롭게 명명하며 근본원인을 자연어로 설명한다. 어떤 이상이 올지 설계 시점에 다 알 수 없다는 점이 이 선택의 이유이다.

Plan 단계는 제안하는 시스템이 전통적인 자가 적응 기법과 가장 다른 지점이다. Rainbow[28]와 같은 기존 접근에서 Plan은 설계 시점에 미리 만들어 둔 적응 전략 가운데 하나를 고르는 일이다. 반면 제안하는 시스템의 Plan은 신규 Read Model의 스키마와 DDL, 프로젝션 로직, API 버전 전환 절차처럼 설계 시점에 미리 만들어 둘 수 없는 것을 실행 시점에 생성한다. 다만 무엇을 만들 것인가의 선택은 네 가지 조치 유형 안에서만 이루어진다. 따라서 제안하는 시스템의 적응 범위는 조치의 종류는 고정되어 있고 조치의 내용은 열려 있는 이중 구조를 갖는다. 이 구조 안에서 LLM의 판단은 앞뒤로 사전 판정, 동반 규칙, 응답 검증에 둘러싸여 있고, 검증을 통과하지 못한 판단은 규칙 기반 합성으로 대체되거나 보류된다. 즉, 열려 있는 부분은 LLM이 채우되 그 결과가 실행 가능한 형태로 완성되는 것은 규칙 기반 처리가 보장한다.

Execute 단계는 자동화하지 않는다. 제안하는 시스템은 생성한 DDL과 코드를 스스로 적용하지 않고 Docs로 산출하는 데서 멈추며, 적용은 사람이 이 문서를 검토하고 승인한 뒤에 수행한다. 사람이 개입하는 자리는 Plan과 Execute 사이의 경계이다. 이 자리를 사람에게 남긴 이유는 두 가지이다. 하나는 LLM이 생성한 스키마가 문법적으로 유효하고 실행 가능하더라도 도메인의 관점에서는 부적절할 수 있고[24], 이를 판단할 최종 권한은 도메인을 아는 사람에게 있어야 한다는 점이다. 다른 하나는 DDL의 적용과 API 버전 전환이 되돌리기 어려운 변경이라는 점으로, 이를 자동으로 적용하면 LLM 판단의 오류가 데이터 계층으로 번진다. 제안하는 시스템은 이 위험을 기존 자산을 보존하는 버전 전략과 사람의 승인으로 통제한다. 사람이 개입하는 두 번째 자리는 Knowledge의 갱신이다. 신규 Read Model의 스키마 정보는 사람이 DDL과 함께 등록하며, 시스템은 등록을 빠뜨렸을 때 이를 감지하여 알릴 뿐 Insight Read DB를 스스로 고치지 않는다.

Knowledge는 제안하는 시스템에서 자가 적응을 한 번으로 끝나지 않고 반복되게 만드는 요소이다. 전통적인 접근에서 지식 베이스는 아키텍처 모델과 정책으로 구성되어 설계 시점에 대부분 확정되지만, 제안하는 시스템의 Insight Read DB는 적응의 결과로 갱신된다. 한 번의 루프에서 만들어진 신규 Read Model의 스키마 정보가 등록되면, 다음 루프의 Analyze와 Plan은 이를 기존 자산으로 인식하여 같은 조회 요구에 대해 새 설계를 만드는 대신 기존 Read Model을 쓰도록 판단한다. 이 순환은 자율 컴퓨팅이 제시한 자기 구성(self-configuration)의 성질[9]을 Read Model의 생성과 진화 단계에서 구현한 것이다.
