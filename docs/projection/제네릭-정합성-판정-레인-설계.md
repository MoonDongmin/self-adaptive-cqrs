# 제네릭 정합성 판정 레인 설계

> 짝 문서: [`docs/llm-context/구현가이드-센서값-이상관찰자.md`](../llm-context/구현가이드-센서값-이상관찰자.md) — grip 센서 값 축의 이상 관찰자.
> 1차 출처(충돌 시 우선): `data/research/page1.png ~ page5.png`.

## 0. 한 줄 요약

**"어떤 Read Model이든, 투영된 행이 자기 도메인 정합성 규칙을 위반하면 표준 에러 로그로 방출하고, 기존 로그 레인이 그 로그를 받아 근본원인·권고 문서를 낸다."**
Projector 인터페이스에 선택적 훅 `checkIntegrity?` 하나를 추가하는 것으로, 배관은 한 번만 만들고 새 Read Model은 규칙만 꽂으면 되게 한다.

## 1. 문제 — 왜 지금은 multimodal 이상이 안 잡히는가

기존 이상 탐지는 **두 레인**뿐이고, 둘 다 특정 신호에만 반응한다.

| 레인 | 입력 | 잡는 것 | 대상 |
| --- | --- | --- | --- |
| **로그 레인** (`prejudge`) | 앱 로그 | `level>=40`·`4xx`·miss·순서/반복 이상 | 모델 불문 |
| **센서 값 레인** (`observeSensorBatch`) | 투영된 grip 값 vs 베이스라인 | 구조는 맞지만 물리적으로 틀린 값 | **grip-result 전용** |

Read Model 문제는 성격이 둘로 갈린다.

- **A. 구조적 붕괴** — `toyDataSchema.parse` 실패 → `map()`이 throw. 이미 `MAP_FAILED`/`DB_ERROR` error 로그로 **로그 레인에 흘러간다**(별도 조치 불필요).
- **B. 의미적 값 오류** — 구조(zod)는 통과하고 값만 틀림. **예외가 나지 않으므로** catch로는 영원히 못 잡는다. 오직 "값 판정 규칙 + 대조 judge"로만 잡히는데, 그게 **grip 센서 값 축에만** 구현돼 있다.

multimodal의 값 정합성 오류(예: 한 모달 미디어가 **다른 scene/attempt를 가리키는** 파일명)는 전형적인 **B**다. `2D_image_file_name`/`video_file_name`이 `z.string()`을 통과하므로(`src/insert/dto/toy-data.dto.ts:87,89`) 예외도 에러 로그도 없고, multimodal은 센서 값을 발행하지 않아 값 레인에도 진입하지 못한다. 결과적으로 **어느 레인에도 걸리지 않는 사각지대**다.

> **도메인 규약 주의(toy-data 139건 전수 확인).** 이 도메인에서 파일명 attempt 규약은 모달별로 다르다 — **2D 이미지는 attempt 단위**(파일명 attempt == event attempt_num), **video는 scene 단위 sentinel(항상 `_00_`)** 로 모든 attempt가 공유한다. 따라서 video의 `_00_`는 **정상**이며, 정합성 규칙은 video attempt를 event와 대조하면 안 된다(그러면 정상 데이터 전부가 오탐된다).

> 핵심: multimodal은 "판정을 잘못" 당한 게 아니라 **판정 대상에 오르지도 못했다.**

## 2. 핵심 아이디어 — 신호 방출로 일반화

이 시스템의 철학은 예외 catch가 아니라 **"신호를 방출하면 비동기 judge가 관찰한다"**이다. 센서 레인이 이미 그 형태다(projector가 값을 발행 → 관찰자가 베이스라인과 대조). 이를 **일반화**한다:

> 각 projector가 **자기 도메인 규칙으로 자기 이상을 검사**하고, 위반을 **표준 에러 로그**로 방출한다. 그러면 이미 존재하는 로그 레인(1차 게이트 → 분석 그래프 → 권고 문서)이 **모델 불문**으로 그것을 처리한다.

새 이상 채널(Kafka 토픽·컨슈머·모델별 judge·베이스라인 판정기)을 만들지 않는다. **에러 로그 방출**만으로 기존 파이프라인을 재사용한다.

## 3. 계약 (contract)

### 3.1 `IntegrityViolation` — 위반 1건의 근거

`src/projection/projector/projector.ts`

```ts
export type IntegrityViolation = {
  readModelName: string;   // 대상 Read Model 테이블명(예: read_multimodal) — Insight 카드와 매칭
  sceneKey: string;
  attemptNum: number;
  streamId: string;
  globalSeq: number;
  ruleName: string;        // 위반한 규칙 이름
  affectedColumns: string[]; // 오염된 Read Model 컬럼
  observedValue: string;   // 실제 관측된(위반한) 값 — 근거
  expected: string;        // 규칙이 기대한 값/범위
  detail: string;          // 사람이 읽는 자족적 한 문장(로그 msg 로 방출)
};
```

### 3.2 `Projector.checkIntegrity?` — 제네릭 확장점

```ts
export interface Projector<Insert> {
  readonly name: string;
  map(event: EventStoreEventRow): Insert;
  upsert(tx: DrizzleTx, row: Insert): Promise<void>;
  toSensorValueMessages?(rows: Insert[], events: EventStoreEventRow[]): SensorValueMessage[];

  // 선택: 투영된 행이 이 Read Model 의 도메인 정합성 규칙을 위반하는지 검사한다.
  // 미구현 프로젝터는 검사를 건너뛴다(프로젝터-불문 유지).
  checkIntegrity?(row: Insert, event: EventStoreEventRow): IntegrityViolation[];
}
```

`toSensorValueMessages?`와 정확히 같은 "선택적 훅 + CatchUpRunner가 커밋 후 호출" 패턴이다(검증된 기존 패턴의 반복 적용).

### 3.3 표준 로그 상수

`src/shared/logger/logging-context.ts`

- `LogAction.PROJECTION_INTEGRITY_VIOLATION = "projection.integrity.violation"`
- `LogContext`: `READ_MODEL_NAME`, `RULE_NAME`, `AFFECTED_COLUMNS`, `OBSERVED_VALUE`, `EXPECTED`

### 3.4 방출 지점 — `CatchUpRunner` (배관, 1회)

`src/projection/runner/catch-up.runner.ts` — 커밋·센서 발행 후 `emitIntegrityViolations(projector, rows, events)`.

- `checkIntegrity` 미구현 프로젝터는 즉시 return (프로젝터-불문 유지).
- 위반마다 `logger.error(...)` 방출: `action=PROJECTION_INTEGRITY_VIOLATION`, level 50, `msg=violation.detail`.
- 검사 자체의 예외는 삼킨다(투영은 이미 커밋됨 — best-effort).

> **왜 `detail`(msg)에 다 담는가.** 분석 그래프가 LLM에 렌더하는 이상 로그 윈도우는 `time·level·action·correlation_id·msg`만 보여준다(`src/analysis/render.ts:34-40`, `LogWindowRepositoryImpl.ROW_COLUMNS`). 구조화 필드는 `log_event` 컬럼에 남지만 **LLM에게 도달하는 건 msg뿐**이므로, 위반 근거를 `detail`에 자족적 문장으로 합쳐 싣는다.

## 4. 종단 흐름 (end-to-end)

```
POST /projection/multimodal
  → CatchUpRunner.run(MultiModalProjector)
     → map → upsert(commit) → publishSensorValues(스킵) → emitIntegrityViolations
        → checkIntegrity(row) 위반 발견
        → logger.error({action:'projection.integrity.violation', ...}, detail)   [level 50]

방출된 로그는 같은 pino 호출에서 두 레인으로 팬아웃(같은 correlationId):
  ├ Lane A: pino file → LogController @Interval(1000) → Postgres log_event
  │           → LogWindowRepositoryImpl.buildWindow(correlationId)  [앵커: level>=40]
  └ Lane B: pino socket → fluent-bit(tcp 5170) → Kafka 'log-events'
              → LogConsumer(llm-context) → prejudge  [level>=40 → triggered=true]

  → LLMContextService.analyze(): buildWindow → analysis 그래프
     → rootCauseNode → decisionNode → recommendationDocsNode(모델 불문)
        → 단일 권고 Docs(.md)
```

**correlationId 보장.** `POST /projection/multimodal`은 컨트롤러→서비스→러너로 이어지는 순수 await 체인이고, nestjs-pino가 요청 시작 시 바인딩한 자식 로거를 `AsyncLocalStorage`로 유지하므로, 배치 여러 행에서 방출한 위반 로그가 **모두 동일 correlationId**를 가진다. 따라서 `buildWindow(correlationId)`가 트레이스를 모으고 위반 로그를 앵커로 잡는다.

**소프트 레이스(주의).** `buildWindow`가 읽는 Postgres 적재는 1초 파일 폴러(Lane A) 경유다. `analyze()`가 도는 시점(Kafka+LLM 왕복, Lane B)이 훨씬 느려 실무상 이미 적재돼 있지만, 순서가 강제되진 않는다. correlationId 트레이스가 아직 없더라도 `resolveAnchor`는 `level>=40`인 최신 로그로 폴백하므로(`LogWindowRepositoryImpl:104-121`) 파이프라인은 견고하게 degrade한다.

## 5. 새 Read Model을 태우는 방법 (확장 절차)

배관(3.1~3.4)은 한 번만. 새 Read Model마다 필요한 건 **둘**뿐이다.

1. **규칙 구현** — 해당 projector에 `checkIntegrity(row, event)`를 구현해 위반을 `IntegrityViolation[]`로 반환. (도메인 지식이 들어가는 진짜 작업. 배관 아님.)
2. **컨텍스트 등록** — 권고 문서 품질을 위해:
   - `src/analysis/context/source-examples.ts`의 `SOURCE_FILES`에 그 projector·스키마 소스를 추가(생성 노드가 실제 코드를 인용).
   - 이미 존재하는 Read Model이면 Insight 카드(`PHASE1_CARDS` + `InsightSeedService`)에 그 컬럼·의미가 등록돼 있어야 `decision`/`recommendationDocs`가 스키마를 본다.

> 즉 "예시(grip/multimodal) 말고 앞으로 들어올 어떤 Read Model이든 포괄"이라는 목표는, **1번(규칙) + 2번(컨텍스트)** 로컬 추가만으로 달성된다. 로그 레인·분석 그래프는 손대지 않는다.

## 6. 설계 근거 / 트레이드오프

- **로그 레인 재사용 vs 센서 레인 복제.** 모델마다 토픽·컨슈머·베이스라인·전용 judge를 복제하는 대신(무거움), "에러 로그 방출 → 기존 로그 레인"으로 통일했다. 로그 레인의 `rootCause`/`recommendationDocs`는 read-model 이름이 박혀 있지 않은 모델 불문 노드다(`recommendationDocsOutputSchema`의 free-form `targetReadModel`). 대가: multimodal 위반은 grip 전용 `dataQuality` 포맷이 아니라 **일반 `recommendationDocs` 포맷**으로 문서화된다(값-정합성 전용 섹션이 꼭 필요하면 그때 센서 레인식 전용 노드를 추가).
- **fail-fast 보존.** 구조적 붕괴(A)는 기존대로 `map()`이 throw → 배치 롤백(이벤트 소싱에서 오염 이벤트에 멈추는 건 바람직). 이번 변경은 **의미적 값 오류(B)만** 다루며 fail-fast를 건드리지 않는다.
- **왜 예외가 아니라 훅인가.** B는 예외가 절대 안 난다(`z.string()` 통과). 그래서 "검사→위반 목록 반환"이라는 훅이 유일하게 맞는 형태다.
- **관찰적(observational) 방출.** 검사·방출은 커밋 이후 TX 밖에서, 예외를 삼키며 수행한다. 투영 결과의 정확성/성능에 영향을 주지 않는다.

## 7. 첫 구현 사례 — MultiModalProjector

`src/projection/projector/multimodal.projector.ts`의 `checkIntegrity(row)`.

**규칙 (도메인 규약 반영).** 모달별로 attempt 대조 기준이 다르다:
- **2D 이미지** — attempt 단위: 파일명 attempt == `row.attemptNum`, scene == `scene_key`.
- **video** — scene 단위 sentinel(`_00_`): attempt는 **대조하지 않고** scene만 검사.

| ruleName | 위반 조건 |
| --- | --- |
| `modalFileNameParseable` | 파일명이 `{scene}_{attempt}_{date}.{ext}` 형식 이탈 → scene/attempt 판별 불가 |
| `modalFileNameAttemptConsistency` | (2D만) 파일명 attempt ≠ `row.attemptNum` |
| `modalFileNameSceneConsistency` | 파일명의 scene ≠ `scene_key`의 scene |

파싱: `MODAL_FILE_NAME_RE = /_(\d{5})_(\d{2})_\d{8}\.[A-Za-z0-9]+$/` (확장자 불문).

**검증 결과** (실제 `checkIntegrity` 호출):

| 시나리오 | 기대 | 실제 |
| --- | --- | --- |
| **실제 정상 toy-data 139건 전수** (2D=attempt, video=`_00_`) | 위반 0 | ✅ 오탐 0/139 |
| 정상 규약(2D=attempt01, video=`_00_` sentinel) | 위반 없음 | ✅ `[]` |
| 2D가 다른 attempt(05) 참조 | `modalFileNameAttemptConsistency` | ✅ 검출 |
| video가 다른 scene(00002) 참조 | `modalFileNameSceneConsistency` | ✅ 검출 |
| 2D 형식 이탈 | `modalFileNameParseable` | ✅ 검출 |

방출되는 msg 예:
```
read_multimodal 정합성 위반[modalFileNameAttemptConsistency]: 2D 이미지 파일명의 attempt(05)가
이 행의 권위 attempt(01)와 불일치 — 다른 시도의 미디어가 scene_key=...00001 행에 매핑됨.
column=image_2d_file_name, observed="..._00001_05_20230923.jpg".
```

## 8. 알려진 한계 / 향후 확장

- **현재 fixture에는 내부 파일명 이상이 없다.** `data/anomaly-fixtures/`의 이상 fixture 3개(`ANOMALY_BAD_FILENAME`, `emptyObjects`, `transZ`)는 **내부 모달 파일명이 모두 정상**(2D=attempt, video=`_00_`)이다. `ANOMALY_BAD_FILENAME`의 "이상"은 내부 파일명이 아니라 **디스크상 JSON 파일명(`ANOMALY_BAD_FILENAME.json`) 자체가 `FILE_NAME_RE`를 못 통과**하는 것이라, insert 단계에서 거부되어 애초에 투영조차 안 된다. 즉 이 규칙이 잡도록 설계된 "모달 미디어가 다른 scene/attempt를 가리키는" 이상은 **현재 데이터에는 존재하지 않는다**(방어적 불변식으로만 유효). 실제로 잡으려는 multimodal 이상의 정체는 별도 확정이 필요하다(§본문 밖 후속).
- **3D 파일명 교차검사 미포함.** `read_multimodal` row에는 `3D_image_file_name` 컬럼이 없다(`map()`이 버림). 3D까지 대조하려면 `checkIntegrity`에서 `event.payload`를 `toyDataSchema`로 재파싱해 `3D_image_file_name`을 읽어야 한다(선택적 강화).
- **구조화 컬럼의 윈도우 노출.** `log_event`는 `sceneKey/streamId/attemptNum/projectorName` 전용 컬럼과 `payload` jsonb를 이미 보존한다. `LogWindowRepositoryImpl`/`renderAnomalyWindow`를 확장해 이들을 윈도우에 노출하면 근거 grounding이 더 풍부해진다(작고 고가치인 후속 작업).
